# Sandbox Manager 多 Infra 支持设计

## 摘要

同一 Sandbox Manager 可以注册多个 Infra 实现，并通过 `--default-infra` 指定唯一默认后端。内置 OpenKruise Infra 的公开标识为 `openkruise`，本次必须注册，也是参数默认值。连接配置不改变默认选择，一次操作中的资源查找、授权检查和实际执行始终落在同一后端。

E2B 管理 API 对创建、列表及没有源 Sandbox 的资源操作使用 `x-e2b-kruise-infra` 选择后端；省略时选择默认后端。管理 API 查询已有 Sandbox 时仍从 Route 取得归属，先按调用方权限过滤候选，唯一可访问候选不受隐藏候选影响；可通过 Infra 消歧时，仅返回可访问的候选 Infra，由用户显式选择，同一 Infra 内仍有歧义则拒绝。选中交付后，实际写入及重试只能作用于原交付。Gateway 流量请求带非空请求头时只在选中 Infra 内解析 Route；省略或空值时从全部 Infra 的已观测候选中取得唯一归属；缺失、歧义或无法转发时返回通用 `502`。自动唤醒的写入遵守同一交付身份约束，唤醒后继续转发前再次复核身份。

Route 保留现有数据字段和共用的 Sandbox CR 转换逻辑，增加 Infra 归属；资源记录、删除水位、内部查询和版本比较按来源隔离。普通不可服务状态仍保留候选，明确删除由 Infra 单独表达。所有 Infra 都必须提供起到顺序号作用的 `resourceVersion`。Manager 统一管理覆盖全部后端的 API-key 配额，并依赖完整的占用观测。Gateway 将入口 API 的请求解析与 Infra 的转发格式适配分开，不预设新后端都通过 IP 和端口转发；本次不新增全量路由同步或重启恢复机制。

## 背景

OpenKruise Agents 通过 Sandbox Manager 提供 Sandbox 的创建、查询、暂停、恢复和释放能力。OpenKruise Infra 使用 Sandbox CR 及其控制器管理资源；其他后端实现可以通过相同的 Infra 接口接入 Manager。

单后端模式中，请求和资源隐含属于同一个 Infra。多个后端并存后，仅允许注册多个实现还不够：创建时查询模板的后端必须与执行创建的后端一致；管理 API 后续操作必须回到资源原来的后端；Gateway 流量入口需要独立选择后端并采用该后端的转发格式；不同后端的同名资源不能相互覆盖路由或删除记录；原有 API-key 配额也不能因增加后端而被拆成多份。

本设计面向需要在同一管理入口接入不同后端实现的部署者和开发者。默认配置延续使用 OpenKruise 管理 Sandbox 的行为，显式选择则允许调用方访问其他已注册后端。Route 复用现有公共 ID 查询入口，同时表达资源归属，避免新增一份独立的 ID 到 Infra 持久化映射。

## 设计终态

### 职责与范围

管理面的依赖方向保持为 API → Manager → Infra。API 层解释管理请求头、执行认证与授权、转换协议模型和错误；Manager 负责后端选择、Sandbox 生命周期编排、准入及配额；Infra 负责具体资源操作和后端观测。API 层不通过取得后端客户端或缓存来执行本次涉及的资源操作，Manager 和 Infra 不解释 HTTP 请求头。

Gateway 负责流量入口，通过中立的请求与 Route 契约分隔入口协议解析和 Sandbox 实现的转发适配。Gateway Infra 承担流量适配职责，不因使用相同的后端标识而依赖 Manager Infra 的资源管理实现。现有 OpenKruise 流量唤醒对 Manager Infra 实现的依赖属于遗留债务，本次不扩大，也不要求迁出。

所有 Manager Infra 都必须完整实现管理面的 Infra 接口。暂不支持的方法仍需实现，并在调用时明确报错；不能伪装成成功、返回另一后端的结果或使请求自动回退。本次不拆分必选与可选能力接口，不新增能力发现或通用插件框架。接口实现不等于所有功能可用；Manager 启动所需的基础依赖，以及启用配额所需的观测能力，仍须通过各自的启动校验。

本次支持不同后端实现并存，不支持同一种实现的多个命名实例。内置实现只有 OpenKruise Infra，本次必须注册；其他后端与它并存，而不是替代它。公开标识与内部代码组织分离：公开名称统一为 `openkruise`，本次不重命名现有实现目录或 Go 包。

### 注册与默认 Infra

Manager 在构建阶段累积注册 Infra，每个注册项具有稳定、非空的标识，完整匹配 `[A-Za-z0-9][A-Za-z0-9_-]*`：以 ASCII 字母或数字开头，后续只允许 ASCII 字母、数字、下划线或连字符。注册和请求选择使用同一标识语法，非法标识使注册失败。同一标识不能重复注册或覆盖已有实现。标识区分大小写，注册、请求选择、Sandbox 绑定及 Route 归属使用同一值，不自动转换大小写或推导别名。

`sandbox-manager` 通过 `--default-infra` 选择唯一默认 Infra，参数默认值为 `openkruise`。该参数只能引用已注册项，不负责创建或注册后端。未注册 `openkruise`、显式空值、未注册值、重复注册及注册后端初始化失败均使启动失败，不能静默跳过后端或改用另一个默认值。默认项不由注册顺序、连接地址或后端构建结果推导。

连接配置、Infra 注册和默认选择各自独立。为一个后端提供连接信息，不会自动使其成为默认后端。注册集合和默认项在进程启动时确定，本次不提供运行时热切换或动态注册。

共享同一管理与路由范围的 Manager 副本必须使用一致的 Infra 标识及其后端归属；提供同一 API 入口的副本还应采用一致的默认项，避免未指定 Infra 的请求因副本不同而改变含义。

Manager 通过中立的 Infra 操作选项接收选择。尚未绑定资源的操作省略选择时使用默认项；显式选择仅影响当前操作。改变启动默认值不会迁移已有 Sandbox，也不会重写其 Route 归属。

### 请求选择与 Sandbox 绑定

E2B 管理 API 的原生路径与定制路径采用相同选择规则。

管理 API 和 Gateway 的 `x-e2b-kruise-infra` 均为单值请求头。重复请求头即使值相同或均为空，也返回 `400`；含逗号的值（包括代理合并后的值）同样返回 `400`，不得取第一项、最后一项或拆分后选择。

解释字段值前移除首尾 HTTP 空格（SP）和水平制表符（HTAB）；非空值必须完整匹配注册标识语法，否则返回 `400`。内部空白、点号、引号及其他不在语法中的字符均不合法。移除后为空的值，包括原本仅含上述空白的值，按各入口的空值规则处理，不与请求头省略混为一谈。

| 操作 | Infra 来源 |
| --- | --- |
| 从模板或快照创建 Sandbox | `x-e2b-kruise-infra`；省略时使用默认 Infra |
| 列出 Sandbox | 请求头；省略时只查询默认 Infra，不跨后端聚合 |
| 查询、删除、暂停、恢复、连接或修改已有 Sandbox | Sandbox 的 Route；显式请求头只能限定已有候选，不能改写归属 |
| 为已有 Sandbox 创建快照或执行 Fork | 源 Sandbox 的 Route 及取得的绑定对象 |
| 模板操作、快照列表和无源 Sandbox 的快照操作 | 请求头；省略时使用默认 Infra |
| 存储卷操作 | 请求头；省略时使用默认 Infra，归属检查与操作使用同一选择 |

只有省略请求头才可能按上表使用默认值；管理 API 对显式空值或纯空白值返回 `400`，无效格式按上述规则返回 `400`，未注册值也导致请求失败。没有源 Sandbox 的资源可能具有相同名称或 ID，调用方必须在关联请求中保持同一 Infra 选择。例如，快照可以在源 Sandbox 删除后继续存在，使用快照创建 Sandbox 不能依赖已经消失的源 Route。

一次操作只选择一个 Infra。模板或快照查找、参数转换、资源归属检查和实际创建必须围绕同一后端的资源进行；Manager 根据该次操作执行共享配额准入。选中后端不存在资源、不支持操作或执行失败时，保留该失败，不继续尝试其他后端。

Manager 返回的 Sandbox 对象保留 Infra 绑定，包括创建结果、列表结果和从后端观测重建的对象。绑定来自注册关系和可信观测来源，不能由用户 metadata 覆盖。暂停、恢复、删除及其他对象操作沿用绑定；同时提供对象和显式选择时，两者必须一致。后台工作和内部去重也不得将不同 Infra 的资源当作同一对象。

例如，默认项为 `openkruise`，请求显式选择另一个已注册 Infra 创建 Sandbox。后续不带请求头的 Sandbox 查询仍通过 Route 找回该后端；不带请求头的列表只返回 `openkruise` 的资源。

### 管理 API 授权与公共 ID 冲突

公共 Sandbox ID 保持不透明，不能通过解析 ID 推断 Infra。OpenKruise Infra 沿用既有公共 ID 和短 ID 行为；其他实现也必须提供在同一次资源交付期间稳定、可从后端观测恢复的公共 ID。默认 Infra 变化或 Manager 重启不得自行改写已有交付的 ID。

ID 生成方应保证共享 Route 查询范围内的公共 ID 唯一。重复处理只提供兜底，不替代防重机制，也不在本次引入统一发号服务。暂停、暂时无 IP 或存在 ID 冲突，都不是丢弃资源归属记录的理由。

E2B 先认证调用方，再通过 Manager 查询 Route 候选；有合法 Infra 请求头时，只在指定后端内解析。对该范围内的候选逐条执行现有归属检查，过滤无权访问的记录后，再判断唯一性或冲突。这里的用户身份沿用资源 `owner` 所对应的 API-key 身份，不扩大为同一团队；其他用户或 owner 为空的候选不计入可访问候选，也不改变管理 API 的候选选择结果。这样，隐藏候选的出现不会使调用方原本唯一可访问的 Sandbox 因冲突而不可访问。

以下规则均以过滤后的可访问候选为准。同一 Infra 内的歧义优先于跨 Infra 冲突处理，不能通过补充 Infra 请求头区分该后端内的资源。

| 请求情形 | 管理 API 行为 |
| --- | --- |
| 当前查询范围内没有可访问候选，包括没有 Route 记录 | 返回 `404`，不披露隐藏候选的存在、数量或 Infra 列表；不使用默认 Infra、不转查其他后端，也不通过请求头创建归属记录 |
| 无 Infra 请求头，只有一个可访问候选 | 使用该候选（其 Infra 与资源身份），即使还存在其他用户或归属不明的记录 |
| 无 Infra 请求头，可访问候选分属多个 Infra，且每个 Infra 仅有一条 | 返回 HTTP `409`、`sandbox_id_conflict` 错误标识及可访问候选的 Infra 列表，不执行操作 |
| 当前查询范围内，任一 Infra 有多条可访问候选 | 返回 `404`，拒绝歧义访问；即使其他 Infra 也有可访问候选，也不返回跨 Infra 选择响应或要求补头的提示 |
| 有合法 Infra 请求头，指定后端内只有一个可访问候选 | 使用该候选；其他 Infra 的候选及其歧义不影响本次解析 |

仅在上述可通过 Infra 消歧的跨后端冲突中，响应保留既有错误字段，并提供以下信息：

```json
{
  "code": 409,
  "error_code": "sandbox_id_conflict",
  "message": "Specify x-e2b-kruise-infra to select a sandbox.",
  "infras": ["openkruise", "backend-b"]
}
```

`backend-b` 仅为已注册扩展实现的示例标识。`infras` 只包含通过本次归属检查的候选 Infra，不包含仅有隐藏候选的 Infra。`error_code` 和 `infras` 表达本扩展的语义，客户端可据此让用户选择后携带请求头重试；本设计不要求已有 E2B SDK 自动处理选择交互。响应不得附带其他用户身份、后端连接信息或路由凭据。

候选选择、访问检查和本次请求使用的资源身份及 Infra 必须保持一致，不能在后续处理时重新按默认项选择。取得选中候选对应的后端 Sandbox 后，先确认其 Infra 和 `UID` 与该候选一致，且当前公共 ID 仍等于请求中的 ID；任一不一致均按未找到处理。同一后端资源可能被回收后以新 ID 再次交付，资源身份相同不代表仍是同一次交付。之后仍检查实际资源归属和操作所需状态；Infra 选择本身不授予访问权限，上述任一检查失败都不转查其他候选。因选择歧义或访问检查失败而拒绝的请求，不修改任何候选资源。用户可以通过显式 Infra 查询或删除该后端内唯一可访问的冲突资源，但不能把该选择用于修改另一候选的归属。

选中候选后，本次操作固定其 Infra、后端资源身份（资源键及 `UID`）和公共 Sandbox ID，形成不可被刷新或重试替换的预期交付身份。可能产生副作用的 Infra 操作必须通过后端条件操作或等价的并发控制，保证每次副作用提交只作用于该交付；仅在调用前检查身份不满足此要求。只保护 `UID` 也不足以保护同一资源实例再次交付时的公共 ID 变化。

发生重读或冲突重试时，必须重新确认当前对象仍属于原交付，并检查当前归属和操作所需状态。交付身份变化时终止原操作，管理 API 按未找到返回 `404`，不得重新选择候选或将请求自动应用到新交付。仅版本变化不代表交付变化；确认仍是原交付且归属和状态允许后，可以使用最新版本再次尝试受保护的提交，但不能只刷新 `resourceVersion` 就无条件重放旧操作。具体条件操作机制由各 Infra 实现选择，不要求新增全局锁或持久化 ID 映射。

例如，在资源归属和操作状态均满足要求时，调用方在 `openkruise` 拥有公共 ID `X`，另一用户在 `backend-b` 也有 `X`：无头查询返回调用方自己的 Sandbox；显式指定 `backend-b` 则返回 `404`，不转查 `openkruise`。如果两个后端中的 `X` 都属于调用方且各只有一条，无头查询返回 `409`。如果调用方在 `openkruise` 内有两条 `X`，在 `backend-b` 内有一条，无头查询返回 `404`；显式指定 `backend-b` 仍可查询其唯一候选，指定 `openkruise` 则仍返回 `404`。

又如，某后端资源以公共 ID `X` 交付后被回收，随后以新 ID `Y` 再次交付给同一调用方，而某个副本的 Route 仍记录 `X` 指向该资源：对 `X` 的删除重试返回 `404`，不能删除 `Y`。即使旧请求已经通过身份、归属和状态检查，而交付变化发生在实际写入前或冲突重试期间，也必须拒绝对新交付的删除或修改。同 `UID` 换公共 ID、同名资源重建换 `UID` 均受此约束；新旧交付属于同一调用方不能免除身份保护。

### Route 模型与最小解耦

Route 继续承载公共 Sandbox ID、资源身份、owner、状态、目标信息及访问凭据，并增加 Infra 归属。`Namespace`、`Name`、`UID` 等现有字段仍可使用，它们表示适配后的资源身份，不要求每个后端都存在 Sandbox CR。公共 ID 是交付与查询身份，后端资源身份用于区分对象及其更新，二者不可互相替代。

每个 Infra 通过 `GetRoute()` 提供统一 Route，把后端原生数据转换为共享状态和字段语义。共享 Route 存储不解释各后端原生状态、模板模型或连接配置。OpenKruise Infra 和 Gateway 本地 Sandbox informer 继续共用现有 Sandbox CR 转换逻辑，不各自复制规则，也不为复用转换而增加 Gateway 对 Manager Infra 的依赖。

路由资源记录和删除水位以 `(Infra, Namespace, Name)` 隔离，`UID` 区分同名对象的不同资源实例。公共 ID 查询必须能够保留并识别多个资源候选，不能让后到的记录静默接管已有 ID。候选指选定来源范围内尚未删除的全部记录，不按生命周期状态、是否已有 IP 或能否接收流量筛选；管理 API 与 Gateway 对候选存续的口径一致，但前者按授权过滤后解析，后者不按调用方过滤，在请求头选中的 Infra 内、或无请求头时在全部 Infra 内判断目标是否唯一。更新、删除和 ID 变更只影响对应资源；冲突候选删除或不再使用该 ID 后，根据剩余记录重新判断歧义。

内部按 ID 读取 Route 时也必须保持来源范围。例如，OpenKruise Infra 读取 Route 版本以判断本地 CR 缓存是否落后时，只能读取对应后端、对应资源的记录，不能将另一 Infra 的版本与本地 CR 比较。

所有生产者都写入正确归属，包括创建结果、后端观测、Manager 操作后的更新和删除，以及 Gateway 本地 informer 的更新和删除。OpenKruise 的已知观测来源明确写入 `openkruise`；Manager 根据注册来源绑定其他后端的观测，不信任用户可编辑字段中的 Infra 声明。归属信息在现有分发链路中保持完整。

公共 ID 的唯一性由其生成方负责：OpenKruise 短 ID 由 Manager 分配，其他后端的公共 ID 由对应 Infra 提供。Manager 保证正常生命周期内元数据存在、交付身份连续；暂停和唤醒不会使元数据消失。Gateway 使用这些可信资源信息，不另建一套存在性保证。显式删除提交后，不可逆的删除中间态即视为明确删除，无需等待元数据物理消失；删除最终清除元数据。对 OpenKruise 而言，只有非空 `deletionTimestamp` 和 `Terminating` 阶段属于明确删除；`Succeeded`、`Failed`、超时和未就绪都是状态更新。

Route 的状态更新与明确删除是不同语义。普通不可服务状态，包括仅因未就绪或超时得到的 `Dead`，不能单独作为删除信号；只要交付仍有效，记录继续参与候选判断。Infra 负责给出明确删除语义，使 Manager 观测、Gateway 本地观测与 peer 刷新对此保持一致；已接受删除或回收引起的交付撤销可据此移除对应 Route。删除仍遵守现有版本排序和删除水位规则。

<!-- known-limit: 本次仅区分状态更新与明确删除，不保证回收成功后旧交付的 Route 永不被后续观测重建；如需该保证，应另行定义交付撤销与后续观测、恢复的完整契约。 -->

### resourceVersion 顺序契约

`resourceVersion` 是所有 Infra 都必须提供的顺序信息，承担 SEQ 的作用，不能因后端不是 Kubernetes 而省略。本次沿用现有规范正整数表示和比较方式，不增加任意版本格式或后端专属比较器。

版本只在同一 Infra、同一资源键内比较。不同 Infra 或不同资源的版本没有比较意义。每个后端必须保证多个观察者对同一变化取得一致的版本，并能正确区分后续变化，包括同名资源删除、重建后的新旧顺序；不能在 Manager 重启后把版本重置为进程内计数，也不能用观察者本机时间代替后端顺序保证。

更新只接受比当前资源记录或删除水位更高的版本；同版本重复更新不改变状态。删除不得撤销更高版本的记录，同版本删除可以结束该版本的资源记录。删除水位保留期间，删除之前的迟到更新不得使资源重新出现。

例如，同一 Infra 中某资源的版本 `12` 已生效，随后收到版本 `11` 的更新或删除，都不能覆盖版本 `12`。另一 Infra 中同名资源的版本 `3` 不受影响。某资源在版本 `13` 删除后，版本 `12` 的迟到更新不能在删除水位仍有效时恢复它。

沿用现有删除水位的有限保留规则：从首次建立起保留十分钟，后续删除可提高水位但不延长保留期。OpenKruise 本地 informer 对无法取得版本的既有 tombstone 处理例外继续限制在原来的可信来源和语义内；其他后端以及跨节点删除不能借此省略版本。

<!-- known-limit: 删除水位过期后不保证拒绝任意久远的重放；若需要该保证，应单独设计持久化水位或带恢复边界的同步协议。 -->

### 旧 Route 兼容与 Gateway 边界

接收旧 Route 时，未填写 Infra 字段或字段为空，统一解释为 `openkruise`。这一兼容归属固定不变，不使用 `--default-infra`。新生产者必须显式写入 Infra；已填写的非空值不能因无法识别而改写为 `openkruise`。Manager 无法使用未注册的 Infra 执行资源操作，也不能通过请求头替缺失的 Route 创建记录。

未填写 Infra 的旧 Route 同时沿用旧的删除语义，其 `Dead` 或空状态视为删除。新生产者以明确删除标记表达删除，并在删除推送中保留 `Dead` 状态，使尚未升级的组件仍按删除处理；新组件对新格式 Route 只依据明确删除标记判断删除。

该兼容行为支持原有单 OpenKruise 后端部署中的版本过渡。启用多个后端前，共享路由范围内的 Manager、Gateway 及现有流量代理必须都能识别 Infra 归属、来源隔离和状态更新与明确删除的区别；旧组件忽略 Infra 字段或把所有 `Dead` 状态当作删除时，不能宣称具备新的多后端候选与隔离保证。

E2B 流量入口可以携带与管理 API 相同的 `x-e2b-kruise-infra` 请求头。带非空请求头时，Gateway 只在该 Infra 内解析 Route，选定后不转查其他 Infra。省略请求头或其值为空时，从全部 Infra 的 Route 候选中取得归属，不使用默认 Infra。Gateway 将空值视为未指定，是流量入口的特定行为；管理 API 仍拒绝显式空值，不能因共用解析逻辑而抹平该差异。官方 E2B SDK 发往 Sandbox 的请求和浏览器端口访问都不携带自定义请求头，这类流量依靠 Route 找到所属 Infra。请求头格式无效时返回 `400`，不得回退；格式有效但该 Infra 下没有候选时按缺失处理。

Gateway 及现有流量代理沿用既有就绪门控。允许进行路由查询时，在上述范围内解析已观测到的公共 ID 候选：请求头指定非空合法标识时为选中 Infra，省略或空值时为全部 Infra。与管理 API 不同，Gateway 不按调用方过滤候选；范围内缺失或多于一条，均返回通用 `502`，不披露候选、不提示改选 Infra，也不尝试其他范围。暂停、创建中及其他暂不能接收流量的记录同样计入歧义判断；若只有一条，则继续沿用既有鉴权和非 `Running` 状态处理。选择 Infra 本身不授予流量权限。

例如，`openkruise` 的暂停资源 `X` 与另一 Infra 的运行资源 `X` 并存：没有请求头时两条都计入，返回通用 `502`，不转发给运行中的那一条；显式选择另一 Infra 只解析其候选，不受 `openkruise` 中的记录影响；选择 `openkruise` 时仍按其暂停状态处理。若 `openkruise` 内另有第二条 `X`，选择该 Infra 返回通用 `502`，不转向另一 Infra。若只有另一 Infra 有 `X`，没有请求头的流量按其 Route 选中该 Infra；该 Infra 缺少转发能力时拒绝流量。

Gateway Adapter 按 API 和 Infra 分工。API Adapter 理解具体入口协议及其请求头，当前支持 E2B，未来可增加其他协议；它将请求转换为中立的标准请求。Infra Adapter 代表 Sandbox 的具体实现，结合标准请求和选中资源的 Route 信息构造对应转发格式，不重新解释入口协议的 Infra 选择。两侧分别扩展，标准请求不把所有后端的转发方式固定为 IP 加端口。

现有 `openkruise` 目标和转发能力继续适用。其他 Infra 尚未实现，对应转发方式由其后续接入设计确定；缺少对应转发能力时以通用 `502` 拒绝流量，不能套用 OpenKruise 的方式。已有自动流量唤醒仍只作用于 `openkruise`，只能操作已通过鉴权的 Route 所对应的资源实例，不得用其他 Infra 的资源身份操作本地 Sandbox CR；其他后端的通用唤醒不在本次范围内。

自动唤醒以最初通过鉴权的 Route 固定预期交付身份，资源修改及其重读、冲突重试同样遵守上述 Infra 副作用契约。发现交付身份变化时停止唤醒并返回通用 `502`，不得修改新交付；唤醒结束后的转发复核不能替代唤醒写入时的保护。

等待唤醒等异步操作结束后，Gateway 在同一 Infra 内重新解析；只有 Infra、`UID` 和公共 ID 都与最初通过鉴权的 Route 一致时才继续转发，否则返回通用 `502`。同名重建的资源可能沿用遗留 ID，因此不能仅凭公共 ID 判断仍是同一次交付。这项复核只使用已有 Route 信息，不要求 Gateway 建立独立的身份或元数据系统。

Infra 信息和明确删除语义须沿路由链路传播，并由相关消费者一致理解。本次沿用现有分发和版本机制，不新增启动全量同步、定期全量校准或新的 Gateway 重启恢复协议。Manager 从后端重新观察资源时必须恢复同一公共 ID 和正确归属，但不新增所有副本立即可见的保证。

### 共享配额与进程级依赖

同一 API key 的配额覆盖全部已注册 Infra，不按默认项或单次请求选择拆分。例如，某 key 的 Sandbox 总数上限为十，在两个后端各占用六个不能因后端不同而被视为分别未超额。

配额继续由 Manager 统一编排，沿用现有配额模型、Redis 原子计数和准入行为。用于标识一次配额占用的 lock 身份独立于公共 Sandbox ID，必须在同一配额主体范围内唯一，并在准入、回滚、删除释放和后端观测中保持一致；不同 Infra 的占用不得相互覆盖或释放。

实际启用共享配额时，所有注册 Infra 都必须提供完整的占用列表、变化观测和健康状态。任一后端缺少所需能力、返回不支持或无法建立必要观测，启动失败并指出对应 Infra；不能只统计默认后端或仅统计 OpenKruise。认证关闭或未配置配额 Redis 时，沿用既有不执行配额的行为。

Manager 将全部 Infra 的观测合并后，与共享账目进行校准。任一参与后端的列表失败或观测不完整，都不能把部分结果当成全集，推断其他后端的占用已经消失。运行中依据“未观察到资源”释放占用时，仍须满足完整、健康观测和既有等待窗口要求；失去主实例身份时停止校准写入。

这一限制不阻止已经取得明确结果的直接释放：Manager 已接受对应 Sandbox 的删除或回收后，仍按既有 owner 和占用身份释放配额。观测事件路径继续遵守现有健康检查。Redis 传输失败的既有 fail-open 策略不变，本次不重新定义配额的生命周期范围或恢复操作的准入规则。

Manager 的发现、主实例协调、共享配额和 OpenKruise 短 ID 分配，以及 API 层的 API-key 存储和团队 namespace 校验，都属于进程级职责。其依赖不随单次请求选择的 Infra 切换，也不因默认后端变化而消失或改用其他后端的连接和缓存。OpenKruise 的短 ID 配置不强制改写其他后端的公共身份。

### 非目标与适用边界

本设计不提供同类 Infra 多实例、跨 Infra 列表聚合、跨后端资源迁移或自动故障切换，也不支持不注册 `openkruise`、仅接入其他后端的部署。模板、快照和存储卷的选择不会隐式复制资源到其他后端。

<!-- known-limit: 本次要求注册 openkruise，进程级依赖可与其共用 Kubernetes 访问；若需支持仅接入其他后端的部署，应先为进程级依赖提供独立于任何 Infra 的 Kubernetes 访问。 -->

不新增独立 ID 到 Infra 持久化映射、统一 ID 发号服务、动态插件框架或全局实时冲突检测。后端必须满足稳定身份和有序版本契约；不能把未满足这些契约的实现，仅凭注册成功视为已完成接入。

冲突兜底和跨 Infra 解析只基于节点已经观测到的候选，本地唯一不代表全局实时唯一。节点缺少某 Infra 的记录时，可能把同公共 ID 的另一条误判为唯一。

本次确定 Gateway 的后端选择和 Adapter 分工，不实现其他 Infra 的转发机制、通用流量唤醒、全量路由恢复或新的同步协议。现有 Route 数据可表达和传播其他 Infra 的归属，不意味着 Gateway 重启后已具备这些后端的完整恢复与可靠同步能力，也不意味着所有数据面消费者已具备该后端的完整运行能力。

<!-- known-limit: 当前解析保证受节点观测范围限制；如需完整恢复、可靠同步或更强的候选可见性保证，应另行设计路由恢复与同步契约。 -->

本次不新增 JWT Infra claim。现有流量 JWT 只绑定公共 Sandbox ID 和 `UID`，跨 Infra 防重放依赖同一公共 ID 下各 Infra 的 `UID` 不重合。其他 Infra 启用流量能力前，必须验证其身份机制满足这一前提，作为接入验收条件；不能仅凭已注册或已传播 Route 就启用流量能力。

<!-- known-limit: 若新 Infra 无法满足上述 UID 前提，应在启用流量前另行设计 JWT 的 Infra 绑定。 -->
