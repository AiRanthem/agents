# 当前决策

- 用户要求同时支持 Webhook 和 WebSocket 两种 IM 唤醒方式。
- 用户要求将能力做成通用能力，飞书和 OpenClaw 作为具体场景。
- 2026-11-03，用户要求保存原理分析后，拆成 Webhook 唤醒与 WebSocket 唤醒两个并列需求。本项保留原 ID 并收敛为 Webhook 唤醒，同级新项 `3-websocket-wakeup` 承接 WebSocket 唤醒。
- 2026-11-03，用户要求“开始设计webhook唤醒的需求”，授权本项设计探索。
- 2026-11-03，用户明确修正此前“可靠接收”的解释：“不需要做到强可靠，放在内存中就行了，如果收到事件的 Gateway 退出了可以接受事件丢失。”当前契约采用 Gateway 内存接收后确认、异步唤醒与交付；替代此前持久化及跨进程恢复方向。
- 2026-11-03，用户对前述两项建议回复“都按照推荐来”：首期每个 Webhook 接入绑定一个已有 Sandbox，用户和群聊由应用内部路由；自动唤醒开关开启时，手动 Pause 后也允许合法消息唤醒，持续保持暂停需关闭开关。
- 用户要求确认现有 Gateway 优雅下线能否等待所有事件处理结束；分析采用所有唤醒固定 10 秒的假设，并明确要求读取实际 ack-components 编排，不使用源码仓示例编排。
- 用户回复“正常下线的顺序可以做，应该怎么办？”，接受先停收、等待已接收事件完成唤醒与应用交付、最后退出的方向，并要求细化。下线不等待 OpenClaw 最终业务回复；具体本地管理接口与 30 秒业务排空预算是本轮建议，尚未实施。
- 当前没有完整正式设计批准、独立审查、实施或代码交付结果。内存接收、退出可丢失、单接入单目标和上述暂停语义已确认；此前提出的持久存储、24 小时重试、7 天保留和可信中继重签不作为当前已批准方案。
