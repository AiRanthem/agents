# 基于 Webhook 事件的 Sandbox 自动唤醒

## 目标

已有 Sandbox 处于 Pause 时，通过外部可达的 Webhook 入口接收合法 IM 消息事件，自动恢复目标 Sandbox，使其中的应用重新具备消息处理能力。

能力面向通用 IM 平台与应用；飞书事件订阅与 Sandbox 内 OpenClaw 是首个业务场景。Webhook 指平台向开发者接收 URL 推送事件，不指向群发送消息的自定义机器人 Webhook。

## 已确定范围

- 覆盖已经存在、处于 Pause 的 Sandbox。自动唤醒开关开启时，手动 Pause 和自动 Pause 均可被合法消息唤醒；需要持续保持暂停时关闭该开关。
- 上游采用 HTTP Webhook 事件推送，休眠期间仍有可访问的入口承接事件或触发恢复。
- Gateway 将合法事件接收到内存后快速确认，再异步恢复目标并交付。用户接受接收事件的 Gateway 退出后未完成事件丢失，不要求持久化或跨进程恢复。
- 将合法消息关联到正确目标，在授权边界内触发恢复，并定义应用就绪后的事件处理行为。
- 首期每个 Webhook 接入绑定一个已有 Sandbox，接入层不按用户或群聊分配多个 Sandbox；用户、群聊及 Agent 会话路由由 Sandbox 内的应用负责。
- 平台协议由适配层承担，通用唤醒能力不能限定为飞书或 OpenClaw 专用逻辑。
- 与 `3-websocket-wakeup` 为同级独立需求，可分别交付和验收。

本项以 IM 消息事件为当前场景；同步卡片操作、链接预览等回调具有不同响应语义，其支持范围需另行明确。

## 机制约束

来源验证、目标映射及唤醒授权应在触发恢复的信任边界明确。URL 校验请求、非法请求与普通 IM 事件需要区分。

飞书事件确认窗口短于部分可能的冷启动时间，且失败重试有限。接收确认与 Sandbox 冷启动、模型回答解耦；当前选择 Gateway 内存缓冲，不承诺已确认事件在 Gateway 退出后仍能恢复。内存容量、满载响应、去重和短时重试边界需继续细化。

正常下线采用先停止接收新事件、再等待已接收事件完成唤醒和应用交付、最后退出的顺序。排空过程保留任务所需的路由、唤醒和转发能力，等待不包括应用生成最终回复。现有 ack-components 的 drain + sleep 尚不具备该业务排空能力。分析以实际 ack-components 编排与对应镜像源码为依据；用户指定所有唤醒固定耗时 10 秒，不考虑极端慢的唤醒，这不是实测耗时或线上 SLA。

OpenClaw 处理消息后主动调用飞书消息 API 回复用户，Webhook 的 HTTP 接收确认不承载最终回答。外部接收层向应用交付完成的判据、应用业务执行及最终回复的责任边界仍需明确。

并发请求可以合并同一目标的恢复操作，不同消息需保留各自处理语义；事件重投和业务副作用的幂等边界需分别定义。

## 验收方向与待明确事项

基础场景：飞书通过 Webhook 投递合法消息事件，承载 OpenClaw 的 Sandbox 已 Pause；Gateway 内存接收并确认，正确目标随后恢复，事件交给应用。正常下线先停收再排空，刚好与停收并发的接收不得遗漏：事件要么已登记并纳入等待，要么未被接收并返回失败。进程故障或无法在终止预算内完成时仍可能丢失未完成事件，不增加跨进程恢复保证。

正式验收前需明确：

- 触发消息范围、接入配置与目标身份校验、凭据配置责任。
- 唤醒成功与应用就绪的判定、时延要求、恢复失败行为。
- 已接收的首条及后续消息的交付完成判据、内存上限、短时重试与终止条件，以及正常下线的排空时间预算。
- 超过平台确认窗口、请求取消、重复事件和消息并发时的结果。
- 关闭自动唤醒时新事件和已接收事件的处置，以及目标不存在或已运行时的策略。
- 未授权事件不触发恢复，以及 challenge 等协议请求的处理边界。
- 通用扩展接口，以及首期平台、事件和应用支持范围。
