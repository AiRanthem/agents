# 基于 Webhook 事件的 Sandbox 自动唤醒

## 目标

已有 Sandbox 处于 Pause 时，通过外部可达的 Webhook 入口接收合法 IM 消息事件，自动恢复目标 Sandbox，使其中的应用重新具备消息处理能力。

本项按用户最新要求收敛为独立的飞书 IM Webhook 功能，采用标准飞书事件订阅协议，Sandbox 内 OpenClaw 是目标应用场景。Webhook 指飞书向开发者接收 URL 推送事件，不指向群发送消息的自定义机器人 Webhook。本项不要求先设计通用多 IM 接入框架。

## 已确定范围

- 覆盖已经存在、处于 Pause 的 Sandbox。自动唤醒开关开启时，手动 Pause 和自动 Pause 均可被合法消息唤醒；需要持续保持暂停时关闭该开关。
- 上游采用 HTTP Webhook 事件推送，休眠期间仍有可访问的入口承接事件或触发恢复。
- Gateway 将合法事件接收到内存后快速确认，再异步恢复目标并交付。用户接受接收事件的 Gateway 退出后未完成事件丢失，不要求持久化或跨进程恢复。
- 将合法消息关联到正确目标，在授权边界内触发恢复，并定义应用就绪后的事件处理行为。
- 首期每个 Webhook 接入绑定一个已有 Sandbox，接入层不按用户或群聊分配多个 Sandbox；用户、群聊及 Agent 会话路由由 Sandbox 内的应用负责。
- 接收及交付采用标准飞书 IM 事件 Webhook 协议，复用已有 Gateway 路由与唤醒能力；不以 OpenClaw 私有接收接口或响应头作为协议要求。
- 与 `3-websocket-wakeup` 为同级独立需求，可分别交付和验收。

本项以 IM 消息事件为当前场景；同步卡片操作、链接预览等回调具有不同响应语义，其支持范围需另行明确。

## 机制约束

来源验证、目标映射及唤醒授权应在触发恢复的信任边界明确。URL 校验请求、非法请求与普通 IM 事件需要区分。

飞书事件确认窗口短于部分可能的冷启动时间，且失败重试有限。接收确认与 Sandbox 冷启动、模型回答解耦；当前选择 Gateway 内存缓冲，不承诺已确认事件在 Gateway 退出后仍能恢复。内存容量、满载响应和上游重复事件合并仍需细化。

正常下线采用先停止接收新事件、再等待已接收事件完成唤醒和应用交付、最后退出的顺序。排空过程保留任务所需的路由、唤醒和转发能力，等待不包括应用生成最终回复。现有 ack-components 的 drain + sleep 尚不具备该业务排空能力。分析以实际 ack-components 编排与对应镜像源码为依据；用户指定所有唤醒固定耗时 10 秒，不考虑极端慢的唤醒，这不是实测耗时或线上 SLA。

业务排空从首次停收开始最多等待 60 秒，任务清空立即返回，重复调用不延长截止时间。到期取消剩余任务并记录结果，继续既有连接 drain 和退出；超时不算成功交付。新 Webhook 返回 503，readiness 返回失败，liveness 保持正常，排空期间保留任务依赖。ACK 后的任务由进程持有，客户端断连和请求销毁不取消它。管理接口仅限 Pod 内使用。

飞书普通事件的协议接收确认是 HTTP 200；Gateway 在完成合法事件的内存登记后于平台确认窗口内返回该响应。向 Sandbox 内实现标准飞书事件接收接口的应用转交时，普通事件请求得到 HTTP 200 即按协议认定接收完成，不据此承诺业务执行或回复成功，也不额外要求 OpenClaw 的 durable 响应头。URL 校验的 challenge 单独处理，不能算成普通消息交付。转交保留原始 body、事件 ID 与相关飞书签名头，不任意重建签名载荷。

用户于 2026-11-04 明确：按当前默认配置等待唤醒，唤醒后采用简单的指数退避，最多重试五次，失败打日志放弃。沿用现有有效唤醒等待配置，不因本项另加一套恢复等待参数；等待失败或超时后记日志并结束该事件。唤醒成功后立即首次投递，失败最多再重试五次，即最多六次请求。连接失败、请求超时、响应丢失或非 HTTP 200 均按失败处理；得到 HTTP 200 即结束，次数耗尽则记日志并释放任务，不留持久失败队列或自动重启新一轮。

实际 ACK Chart 当前默认 `wakeTimeoutSeconds: 600`（10 分钟），覆盖 Gateway 二进制的 60 秒缺省；具体安装如有覆盖则沿用有效配置，不把正常下线的 60 秒业务排空误作常态唤醒等待。来源及配置输入说明见 [飞书配置与有限投递](../../evidence/feishu-webhook-config-and-retry.md)。

每次 HTTP 请求与退避均有有限时限，退避基数和单次 HTTP 超时使用实现阶段确定的有限默认值；任务从内存登记起的总上限不得超过唤醒等待预算、六次 HTTP 超时及五次退避之和，排队/重试不重置该上限。若进入正常下线，以该任务上限和首次停收后 60 秒截止中的较早者为准。响应丢失可能造成重复投递，沿用相同事件 ID，由应用承担业务去重；不承诺恰好一次。转交仍需兼容目标接收器的验签时间窗，失败不算成功交付。日志记录事件 ID、目标身份、尝试次数和终止原因，不记录密钥或完整消息正文。

OpenClaw 处理消息后主动调用飞书消息 API 回复用户，Webhook 的 HTTP 接收确认不承载最终回答。用户提出的完整 E2B 数据面 URL 可复用现有 Host 解析与路由定位 Sandbox 和端口，无需再建通用接入到目标的映射系统。域名不包含访问 token 或 Kubernetes UID：现有数据面认证开启时，标准飞书请求不能自动通过。飞书入口仍需在 Sandbox 外取得来源验证配置，并明确异步任务的对象身份与开关变化规则；公网 DNS/HTTPS 可达性需在实际环境验证。详见 [入口核验](../../evidence/feishu-e2b-webhook-entry.md)。

并发请求可以合并同一目标的恢复操作，不同消息需保留各自处理语义；Gateway 对上游重复事件的内存合并边界仍需明确，不替代应用对业务副作用的去重责任。

## 验收方向与待明确事项

基础场景：飞书通过 Webhook 投递合法消息事件，承载 OpenClaw 的 Sandbox 已 Pause；Gateway 内存接收并确认，正确目标随后恢复，事件交给应用。正常下线先停收再排空，刚好与停收并发的接收不得遗漏：事件要么已登记并纳入等待，要么未被接收并返回失败。进程故障或无法在终止预算内完成时仍可能丢失未完成事件，不增加跨进程恢复保证。

正式验收前需明确：

- 触发消息范围、接入配置与目标身份校验、凭据配置责任。
- 复用现有唤醒成功条件与应用可接收请求之间的兼容前提；恢复后暂不可接收按上述投递重试处理。
- 内存上限、满载处理与上游重复事件合并。唤醒等待、最多五次重试及失败放弃已确定；正常下线的业务排空上限仍为 60 秒。
- 超过平台确认窗口、请求取消、重复事件和消息并发时的结果。
- 关闭自动唤醒时新事件和已接收事件的处置，以及目标不存在或已运行时的策略。
- 未授权事件不触发恢复，以及 challenge 等协议请求的处理边界。
- 飞书 IM 事件的具体支持范围，以及目标应用标准 Webhook 接口的兼容前提。

## 关系与交付

保留原 `2-feishu-wake-openclaw` ID，原双接入需求按用户指示收敛为本项；WebSocket 部分由 `3-websocket-wakeup` 承接。两项无相互前置依赖。

目标映射、授权、恢复合并、就绪检测及适用的交付机制可以共享，归属在设计中确定。工作项 1 的 Gateway 能力可作为复用候选，当前不据此认定存在已交付的前置能力。

父项作为汇总项保留整体需求、共享契约及集成验收责任，按用户 2026-11-04 的明确要求拆为两个子任务：
