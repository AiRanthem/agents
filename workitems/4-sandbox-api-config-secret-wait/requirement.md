# sandbox-api 等待配置时避免阻塞发布

## 问题与目标

用户更正了原需求：sandbox-api 当前在等待配置时会出现 Pod `0/2 Ready`，导致一些发布系统卡住。本项需要解决等待配置与发布完成判定之间的阻塞问题。

2026-11-17 用户更正原文：

> 需求表达错误，现在等待的时候会出现 0/2 ready ，导致一些发布系统会卡住

原先记录的“配置 Secret 不存在时立即 crash”已被本次更正取代，不再作为当前问题事实。

## 已知范围与约束

- 范围为 sandbox-api 使用配置 Secret 的启动等待，以及相关 Pod Ready 状态和发布完成判定。
- 当前等待能力已经存在；本项不能仅以新增等待或延长等待时间作为达成目标的依据。
- 用户尚未选择缺少配置时的最终结果：允许发布继续、让 Pod 提前 Ready，或使发布在有限时间内明确失败。具体发布系统、判定规则及是否可调整也未指定。
- 此前用户要求进程不感知 startup probe 超时，不读取或复制其配置来推算期限；本次更正没有明确撤回此约束。最终方案需明确它与发布完成条件的关系，不能自行引入进程内总超时。
- 等待期间是否允许 Ready、是否接收业务流量、滚动更新是否允许替换旧副本，均需作为同一行为合同确认。
- 本次为需求更正与设计探索，尚未批准完整设计或授权源码实现。

## 验收目标与待决边界

1. 配置暂未就绪时，发布系统获得与最终批准合同一致的明确结果，避免因当前等待状态持续卡住。
2. 对缺少配置、配置无效、后续补齐和配置原本有效的情况，明确进程、两个容器、Pod Ready、业务请求和发布状态之间的关系。
3. 明确发布完成是否代表 API 可用，以及更新时对旧可用副本的保留要求；不能把提前 Ready 的影响视为纯探针调整。
4. 配置补齐后沿用正常配置生效与启动流程；实际业务接入条件和允许的启动窗口随最终合同确认。

以上为用户更正后的目标及需要收敛的验收边界，不是已批准的完整设计。当前源码事实和已执行的局部检查见 [context.md](context.md)；没有现场验证结论。
