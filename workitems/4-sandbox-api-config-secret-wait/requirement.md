# sandbox-api 等待配置时避免阻塞发布

## 问题与目标

用户更正了原需求：sandbox-api 当前在等待配置时会出现 Pod `0/2 Ready`，导致一些发布系统卡住。本项需要解决等待配置与发布完成判定之间的阻塞问题。

2026-11-17 用户更正原文：

> 需求表达错误，现在等待的时候会出现 0/2 ready ，导致一些发布系统会卡住

原先记录的“配置 Secret 不存在时立即 crash”已被本次更正取代，不再作为当前问题事实。

## 已知范围与约束

- 范围为 sandbox-api 使用配置 Secret 的启动等待，以及相关 Pod Ready 状态和发布完成判定。
- 当前等待能力已经存在；本项不能仅以新增等待或延长等待时间作为达成目标的依据。
- 用户已选择：Pod 先达到 `2/2 Ready`，配置完成前业务请求返回 `503`。选择时已说明会接入流量，也可能推进滚动替换；本项不据此承诺配置未完成期间业务可用。
- 用户确认启动开关为 `--ready-before-config`，默认 `false`，仅在 `--secret-config` 非空时启用提前 Ready 模式；无 Secret 引用时静态 flag/env 路径保持原有行为。
- 进程不读取或推算 startup probe 超时，不设置配置等待总期限。开启新模式后，startup probe 成功即结束其启动检查，不再限制配置等待时长；配置可以持续未就绪，业务持续返回 `503`。
- 新模式区分 Pod Ready 与业务可用：前者允许先完成，后者在初始配置生效和相关运行时初始化完成前保持关闭。控制 API 与经同 Pod Envoy 的业务入口都需符合 `503` 目标。
- 用户于 2026-11-17 以“确认”批准完整合同及 `spec.md` 落位。设计批准不包含独立评审执行或源码实现授权。

## 验收目标

1. 开启新模式且其他必要启动条件满足时，配置暂未就绪不会继续使 Pod 因该等待保持 `0/2 Ready`；依赖 Ready 的发布系统能够继续，业务请求返回 `503`。
2. 缺少配置、内容无效或首次应用失败时保持业务 `503`；配置生效并完成后续运行时初始化后，同一进程自动开放业务。健康和观测端点可用；控制 API 与 Envoy 业务入口都不能绕过配置门禁。
3. 发布完成与 API 可用分别判断；新模式允许提前 Ready 影响流量与滚动替换。关闭开关时保留既有等待初始配置后才完成启动的行为。
4. 依赖有效配置的后台工作保留其启动前提，致命的参数、证书或监听绑定错误保持失败语义，终止取消不会因晚到配置重新开放业务；正常运行后的热更新保留既有语义。

完整已批准合同及可观察场景见 [spec.md](spec.md)，实际决定来源见 [decision.md](decision.md)。源码证据和既有等待路径的局部检查见 [context.md](context.md)；新模式尚未实现或进行现场验证。
