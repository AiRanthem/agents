# sandbox-api 等待配置时避免阻塞发布

## 问题与目标

用户更正了原需求：sandbox-api 当前在等待配置时会出现 Pod `0/2 Ready`，导致一些发布系统卡住。本项需要解决等待配置与发布完成判定之间的阻塞问题。

2026-11-17 用户更正原文：

> 需求表达错误，现在等待的时候会出现 0/2 ready ，导致一些发布系统会卡住

原先记录的“配置 Secret 不存在时立即 crash”已被本次更正取代，不再作为当前问题事实。

## 已知范围与约束

- 范围为 sandbox-api 使用配置 Secret 的启动等待，以及相关 Pod Ready 状态和发布完成判定。
- 当前等待能力已经存在；本项不能仅以新增等待或延长等待时间作为达成目标的依据。
- 用户已选择：Pod 先达到 `2/2 Ready`，等待配置时控制 API 拒绝业务请求，可以返回任意 HTTP 错误码。用户确认 Envoy 可以接流并按已有 Sandbox 路由转发，滚动替换也可以继续。
- 用户确认启动开关为 `--ready-before-config`，默认 `false`，仅在 `--secret-config` 非空时启用提前 Ready 模式；无 Secret 引用时静态 flag/env 路径保持原有行为。
- 进程不读取或推算 startup probe 超时，不设置配置等待总期限。开启新模式后，startup probe 成功即结束其启动检查，不再限制配置等待时长；配置可以持续未就绪，控制 API 持续拒绝业务请求。
- 新模式区分 Pod Ready 与业务可用：前者允许先完成，控制 API 在初始配置生效和相关运行时初始化完成前保持关闭。经 Envoy 转到控制 API 的请求遵循同一门禁，Sandbox 数据面沿用已有路由规则。
- 用户于 2026-11-17 批准设计 v1，于 2026-11-18 明确 Envoy 数据面和控制 API 等待期错误码的决定，已记入设计 v2。

## 验收目标

1. 开启新模式且其他必要启动条件满足时，配置暂未就绪不会继续使 Pod 因该等待保持 `0/2 Ready`；依赖 Ready 的发布系统能够继续，控制 API 拒绝业务请求。
2. 缺少配置、内容无效或首次应用失败时，业务请求不能进入控制 API 的鉴权、存储或业务处理，允许返回任意 HTTP 错误码。配置生效并完成后续初始化后，同一进程自动开放控制 API。健康和观测端点可用，Envoy 的 Sandbox 数据面按已有路由接流。
3. 发布完成与 API 可用分别判断；新模式允许提前 Ready 影响流量与滚动替换。关闭开关时保留既有等待初始配置后才完成启动的行为。
4. 依赖有效配置的后台工作保留其启动前提，致命的参数、证书或监听绑定错误保持失败语义，终止取消不会因晚到配置重新开放业务；正常运行后的热更新保留既有语义。
