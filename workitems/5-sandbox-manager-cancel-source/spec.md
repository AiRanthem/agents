# 摘要

sandbox-manager 在现有取消日志、对应的 `API Error` 日志以及返回给调用方的 JSON 错误响应中提供结构化字段 `cancelSource`。排障人员和 API 调用方由此可以判断本次操作因何退出。

# 背景

刷新流量令牌时，多个 HTTP 请求可以共用一次签发。请求可以各自结束等待，共享签发则由 Manager 的生命周期控制。签发保留首个请求的日志信息，所以同一个 `requestID` 下可能出现两种来源的取消。在 HTTP 层，业务错误还会转换为面向调用方的消息；到这里才看错误文字或请求当前状态，可能丢失或误判来源。

# 设计终态

| 本次操作的结果 | 日志及对应 API 错误响应中的 `cancelSource` |
| --- | --- |
| 入站 HTTP 请求的取消传播到当前操作，并使它退出 | `http_request` |
| sandbox-manager 主动取消其管理的操作，例如停机终止共享签发 | `internal` |
| 能确认本次操作因取消退出，但无法确定是哪一方触发 | `unknown` |
| 操作正常结束、达到期限（`context.DeadlineExceeded`）或发生其他业务错误 | 省略字段 |

**归因与传播。** 在能观察到退出原因的操作边界确定来源。来自依赖的错误即使被包装，只要仍能确认是 `context.Canceled`，也适用上表。已知来源随同一次失败传到现有的上层错误日志，包括转换成面向调用方的 API 错误之后。请求 ID、错误文案中出现的单词和写日志时某个 context 已经结束，都不足以单独证明因果。对于能取得原始原因的本地路径，应保留该证据，避免因中途转成字符串而在上层退化为 `unknown`。

**并发与边界。** 每个操作按实际导致它退出的事件归因。后到的取消不能覆盖已经确定的来源。两个取消都已就绪时，以操作实际采用的退出分支及其原因判断；若现有证据只能确认取消，则记 `unknown`。`http_request` 表示沿入站请求传播的取消，日志无需推断最终用户、代理或网络中哪一方发起断开。

**可观察场景**

- 客户端在等待共享令牌时断开连接。该请求的等待日志和相应的 API 错误日志记 `http_request`，其他请求仍可等到同一次签发的结果。
- Manager 停机取消共享签发。收到该签发失败的请求，其相应错误日志记 `internal`，即使某个请求在错误写入日志前也断开了。另一个等待者若因自身请求取消退出，其日志仍记 `http_request`。
- 依赖只返回可识别的 `context.Canceled`，没有提供来源，日志显式记 `unknown`。排障人员可以把这一类与没有发生取消的日志分开检索。
- Pause/Resume 等待返回冲突，随后请求也结束。日志描述实际冲突，省略字段；只有请求取消确实导致等待退出时才记 `http_request`。Claim 自身超时也省略字段，即使旧文案中含有 “context canceled”。

**API 错误响应。** 对于由取消导致的失败，JSON 顶层增加可选字符串字段 `cancelSource`。即使 API 将底层错误映射为通用消息，仍使用本次失败已经确定的来源。中间件提前返回错误时也适用。成功、普通超时及业务错误省略该字段。HTTP 状态码、既有响应字段和消息沿用原有约定。只传递表中的来源值，后端原始原因继续遵守原有脱敏规则。客户端已断开连接时，服务端生成的响应可能无法送达。

现有日志继续使用原有级别，静默处理正常取消的路径维持静默。取消传播、超时、重试和后台工作的生命周期继续按原有规则运行。
