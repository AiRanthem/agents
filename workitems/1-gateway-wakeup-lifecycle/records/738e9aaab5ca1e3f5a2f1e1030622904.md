## 非阻塞发现（Low）

### L1 · Gateway 续期写入与唤醒共用同一客户端限流，契约只写了按 UID 合并

- 位置：spec「并发、身份与失败」中“同一 Gateway 对同一 Sandbox UID 合并并发触发，工作量和等待队列有界”；「与自动唤醒的关系」中“未开启续期的 Sandbox 继续使用已有唤醒行为”。
- 事实：`pkg/sandbox-gateway/controller/gateway_controller.go:132` 用 `ctrl.GetConfigOrDie()` 构造 manager。controller-runtime v0.20.2 的 `pkg/client/config/config.go:101-105` 在未显式设置时使用 20 QPS / 30 burst。现有唤醒会经 `sandboxcr.Sandbox.Resume`（`pkg/sandbox-manager/infra/sandboxcr/sandbox.go:594-634`）执行 APIReader Get 与 patch，二者共用这一客户端令牌桶。
- 场景：契约允许 R=`2s`、H 接近 R（如 H=`1.5s`）。在持续流量下，每次成功写入会把 E 推后至少 1 秒，所以每个 Sandbox 约每秒写一次。同一 Gateway 上只要有几十个这类 Sandbox，就可能用满该 Gateway 的令牌桶，使其他租户的流量唤醒排队，延迟变长甚至触及 `wake-timeout-seconds`。默认配置（timeout=300s、H=10%）大约每 270 秒才写一次，影响可以忽略。
- 归因：这是新增的写入来源，属于本变更。不判为阻塞的原因有两点：契约已经要求“工作量和等待队列有界”、续期为尽力而为、不影响既有唤醒行为；独立限流或独立客户端、全局并发上限、超额时丢弃续期、唤醒优先等合规的内部实现都可选，不需要修改用户契约。
- 实现交接：除按 UID 合并外，还应为续期设置 Gateway 级的全局并发或速率上限，并保证唤醒请求不排在续期写入之后。实现审查应专门核对这一点。

### L2 · 两者都开启时，R 取代唤醒规则 `PauseTimeout`，应在提案与实现中明示

- 位置：spec「与自动唤醒的关系」中“共用 connect 核心能力以保存的 R 发起恢复……本次恢复时长取为 `max(R, 300 秒)`”。
- 事实：`Spec.AutoPausePolicy.Resume.OnIngressTraffic.PauseTimeout` 是已发布的 CRD 字段。`docs/proposals/20260627-wake-on-traffic-via-spec-patch.md:68-79` 将它定义为流量唤醒时重新设置的暂停时长，也支持经 `kubectl patch` 设置。现有 `wake.go:152-171` 取 `max(PauseTimeout, 300s)`，未设置时清除 PauseTime 并保持运行。
- 判断：spec 已唯一规定开启续期后恢复时长按 R 计算，所以这不是缺失的决定，也不需要修改候选文档。但这确实改变了一个公开 CRD 字段在两项功能同时开启时的有效语义。E2B create 默认 R 等于 timeout，等于 `PauseTimeout`，所以多数情况下二者一致；用户显式设置不同的 R，或 out-of-band 修改 `PauseTimeout` 时会产生差异。
- 实现交接：在实现所需的提案和代码注释中写明这一优先级，并在测试里覆盖 R 与 `PauseTimeout` 不同的情况。

### L3 · 仓库规则要求的 `docs/proposals/` 提案未在设计交付物中出现

- 事实：仓库根 `AGENTS.md`（Generated Files And Design Changes）要求“New APIs and architectural changes require a proposal in `docs/proposals/`”。本设计新增公开扩展参数和系统 annotation，还新增 Gateway 写入生命周期期限、由 connect 与 Gateway 共享中立生命周期核心的架构；前序的唤醒功能也有独立提案。requirement 的交付结果写的是“待确认具体代码交付和文档要求”。
- 判断：仓库规则已经确定提案义务，内容可直接来自 v3 契约，不涉及待用户决定的设计选择，因此不阻塞。实现交付时应包含该提案，并按 L2 写明与唤醒规则的关系。

## 既有基线警告（不影响结论）

- `pkg/controller/sandbox/sandbox_controller.go:1183-1206` 到达 `ShutdownTime` 时直接 `Delete`，没有 resourceVersion 前置条件，判断依据是控制器缓存视图；到达 `PauseTime` 的暂停（`:1150-1176`）使用乐观锁 patch。因此在自动销毁模式下，紧贴到期时成功写入的续期仍可能被持有旧视图的控制器删除。现有 connect 已有同样的竞争，本变更未使它恶化，spec「兼容性与能力边界」已声明接近到期时可能来不及续期。

## 覆盖范围与关键证据

1. **需求对齐**：原始诉求是唤醒后未调整期限。context 记录了基线核实结果（唤醒经 Resume 重新设置自动暂停期限，运行中没有流量续期），也记录了用户逐项确认的协议、原子性、400/409 和共享核心约定。v3 在此基础上提供按需开启的运行中续期，并与唤醒结合。未开启续期的唤醒行为保持不变，符合已批准的范围。
2. **create 前置校验**：`pkg/servers/e2b/create.go:315-396` 中，`ParseExtensions` 消费并移除扩展键，然后做 metadata 黑名单检查（`E2BPrefix`、`InternalPrefix`），再填充 timeout 默认值并校验 30 秒下限与上限，全部在 `HasTemplate`/Claim/Clone 之前完成。spec 要求的顺序（先确定 timeout，再换算百分比和默认 R）可以实现。系统键 `agents.kruise.io/traffic-renewal-*` 受黑名单保护，也不会回显（`sandbox.go:143-157` 用 `ValidateMetadataKey` 过滤）。
3. **Claim/Clone 残留**：Clone 时 `RestoreAnnotationsFromCheckpoint`（`checkpoint_utils.go:28-88`）只恢复白名单 annotation，且在 Modifier 之后执行（`clone.go:396-417`），续期键不会被带回。Claim 的 Modifier（`claim.go:1044-1047`）可以清除候选残留。“只采用本次请求的选择”可以实现。
4. **connect/timeout 原子更新**：现有 `updateConnectTimeout`/`setSandboxTimeout` 在无需改期时直接跳过（`pause_resume.go:422-453`、`timeout.go:49-91`），timeout 外层把非 404 一律改成 500（`timeout.go:35-46`）。spec 已明确要求在同一受版本保护的写入中提交配置和期限，并保留新增 400/409。可用的现有机制包括 `retryUpdate`/`retryPatch` 的 Modifier 及乐观锁（`sandboxcr/sandbox.go:159-296`）。“不能仅凭旧缓存宣告满足”可以用带 resourceVersion 的条件写确认，不需要新增 APIReader。并发组合示例（H=8m / R=5m）能区分正确的重新合并与按字段覆盖。
5. **协议兼容**：核对上游 E2B OpenAPI：`/sandboxes/{id}/timeout` 只列出 204/401/404/429/500；v1/v2 connect 列出 400/409。timeout 返回 400/409 偏离上游，但这是用户确认的取舍，且只在显式携带新扩展 header 时出现；不带扩展的旧请求保持现有映射。
6. **暂停恢复**：`Resume`（`sandboxcr/sandbox.go:594-686`）已有“首写获胜”的 patch 与等待分离，可以扩展为在同一 patch 中提交配置、保护期限和 `paused=false`。spec 覆盖了败者路径、只延长、补充延期的失效条件，以及等待失败不回滚。
7. **Gateway 流量与身份**：`filter.go:89-192` 先定位路由并鉴权，再判断是否 Running；`:302-345` 是唤醒准入。续期绑定准入时的 UID 与公开 ID，普通续期不允许写 `paused=false`。WebSocket upgrade 沿用包含 Go filter 的默认过滤链（`config/sandbox-gateway/configmap.yaml:87-111`），所以双向数据事件可以观测。
8. **写入安全**：Gateway 的 ClusterRole 已有 sandboxes `update/patch`（`config/sandbox-gateway/rbac.yaml:9-11`）。Gateway 缓存会裁剪 `EmbeddedSandboxTemplate`（`cache_transform.go:21-30`），spec 要求不得擦除被裁剪字段，现有 `retryPatch` 带乐观锁的 merge patch 正是这种用法。现有 `retryPatch` 冲突后会改用 APIReader 重读，spec 已要求新增续期只用缓存加条件写，与仓库的 Kubernetes Read Discipline 一致。
9. **期限数学**：现有向下截断（`timeout.go:73-78`）和严格延长（`:59-66`）配合 R ≥ 2s、H ≥ 2ns、`0<H<R`：对整秒 E，在 `0<E-t<min(H,1s)` 内取 `t=E-d`，有 `floor(t+R)=E+R-1s>E`。验收表的 9 个具体数值场景我逐项手算核对，结果一致。
10. **分层**：spec 要求共享核心放在中立边界，不依赖 E2B/HTTP，也不扩大 Gateway 对 API/Manager 的遗留依赖，控制器不产生反向依赖，与根目录及 `pkg/sandbox-gateway`、`pkg/sandbox-manager/infra` 的 `AGENTS.md` 一致。具体包位置属于实现选择，必须遵守“共享包保持策略中立”的规则。
