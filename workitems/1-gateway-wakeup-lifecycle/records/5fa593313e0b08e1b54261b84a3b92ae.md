## v4 → v5 差异

## 非阻塞发现（Low）

### N1 · 超额放弃未规定在 Sandbox 之间如何分配额度

- 位置：spec「并发、身份与失败」中“超出上限时本次续期按尽力而为处理……被直接放弃的续期可由后续合格流量重新触发”。
- 场景：某租户在同一 Gateway 上有大量 R=`2s`、H 接近 R 的 Sandbox，并持续有流量。它们每秒各请求约一次写入，长期占满实例级上限。另一租户的 Sandbox 配置正常（例如 H=`1m`、R=`10m`），但流量稀疏，在剩余 60 秒的窗口内只有一两次合格流量。如果每次续期尝试都恰好遇到额度已满而被放弃，这个 Sandbox 有流量也会按期暂停或销毁。
- 归因与严重度：这是 v5 新增“超额放弃”带来的结果；v5 之前额度不足时会排队等待，而不是放弃。spec 已声明续期是尽力而为、不保证每次合格流量都能阻止到期；影响仅限于续期，唤醒已被新条文隔离；按剩余时间优先或按 UID 公平准入等实现都满足当前契约。因此判为 Low，不需要修改 spec。
- 实现交接：实现宜让临近到期的续期优先获得额度，或按 Sandbox UID 公平分配，避免小 R 配置长期独占；实现审查可核对。

## 交互与可行性核对

1. **限流隔离可以实现**：client-go v0.35.0（`go.mod` 的 replace 目标）在 `rest.Config.RateLimiter` 为空时，为每个 RESTClient 新建 QPS/Burst 令牌桶（`k8s.io/client-go@v0.35.0/rest/config.go:371-381`）。controller-runtime v0.20.2 按 GVK 构造 RESTClient（`pkg/client/client_rest_resources.go:59-65`），所以 Gateway manager 客户端对 Sandbox 的写入目前共用一个桶（`gateway_controller.go:132` 未自定义 QPS/Burst/RateLimiter）。为续期使用独立的 rest 配置或客户端就能得到独立的令牌桶，唤醒路径不受影响；也可以选择共用并证明不会挤占。新条文因此可以实现，具体方式留给实现。
2. **与既有约束一致**：独立写客户端不属于 APIReader 直读，续期仍按缓存视图加条件写，不违反“不新增 APIReader 直读依赖”。实例级上限是本地机制，不引入跨 Gateway 分布式锁，也不新增 Prometheus 指标。`pkg/sandbox-gateway/AGENTS.md` 要求新行为使用本地或中立契约、不扩大对 API/Manager 包的依赖，Gateway 本地限流与此一致。
3. **与异步与失败语义一致**：因额度被放弃不同于写入失败，不形成后台重试，由后续合格流量重新触发，与“无新流量时不形成无限后台重试”一致；数据转发不受影响，与“不阻塞数据转发”一致。
4. **作用范围**：上限只约束“运行中续期写入”，不约束流量唤醒（包括开启续期后的唤醒）。唤醒的实际耗时仍取决于 Sandbox 恢复，新条文只要求唤醒不因续期写入而延迟，不承诺唤醒一定在超时内完成；验收行的写法（“在 `wake-timeout-seconds` 内完成或按既有唤醒失败语义返回”）与此一致。“不排在续期写入之后”按 Gateway 内部排队理解；API Server 端的公平调度不属于 Gateway 能控制的范围，而实例级上限本身限制了续期对服务端的负载。
5. **`wake-timeout-seconds`**：已有 filter 配置项（`pkg/sandbox-gateway/filter/config.go:84-100,159-165`，默认 60 秒），不是新参数。
6. **验收可判定**：三行新增验收能区分“无上限排队拖慢唤醒”和“有上限、唤醒优先、续期尽力而为”两类实现，可用受控的限流与假客户端验证，不依赖精确的 Sandbox 数量。
7. **与 v4 契约的其余部分**：未改动的段落及上一轮的覆盖（协议、持久化、原子提交、期限数学、暂停恢复、身份与分层）不受影响；原验收行“无竞争且提交及时成功时”的限定与新增上限相容。
