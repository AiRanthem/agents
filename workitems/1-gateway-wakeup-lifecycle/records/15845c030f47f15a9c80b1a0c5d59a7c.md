# 需求 1 设计独立审查

结论：**Design changes required（需要修订设计）**。发现 1 项 Medium 阻塞问题；其余已审查边界未发现新的阻塞问题。

## 阻塞发现

### D1 · Medium：合法的 1 秒目标在整秒截断规则下永远不能续期

- 设计位置：`spec.md:34` 允许任意正整秒 R 和亚秒 H，`:40` 仅要求 `0 < H < R`；`:78` 要求尚未到期才触发；`:92` 使用现有整秒规范化的 `t + R`，`:96` 要求只延长。
- 具体场景：通过 create 或配置 header 设置 `R=1s、H=500ms`，当前有效截止时间 E 为 `12:00:10Z`。在 `12:00:09.600Z` 收到合格流量，剩余 400ms，满足阈值条件；但目标 `12:00:10.600Z` 向下截断后仍为 `12:00:10Z`，因此写入不能延长期限。
- 这不只是一次取整丢失：对任意整秒 E 和 `0 < E-t < H < 1s`，`floor(t+1s)=E`。窗口内所有后续流量都只能得到原期限；到达 E 之后又被“已经到期不抢救”规则排除。固定目标重试、增加触发频率和消除后端延迟均不能解决。
- 代码证据：`pkg/utils/timeout/timeout.go:73-77` 的 `NormalizeTime` 使用 `Truncate(time.Second)`；`:59-65` 的 `ShouldExtendTimeout` 只接受严格晚于原期限的目标。`pkg/sandbox-manager/infra/sandboxcr/sandbox.go:357-366` 在持久化两个截止时间时也执行该规范化；`:466-496` 的现有期限更新路径按该只延长规则判断。
- 归因：整秒存储本身是既有行为；本次新增协议接受 1 秒自动续期目标，并将其与“仅在未到期阈值窗口续期”组合，才产生这类必然无效的有效配置。`spec.md:114` 的有界重试要求只能控制负载，`:126` 的尽力续期限制覆盖时延、故障和竞争，不能解释健康环境中数学上完全没有可延长期限的机会。
- 所需结果：明确最小目标值与时间取整规则，使每个被接受为开启的配置存在实际延长的可能，并补充最小 R、亚秒 H、整秒 E 的验收反例。可由设计所有者选择排除无法生效的目标值，或明确支持 1 秒目标的期限规范化语义；两者会分别改变输入范围或期限行为，不属于评审者可以直接作出的机械修正。
- 证据性质：完整源码静态推导，并用共享 Python 环境运行整数纳秒计算验证 499999999、400000000、250000000 和 1ns 四个剩余时间，全部满足触发条件且目标等于旧期限。一般性等式如上。未把此计算宣称为 Gateway 功能测试或真实集群复现。

## 已覆盖的关键路径

1. **create 和公开输入边界。** `pkg/servers/e2b/routes.go:49-64` 将 v1/v2 create 复用到同一 handler；`create.go:82-116,310-396` 展示解析、默认 timeout、范围校验均可先于 Claim/Clone。`create.go:139-148,240-247,399-445` 的交付 modifier 提供写入本次策略并清理继承值的位置。现有 metadata 黑名单保护内部键；新扩展需要在 API 层消费。设计明确了字段单值、溢出、百分比计算、零值删除、候选残留清理和 never-timeout 边界，没有要求从旧期限猜测目标。
2. **原子配置更新和并发。** `pause_resume.go:287-345,422-455`、`timeout.go:35-89` 与 `sandboxcr/sandbox.go:159-218,225-295,466-496` 表明旧代码不能直接原样复用：无需延长时会跳过 annotations，timeout 外层会改写错误码，旧重试也会使用 APIReader。设计已经明确要求改造这些行为，并将条件写、身份校验、按字段重合并和错误映射分配到恰当边界；这些是已要求实现的工作，不另列为设计遗漏。合并后的 H/R 冲突示例能区分正确条件写与字段各自更新的错误实现。
3. **暂停、恢复和保留期限。** `pause_resume.go:231-267,318-345`、`sandboxcr/sandbox.go:594-684` 和 `sandbox-manager/api.go:376-424` 支持首次提交与后续等待的分离。设计覆盖首次配置/期限/paused 原子提交、同向竞争、恢复后补充延期失效、取消不回滚、只延长、never-timeout 和独立暂停保留策略。`controller/sandbox/sandbox_controller.go:1124-1206` 核实控制器继续执行到期动作；设计不声称撤销已经发生的到期或主动暂停。
4. **Gateway 流量和身份。** `filter/filter.go:89-192` 先定位路由再鉴权，`:302-345` 的唤醒门槛与 Running 准入分离；`:350-507` 有异步完成和流销毁取消机制。设计明确把续期绑定原准入身份、重查 UID/公开 ID，禁止普通续期唤醒。`controller/cache_transform.go:21-30` 保留 annotations、状态、期限和 resourceVersion，仅裁剪模板等字段；按条件 patch 可避免擦除裁剪字段。
5. **双向流与资源上界。** 当前 Envoy v1.37.3 Go API 的 `StreamFilter` 提供 `DecodeData/EncodeData`，BufferInstance 可直接检查长度。`config/sandbox-gateway/configmap.yaml:87-111` 的 WebSocket upgrade 沿用包含 Go filter 的默认链；[Envoy 1.37 HTTP upgrades 文档](https://www.envoyproxy.io/docs/envoy/v1.37.0/intro/arch_overview/http/upgrades)确认升级请求和双向 payload 经该链。由此可支持设计所需字节事件，未作真实 SSE/WebSocket 运行验证。有界异步工作应独立于当前 wake 的流级 cancel；现有进程停止钩子可作为实现入口，设计已要求停止取消、队列有界、退避、无流量不无限重试和不持有流回调。
6. **协议与分层。** 对照了当前 [E2B OpenAPI](https://github.com/e2b-dev/E2B/blob/main/spec/openapi.yml) 的 connect/timeout：connect 只延长、v2 缺省 300 秒，timeout 覆盖 TTL。设计保留这些行为，把新扩展 400/409 限定在已确认的新协议。共同核心需遵循中立依赖边界、Manager/Infra 职责以及新增续期不扩大 APIReader 依赖；现存跨层依赖不是允许扩张的依据。
