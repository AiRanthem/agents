# 修复独立 SandboxSet 创建后 E2B create 的缓存同步竞态

## 目标与问题

用户通过 Kubernetes 手动成功创建 SandboxSet 后，立即调用 E2B create，可能因 sandbox-manager 的 informer 尚未观察到该对象而收到 template not found。需要容忍短时间的缓存传播延迟，减少这一误报。

本项仅覆盖使用 `spec.template` 内嵌 Pod 模板的独立 SandboxSet。目标是让窗口内变得可见的 SandboxSet 被正常查到，随后继续现有创建流程；不承诺 Sandbox 一定能在该窗口内就绪。

## 已确认范围

- 将等待集中在 `cache.PickSandboxSet`，保留现有上层接口、创建流程和错误映射。
- 每次查询首次缓存未命中后，最多等待 5 秒，且只读取 informer；禁止显式或经 helper 隐式使用 `APIReader`。
- 缓存命中立即返回；对象在窗口内可见后立即返回；调用取消或更早超时应终止等待；非未命中读取错误立即返回。
- 保留现有 namespace、label selector、管理员跨 namespace 的匹配规则及资源只读约束。
- 共用该方法的调用方统一获得这一等待行为，接受其未命中时增加最多 5 秒的延迟。
- 5 秒是每次 cache 查询的等待上限，不是跨层共享预算或整个 create 的完成上限。

`spec.templateRef` 的引用解析、专项等待及验收不在本项范围内。共享方法对现有调用方生效，不代表新增 Ref 一致性保证。

## 可观察验收

1. SandboxSet 已在当前可见范围的缓存中时，查询立即返回，创建不增加固定等待。
2. Kubernetes 已成功创建内嵌模板的 SandboxSet，而初始缓存未命中；对象在 5 秒窗口内可见且未发生并发删除等变化时，同次查询能观察到对象并继续现有创建流程，不因首次未命中立即返回 template not found。
3. SandboxSet 在窗口结束时仍不可见，查询以现有未命中失败语义结束；不无限等待，不保证对象在 API Server 中确实不存在。
4. 请求在窗口结束前取消或更早到期，cache 等待随之结束；实际读取错误不被当作未命中持续轮询。
5. 多个并发调用独立计时与取消，一个调用退出不会提前终止其他仍有效调用的等待，也不会继承其他调用的剩余窗口。
6. 等待期间保持原有匹配和可见范围，不通过默认 namespace、跨租户搜索或实时 API 回源改变结果来源。
7. 共用方法的 GET、claim 和模板删除等调用保持现有返回模型及状态映射；SandboxSet 未可见时的查询允许增加最多 5 秒等待。同名 checkpoint 仍在 SandboxSet 判定未命中后按既有流程处理。
