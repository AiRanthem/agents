# 当前决策

- 用户要求同时支持 Webhook 和 WebSocket 两种 IM 唤醒方式。
- 用户要求将能力做成通用能力，飞书和 OpenClaw 作为具体场景。
- 2026-11-03，用户要求保存原理分析后，拆成 Webhook 唤醒与 WebSocket 唤醒两个并列需求。本项承接原工作项 2 的 WebSocket 范围，工作项 2 保留其 ID 并收敛为 Webhook 范围。
- 2026-11-09，用户在当前设计会话明确推进决策：“休眠期间，必须有一个仍在运行、位于暂停边界外的组件承担消息感知责任，并把消息关联到目标 Sandbox。”同一回复要求“一个统一的解决方案应对所有 IM”。这确认接收责任边界与统一覆盖目标。
- 2026-11-09，针对“外部接收组件 + 各 IM 适配器 + 统一唤醒核心”，外部组件持续维护连接、应用通过内部接口接收事件的兼容选择，用户回答“允许调整应用接入方式（推荐）”。按该方向继续设计，无需保持沙箱内原接收 SDK 和连接方式完全不变。
- 2026-11-09，针对外部接收组件“内存暂存并按平台协议确认，再唤醒和交付；恢复后首次交付失败，最多再重试 5 次，仍失败则记日志放弃；接收进程退出时已确认但未交付的内存消息可能丢失”，用户回答“接受内存暂存和上述失败边界（推荐）”。这是本项独立取得的可靠性选择，跨进程持久恢复不在已选承诺内。
- 2026-11-09，对首期采用“每个平台账号/接入绑定一个已有 Sandbox”或“同账号按用户/群聊分流”的问题，用户要求解释决策影响，尚未选定映射模式。
- 以上批准仅覆盖已述需求、接收边界、接入调整方向及内存接收/有限交付重试的失败边界；具体内部接口、多实例消费所有权与目标映射细则仍待收敛，不代表完整设计批准、独立审查或代码交付。Webhook 工作项的其他配置和兼容选择不自动适用于本项。
