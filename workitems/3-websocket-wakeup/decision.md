# 当前决策

- 用户要求同时支持 Webhook 和 WebSocket 两种 IM 唤醒方式。
- 用户要求将能力做成通用能力，飞书和 OpenClaw 作为具体场景。
- 2026-11-03，用户要求保存原理分析后，拆成 Webhook 唤醒与 WebSocket 唤醒两个并列需求。本项承接原工作项 2 的 WebSocket 范围，工作项 2 保留其 ID 并收敛为 Webhook 范围。
- 2026-11-09，用户在当前设计会话明确推进决策：“休眠期间，必须有一个仍在运行、位于暂停边界外的组件承担消息感知责任，并把消息关联到目标 Sandbox。”同一回复要求“一个统一的解决方案应对所有 IM”。这确认接收责任边界与统一覆盖目标。
- 2026-11-09，针对“外部接收组件 + 各 IM 适配器 + 统一唤醒核心”，外部组件持续维护连接、应用通过内部接口接收事件的兼容选择，用户回答“允许调整应用接入方式（推荐）”。按该方向继续设计，无需保持沙箱内原接收 SDK 和连接方式完全不变。
- 2026-11-09，针对外部接收组件“内存暂存并按平台协议确认，再唤醒和交付；恢复后首次交付失败，最多再重试 5 次，仍失败则记日志放弃；接收进程退出时已确认但未交付的内存消息可能丢失”，用户回答“接受内存暂存和上述失败边界（推荐）”。这是本项独立取得的可靠性选择，跨进程持久恢复不在已选承诺内。
- 2026-11-09，对首期采用“每个平台账号/接入绑定一个已有 Sandbox”或“同账号按用户/群聊分流”的问题，用户要求解释决策影响，尚未选定映射模式。
- 2026-11-10，在说明两种模式及其与 OpenClaw 部署关系的区别后，用户回答“就一对一绑定”。据此确定每个平台账号/接入绑定一个已有 Sandbox，不按同账号的用户或群聊分流到不同 Sandbox；一个 Sandbox 可绑定多个 IM 账号/接入。
- 2026-11-10，针对绑定开启自动唤醒后手动 Pause 是否仍可被合法消息恢复，用户回答“允许手动 Pause 后唤醒”。本项不以手动 Pause 作为禁止消息唤醒的理由；关闭自动唤醒时不因新消息恢复已暂停目标。
- 2026-11-10，在说明额外白名单与应用内访问判断的区别后，用户决定“不要做唤醒前过滤了吧，依赖 IM 平台自己的权限控制就行了”。据此不增加外部发送者/群聊唤醒白名单，不复制应用业务访问规则；平台来源认证、账号绑定和目标 Sandbox 唤醒授权仍在恢复前校验。应用保留原有业务访问逻辑，因此通过基础校验的消息可能先触发恢复，随后被应用忽略或拒绝。
- 2026-11-10，用户选择“统一框架＋飞书先交付，其他平台后续扩展（推荐）”。首期交付公共接收/唤醒/交付框架及飞书适配，不将已调研的 15 个平台全部纳入首期验收。
- 2026-11-10，对比运维维护外部接入配置与应用启动后自行注册的操作流程后，用户选择“运维配置吧”。据此由运维在沙箱外维护账号、凭据引用、固定目标与应用事件入口，应用不承担自行注册或持续续租；绑定与凭据保存在外部可恢复配置中，消息仍按既定内存暂存与失败边界处理。
- 2026-11-13，针对停用后的消息处理，用户要求“怎么简单怎么来。选择最简单的方式”。按该授权，主代理选择停收新消息、已接收消息沿原目标继续有限处理，沿用已确定的处理与重试流程，不增加队列清空或专门取消机制。旧消息仍可能在停用后恢复原 Sandbox，原目标身份与有效唤醒授权校验仍保留；进程退出仍允许丢失内存消息。换绑先结束旧绑定再新建，旧消息不迁移到新目标。
- 以上批准与授权选择覆盖已述需求、接收边界、接入调整方向、内存接收/有限交付重试的失败边界、账号/接入到 Sandbox 的一对一绑定、手动 Pause 后允许唤醒、不增加外部发送者/群聊过滤、首期统一框架和飞书适配、运维维护外部接入配置，以及停用时保留旧消息的有限处理；具体内部接口、多实例消费所有权、配置结构与凭据更新仍待收敛，不代表完整设计批准、独立审查或代码交付。Webhook 工作项的其他配置和兼容选择不自动适用于本项。
