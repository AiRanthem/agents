# 基于 WebSocket 事件的 Sandbox 自动唤醒

## 目标

已有 Sandbox 处于 Pause 时，通过 WebSocket 接入的合法 IM 消息事件能够自动恢复目标 Sandbox，使其中的应用重新具备消息处理能力。

能力面向通用 IM 平台与应用，用户要求以统一解决方案应对所有 IM；飞书长连接订阅与 Sandbox 内 OpenClaw 是首个场景。需要覆盖应用内旧连接已失效的休眠状态，不能仅以 Pause 后短时间内连接尚存作为成功依据。具体平台接入条件、适配与验收范围由设计明确，既有 15 平台调查不代表全部平台已经适配。

## 已确定范围

- 覆盖已经存在、处于 Pause 的 Sandbox，休眠原因尚未限定。
- 休眠期间，必须有一个仍在运行、位于暂停边界外的组件承担消息感知责任，并把消息关联到目标 Sandbox；该责任不能依赖沙箱内旧连接继续存活。
- 采用外部接收组件、各 IM 适配器与统一唤醒核心的方向，允许调整应用接入方式，由应用通过内部接口接收事件。上游长连接由外部组件持续维护。
- 将合法业务事件关联到正确目标，在授权边界内触发恢复，并定义应用就绪后的事件处理行为。
- 平台连接及事件协议由适配层承担，通用能力不能限定为飞书或 OpenClaw 专用逻辑。
- 与 `2-feishu-wake-openclaw` 为同级独立需求，可分别交付和验收。

本项以 IM 消息事件为当前场景；同步交互回调和其他长连接协议的支持范围需另行明确。

## 机制约束

Sandbox 内被暂停的客户端不能执行 handler、心跳或重连；TCP 缓冲、连接状态与业务 ACK 不能代替可靠接收。平台有限重试不构成无限离线保留承诺。

必须区分业务事件与心跳等控制消息，普通心跳及重连活动不应作为业务唤醒信号。飞书同一应用的多个客户端会竞争接收事件，不能依赖额外连接旁路监听全部消息。

消息在外部接收组件的内存中暂存，并按平台协议及时确认，再唤醒和交付。用户接受接收进程退出时，已确认但尚未交付的内存消息可能丢失。恢复后首次交付失败，最多再重试 5 次；仍失败则记日志放弃。平台接收确认、Sandbox 恢复、应用接收和业务执行完成仍是不同结果；内部应用接收确认、缓存容量/期限和恢复失败边界需在设计中明确。

## 验收方向与待明确事项

基础场景：承载 OpenClaw 的 Sandbox 已 Pause，应用内旧连接已失效，用户发送飞书 IM 消息，仍可通过工作中的消息接收机制触发正确目标恢复，并达到约定的应用可用状态。

正式验收前需明确：

- 触发消息范围、应用/租户/会话到目标的映射、应用凭据的配置与保管责任。每账号/接入绑定一个 Sandbox，或同一账号按用户/群聊分流到不同 Sandbox，用户要求先了解影响，尚未选择。
- 平台适配器与应用内部接收接口的责任、事件身份和载荷，以及需要依赖原接收会话的回复如何完成。
- 接收方与原应用的连接、消费所有权及多实例协调，避免非预期竞争消费。
- 唤醒成功与应用就绪判定、时延要求及恢复失败行为。
- 首条及休眠期间后续消息的内存容量/期限、超限行为、协议确认与内部应用接收确认边界，以及恢复失败和有限交付重试的具体行为。
- 接收方断线/重启、重连、分片不完整、重复事件和消息并发时的结果。
- 心跳不唤醒、未授权事件不唤醒，以及手动 Pause/禁用自动唤醒策略。
- 通用扩展接口，以及首期平台、事件、SDK 版本和应用支持范围。

## 关系与交付

本项从原 `2-feishu-wake-openclaw` 的双接入范围中拆出，与收敛后的 Webhook 唤醒需求并列；`split_from` 记录来源，不表示父子层级或前置依赖。

目标映射、授权、恢复合并、就绪检测及适用的交付机制可共享，共同实现归属在设计中确定。若通过内部 HTTP 接口交付应用，该接口不自动形成对“公网 Webhook 入口唤醒”功能的依赖。

实现仓库、代码分支和发布方式待确定。承接原范围的“代码合并”交付义务；项目记录提交不代表代码交付。当前处于设计探索，已确认接收责任边界、统一方案目标和允许调整应用接入，尚无完整正式设计或业务实现。
