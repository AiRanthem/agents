# Checkpoint 重试与自动休眠 · 设计稿 v3

## 用户遇到了什么

Sandbox 刚唤醒时，用户要求保存当时的文件系统。管理服务成功创建了 Checkpoint 对象，底层服务两次回复实例状态暂不允许创建快照。下一次处理请求前，自动休眠已经删除了源 Pod。用户最后只看到 `Pod Not Found`，无法从返回结果知道快照曾经针对一个真实运行的 Pod 发起过。同期旧控制器还在反复处理已经结束的 Checkpoint。现场时序和版本证据见[排查记录](context.md)。

## 已有快照的处理

建议把 Succeeded 和 Failed 作为该次创建的最终结果。源 Pod 消失、重建或控制器重启后，再处理这些对象时，保留原结果、原因、完成时间、后端 ID 和恢复数据。common control 没有收尾动作时直接结束本轮。只有实际的生命周期任务才需要后续调谐，例如 ACS 控制模式下从原完成时间计算的 TTL 到期，以及已请求删除对象的 finalizer 清理。该约定同时覆盖旧标签形式的 pod-info 和包含 filesystem 的快照。

这样处理有实际的兼容性要求。快照列表只展示 Succeeded，休眠及升级流程也判断 phase，恢复和克隆仍可能读取快照 ID、Pod 模板差异和关联的 SandboxTemplate。直接用 `agent-sandbox-controller-v0.6.7-release.4` 替换旧版会停止这类错误重试，但其 common control 会将已成功的非 pod-info-only 对象改成 Failed。因此建议选择包含终态保留行为的修订镜像。现有候选镜像能否作为临时缓解，取决于存量对象会选中哪种控制模式；评估还需计入升级后源 Pod 才消失的对象。

停止重试无需先清空旧对象。对完成时间或模式不明、有后端 ID、有关联模板或仍用于恢复的对象，默认保留。按既有 TTL、所有者和显式删除语义回收；不能仅凭 phase、对象年龄或 Pod 缺失推定数据可丢弃。是否人工清理须有资源归属和引用证据。已经被旧版本改写的历史结果只能凭额外证据恢复。

## ACS 拒绝创建时如何重试

Checkpoint 处于 Pending、尚未取得后端 ID 时，只要 **ACS CreateCheckpoint 返回可核实的 HTTP 403**，即进入同一套有限重试。SDK 错误中的 HTTP 状态也可以作为依据。业务错误码和文案均为可选诊断信息。即使两者缺失，已确认的 403 仍适用。其他操作返回的 403、Kubernetes RBAC 拒绝、仅在错误文本中出现的“403”、网络超时和其他 HTTP 状态均沿用各自已有的处理。这个选择也会让持续的权限拒绝多尝试几次。

采用首次 403 后 **30 秒的窗口，每次 403 后计划等待 5 秒**。到期时停止发起新的创建调用。即使持续立即返回 403，首次调用后也最多再试 5 次。排队或共享限流可使实际执行更晚，错过的次数不补发。30 秒给默认等候 60 秒的 manager 留出快照实际创建的时间。重复事件、状态更新和重启沿用已记录的原窗口与下次允许尝试时间。所有对象共享控制器的重试速率约束。

重试使用同一 Checkpoint UID 作为幂等 token，并绑定最初的 Pod UID、实例及创建参数。在窗口内，原 Pod 仍可用且后端返回 ID，就进入 Creating 并按该 ID 跟踪。原 Pod 开始删除、已消失或已被同名新 Pod 替换，就停止对源 Pod 的新建尝试。Checkpoint 进入删除流程时优先清理。后端明确拒绝后一直未接受，窗口到期即在下次调谐写 Failed 和完成时间。若响应丢失、成功返回 ID 后写状态失败，或结果因其他原因无法确认，须按原创建身份接续，只报告已知事实。不得因窗口到期断言远端没有快照，或将同一实例的另一份快照认作本次结果。已有 ID 的查询和 Unhealthy 重建有各自的生命周期。

## 后端的答复写在哪里

Checkpoint 的状态是调用方读取诊断的依据。首次拒绝时，在 Pending 状态持久记录发生时间、源 Pod 身份及 API 摘要。摘要包含操作名和 HTTP 状态，并在实际取得时附后端业务码、经脱敏和截短的错误说明、对应请求的 requestId。缺少业务码、说明或 requestId 时允许省略；只有 403 时写“ACS 拒绝创建快照（HTTP 403）”。不要从状态码推测是权限不足还是实例状态不符，也不要存整份响应、响应头或 SDK 错误转储。

首次 403 发一条 Warning Event 便于排障。同一轮连续 403 不逐次制造相同事件，也不在状态中累积响应列表。结束时，失败状态的 `status.message` 与终态 Event 同时给出首次拒绝摘要和实际停止原因；后一次返回不同的明确原因时，说清先后。重启及 Event 过期后，仍能从对象读到原因。后续成功则更新为 Creating 或 Succeeded 的正常状态，先前的拒绝仅作为历史。manager 的同步请求若先超时或被取消，返回当时的等待结果，不能预报后续终态。

## 自动休眠与快照各自的结果

用户已选择按时休眠。自动休眠到点即按原流程启动，正在等待的用户快照不延长实例运行时间。`keepRunning` 继续只控制底层快照完成后的 Pod 运行行为。休眠流程自己创建的 Checkpoint 仍按原流程推进。[用户决定](decision.md)

失败消息必须单独读得懂。Checkpoint 的 `status.message`、对应的失败 Event 以及观察到该终态的快照 API 调用方，都应看到失败的步骤、已知的首次拒绝和重试结束原因。若失败的是休眠本身依赖的 Checkpoint，Sandbox 的休眠失败原因应说明“休眠所需的快照创建失败”，并保留相同的原因。独立的用户快照失败不会把已经成功的休眠标为失败。以下示例描述消息语义，实际文案沿用组件语言。

| 控制器掌握的事实 | 调用方应看到的结果 |
| --- | --- |
| ACS 只返回 HTTP 403，没有业务码和文案；窗口内一直被拒绝 | “快照创建失败。ACS 拒绝了创建请求（HTTP 403），30 秒重试窗口已结束。” |
| ACS 返回 HTTP 403，明确说明权限不足，重试后仍被拒绝 | 说明 ACS 返回 403、权限不足及窗口耗尽。保持原有休眠计划。 |
| ACS 明确拒绝，之后有证据表明自动休眠释放了同一源 Pod | “快照创建失败。首次请求时实例状态暂不允许创建快照。重试前，自动休眠已释放源 Pod。” |
| 已记录拒绝，重试时原 Pod 已经不可用，删除原因不明 | “快照创建失败。首次请求被后端拒绝，重试时原 Pod 已不可用。”附已知的拒绝原因。若同名 Pod 的 UID 已变，明确说明源 Pod 已被替换并停止对新 Pod 发起创建。 |
| 第一次检查就无法定位 Pod，或旧对象缺少此前创建尝试的记录 | 说明在哪一步无法定位源 Pod。例如“快照创建失败。首次检查时未找到可用于快照的源 Pod。”旧对象不能断言这是第一次检查。 |
| 已取得后端快照 ID，随后源 Pod 消失 | 按已有 ID 跟踪快照结果。单凭 Pod 消失不能宣告该快照失败。 |

上述情况均不以裸 `Pod Not Found` 作为业务失败原因。仅凭 Sandbox 当前为 Paused 或一次 Pod 查询未命中，无法确认是谁删除了原 Pod。若队列延误使控制器同时发现重试期限已过、原 Pod 已不可用，消息应保留首次拒绝和当前观察，不猜测 Pod 在期限前还是期限后消失。

## 当前边界

休眠优先顺序与用户可见的失败原因已确认。当前完整候选采用创建接口的 HTTP 状态判断、30 秒窗口、5 秒间隔以及状态和 Event 的诊断摘要。现场的 ACS 业务码仍未知，设计和验收都能覆盖这个情形。

已核对的社区 master 含 Checkpoint API 和 manager 调用方；处理本次错误的控制器和 ACS provider 位于组件维护源码。后续源码交付须先确定符合项目分支基线约束的内部组件工作路径。本文是产品行为候选，尚未进入独立评审或实施。
