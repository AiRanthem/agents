# Checkpoint 重试与自动休眠 · 设计讨论稿 v1

## 用户遇到了什么

Sandbox 刚唤醒时，用户要求保存当时的文件系统。管理服务成功创建了 Checkpoint 对象，底层服务两次回复实例状态暂不允许创建快照。下一次处理请求前，自动休眠已经删除了源 Pod。用户最后只看到 `Pod Not Found`，无法从返回结果知道快照曾经针对一个真实运行的 Pod 发起过。同期旧控制器还在反复处理已经结束的 Checkpoint。现场时序和版本证据见[排查记录](context.md)。

## 已有快照的处理

建议把 Succeeded 和 Failed 作为该次创建的最终结果。源 Pod 消失、重建或控制器重启后，再处理这些对象时，保留原结果、原因、完成时间、后端 ID 和恢复数据。common control 没有收尾动作时直接结束本轮。只有实际的生命周期任务才需要后续调谐，例如 ACS 控制模式下从原完成时间计算的 TTL 到期，以及已请求删除对象的 finalizer 清理。该约定同时覆盖旧标签形式的 pod-info 和包含 filesystem 的快照。

这样处理有实际的兼容性要求。快照列表只展示 Succeeded，休眠及升级流程也判断 phase，恢复和克隆仍可能读取快照 ID、Pod 模板差异和关联的 SandboxTemplate。直接用 `agent-sandbox-controller-v0.6.7-release.4` 替换旧版会停止这类错误重试，但其 common control 会将已成功的非 pod-info-only 对象改成 Failed。因此建议选择包含终态保留行为的修订镜像。现有候选镜像能否作为临时缓解，取决于存量对象会选中哪种控制模式；评估还需计入升级后源 Pod 才消失的对象。

停止重试无需先清空旧对象。对完成时间或模式不明、有后端 ID、有关联模板或仍用于恢复的对象，默认保留。按既有 TTL、所有者和显式删除语义回收；不能仅凭 phase、对象年龄或 Pod 缺失推定数据可丢弃。是否人工清理须有资源归属和引用证据。已经被旧版本改写的历史结果只能凭额外证据恢复。

## 新快照如何推进

- 建议仅给后端**明确返回实例状态暂不允许创建**的首次创建操作设置短重试窗口。重试使用同一个 Checkpoint UID、原 Pod UID 和原实例，避免同名 Pod 重建后拍到另一份数据。权限拒绝、传输超时或缺少返回 ID 的情形分别保留原有处理路径。超时只说明结果未知，同实例的另一份快照不能作为本次成功的凭据。
- 讨论用的初始参数为首次明确拒绝后最多等待 30 秒，同一对象每 5 秒左右再试一次，单次计划延迟上限 5 秒。选择这个量级，是为 manager 默认 60 秒的同步等待留出完成快照的时间。窗口和最早可重试时间跨重复事件及控制器重启生效；受限流或排队影响，实际执行可能更晚。窗口到期后若此前均为明确拒绝，就在下一次调谐记录超时失败。对大量同时拒绝的对象仍需限制总体重试速率。
- 在 Checkpoint 状态里保留首次拒绝的时间和可识别原因。后续查到源 Pod 已删除、正在删除或已换成新 UID，要能向仍在等待的调用方同时说明先前拒绝和当前源 Pod 的情况。首次检查就查不到 Pod 时，只报告当时观察到的事实。只有审计或对应生命周期证据能归因到自动休眠。manager 已通过现有错误消息传递 Failed 原因，可以沿用原 API。
- 已取得后端 ID 的请求进入 Creating，由控制器跟踪这份快照。首次创建被暂时拒绝、首次创建是否获接纳未知、已创建快照被明确报告 Unhealthy，是三个不同的恢复场景。对于晚到的创建成功响应或状态写入失败，凭原请求身份和已知 ID 接续。删除或调用方先超时时，服从既有清理流程。

## 需要决定的产品行为

推荐让自动休眠按时启动。控制器及时重试快照，若底层在源 Pod 可用期间接受请求，则跟踪至完成；若源 Pod 先消失，则结束这次请求并解释原因。这样保留用户设定的休眠和计费预期。`keepRunning` 表示底层执行完快照后是否让 Pod 继续运行。Sandbox 为完成自身休眠而创建的 Checkpoint 有独立的所有者，仍须能推进休眠。

另一个选择是让已接纳的用户快照限时推迟自动休眠。这能增加成功机会，也会延长实例运行时间。若选择此路线，下一版须定义保护从何时开始、最长多久、多个请求是否共享截止时间、控制器重启或调用方取消如何释放保护，以及已经启动休眠时新来的请求如何响应。

## 当前边界

本稿等待用户选择快照与休眠的优先关系。短重试窗口的参数是设计建议。现场材料只包含 HTTP 403、错误文案和请求标识，尚缺可作为分类依据的实际后端错误码。可凭对应 Checkpoint 的 Warning Event reason 或后端请求记录补证；取证前不启用针对所有 403 的快速重试。队列的 26 分 45 秒间隔无需作为重试目标。

已核对的社区 master 含 Checkpoint API 和 manager 调用方；处理本次错误的控制器和 ACS provider 位于组件维护源码。后续源码交付须先确定符合项目分支基线约束的内部组件工作路径。本文是产品行为候选，尚未进入独立评审或实施。
