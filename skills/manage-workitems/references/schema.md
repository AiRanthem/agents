# Project record schema, version 2

The ownership rules below describe ordinary operations. [User-authorized manual recovery](recovery.md#user-authorized-manual-recovery) permits concrete state/file corrections and script repair after a script blocker; preserve actual evidence and invalidate affected bindings.

The program creates and maintains YAML. Work-item agents read the returned prose payload and edit only the Markdown drafts selected by `begin` or supplied as actual work-product reports; Markdown bodies contain the complete current effective content, not superseded alternatives or event transcripts. The program treats their prose as opaque and validates only structured state and designated bindings. Git history is the audit trail for earlier body versions. Paths below are relative to the management root.

| Path | Owner and content |
| --- | --- |
| `.project/project.yaml` | Program: project identity, exact storage authority, backend configuration, repository and optional main-workspace/worktree configuration. |
| `workitems/<id>/metadata.yaml` | Program: identity, title, kind, dependencies, decomposition/fix links, document routes and design version/state. |
| `.project/state/<id>.yaml` | Program: exclusive ownership, active development, checkpoint state and `workflow.autonomy` scope authorization, content-bound work products and user acceptance bindings; author/reviewer attribution remains independent of executor lifecycle. |
| `.project/sync/<id>.yaml` | Program: durable external intent, uncertain outcomes and verified receipts. Returned commands resolve its location; it is not a Markdown handoff. |
| Root and item `AGENTS.md` | Program-generated routing to the current shared workflow and preserved business instructions. |
| `.project/context.md` | Overall project facts and business context. |
| `.project/project-instructions.md` | Program-generated routes to current project context and business instructions. |
| `.project/business-instructions.md` | Optional explicit project-specific instructions containing current effective constraints. |
| `evidence/<id>.yaml` and `.md` | Program-owned knowledge metadata and its complete current opaque Markdown body; entries are global and need not point to an item. |
| `workitems/<id>/requirement.md` | Goal, scope, acceptance and delivery obligations. |
| `workitems/<id>/spec.md` | The complete current design; no machine-status frontmatter. |
| `workitems/<id>/decision.md` | Current effective decisions and approval context, maintained as one complete Markdown document. |
| `workitems/<id>/context.md` | Current facts, verification, remaining uncertainty and handoff. |
| `workitems/<id>/logs.md` | Current operational context and handoff, maintained as one complete Markdown document. |
| `workitems/<id>/records/<record-id>.md` and `.yaml` | Current pointer-bound review, delivery, waiver, cleanup or source-preservation evidence, paired with program-owned bindings. |

Agent-authored Markdown is opaque to the program. For decision and log updates, write the complete current document, remove superseded statements, and retain constraints that still apply. The program replaces the file; it does not append events or infer semantic staleness. Git history is the audit trail for prior document versions. Keep only evidence pairs required by current review, delivery, waiver, cleanup or preservation pointers, plus artifacts needed to resume pending operations; when a pointer is invalidated, its evidence pair is removed in the same publication. Explicit development discard retains its cleanup snapshot through `workflow.development_discard_record` until fresh code preparation is recorded; ordinary cleanup may replace `cleanup_record` without losing that pending reservation evidence.

## Identity and hierarchy

New IDs are `<code>-<phrase>`, for example `123-quota-lock`. Each code character identifies one hierarchy level; siblings use `1`–`9`, then `A`–`Z`. Phrases use lowercase ASCII words separated by hyphens. IDs are stable after publication, including archived and cancelled items. The program allocates and resolves IDs; an unpublished conflicting allocation is retried only through its returned workflow.

Hierarchy and `split_from` record decomposition provenance. `depends_on` records delivery prerequisites. A separate post-delivery defect item records `fixes: <original-id>` and retains the original `done` delivery history. Cancellation never fulfills a prerequisite. Migration preserves existing IDs and DAG references.

known-limit: one character per level allows 35 siblings. A larger capacity needs an agreed encoding change preserving existing references.

## Program-derived lifecycle

`owner.token` and `workflow.autonomy.authorization.claim_token` authorize current item writes. Each transfer creates a fresh item-scoped token; local identities preserve other item claims. Session/coordinator fields record provenance. `workflow.control_transfers` binds the actual user source and original/receiving claims. A transfer preserves source and business evidence while removing runtime scheduling state. Project state does not track native workers or require liveness proof. Signed edit tickets and publication journals retain their exact transaction identities; they are not execution tasks.

`workflow.validation_waivers` maps named verification checkpoints to current `validation-waiver` record pairs with `result: skipped`, actual user source, contract/base/dependency binding and original input guards. Code-related decisions retain source snapshots. Explicit human acceptance may replace implementation review with a `development-finish` pass whose `approval_kind` is `human_acceptance`, retaining actual user source and registrar. These current user decisions override their corresponding default gates below without fabricating independent evidence; changed targets require current authorization. See [user verification decisions](commands.md#user-verification-decisions).

The design begins at version 1 when first written. The program hashes raw bytes: changed bytes or a changed `design.next_action` increment the version; identical bytes and route do not. Changed bytes invalidate stale current bindings, not semantic approval by themselves; a material contract change invalidates the affected approval and independent coverage. An authorized contract-internal autonomous revision records approval `kind: derived_revision`, preserves `original_user_approval` and binds the new design bytes and revision ticket; an independent passing assessment of the current version must explicitly return `contract_unchanged: true`; the reviewer may retain applicable earlier coverage under the [shared rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage). A changed approved contract requires a user decision. Publishing a complete user-approved spec moves it to `review-pending` and records publication-bound approval, or preserves this bound derived revision; `implementable` requires genuine independent passing coverage bound to the current requirement, spec, base and sessions, either from current review or a valid applicability carry-forward. A retained genuine earlier independent Pass may instead support a `design-reuse` applicability checkpoint for an unchanged approved contract and relevant assumptions. `workflow.design_basis` retains the original review, approval and complete original read contents/hashes; `workflow.design_reuse` records applicability against the current binding, assessor and report. The original `design.review` identity, report and old binding remain intact; it is not a new independent Pass or waiver. A missing prior Pass, newer failed review or pending user-owned contract decision blocks reuse. A failed applicability assessment that cannot establish equivalence or key-assumption impact may retain `derived_reuse_pending` only when genuine original approval and Pass exist. This candidate-comparison evidence permits independent review against the original approved contract, not implementation or a skip waiver. An independent comparison failure is retained in `workflow.design_review_failure` and blocks reuse. A subsequent contract-internal `design-update` retains `derived_reuse_pending`, `assessment` and `original_user_approval`, rebinds requirement/spec/version and remains `review-pending`; only a later independent pass clears the failure. Ordinary `begin design-review`  return the full `design_basis` for this comparison. That pending candidate’s ordinary independent pass requires the actual reviewer’s `--contract-unchanged` confirmation; the owner/controller’s applicability pass requires no new independent confirmation; the controller registers the actual reviewer confirmation with the same finish flag. An identified material contract change clears the reuse basis and returns to actual user approval. The program checks structure, identity, hashes and stale writes rather than Markdown semantics. None of these states is expressed by editing prose.

Formal spec publication attests user approval obtained before writing and records current provenance; separate approval registration is not required to start design review. `design.next_action` defaults to `implement`; `split` records an oversized parent’s reviewed destination. The route is part of its design binding, so changing it increments the version and invalidates affected review. A split-routed parent requires current independent Pass before child creation and cannot start source implementation, including through a design-review waiver at `development-start`. Child creation writes a relevant inherited spec at version 1 and `review-pending`; its own independent review can pass without supplementary design.

Implementation requires a current approval/review binding or the user's explicit scoped design-review waiver, plus delivered prerequisites and published exclusive ownership. For a simple requirement, the user may explicitly authorize `development-start --skip-design-review --approval-source SOURCE` for this unchanged contract; the program records a requirement/spec/base/dependency-bound waiver, not a review pass. The agent cannot decide to skip review itself. A requirement-only contract is permitted for that waiver when there is no spec. Contract/dependency changes invalidate it and migration never fabricates it. Actual verified delivery records `done`; passing tests, review or a local commit is insufficient. Delivery and local cleanup remain separate. An unfinished fix blocks new downstream implementation/delivery, aggregate completion and the next gated checkpoint in an active session. After fix delivery, relevant baselines and reviews are checked again.

Autonomy authorization binds a coordinator, selected scope, requirement/decision hashes and any explicit design-review skip. For current actual user approval, `approved_contract` preserves that approval and the complete approved requirement/spec/decision for subsequent independent comparison. First authorization of a derived reuse/mechanical/confirmation/revision state requires valid independent coverage without a waiver and obtains those complete texts from `design_basis.read` with authentic `design_basis.approval` kind/source/original approval provenance. Pending comparison is never captured as a currently approved contract; derived provenance is never fabricated as new user approval. Actual implementation/fix products retain report bodies/hashes, provenance, current contract/code binding and the development-start read basis. `instruction_changes` records changed guarded instructions for current design coverage and mandatory independent code review. They establish neither acceptance nor delivery. Author sets retain all substantive contributors, including unsuccessful writers; they enforce review independence without tracking executor lifecycle. Human acceptance binds the actual source and current reviewed tree. Verified-cleaned delivered items exempt only missing historical reads inside their removed worktree.

Schema 1 is readable for diagnostics and migratable through `migrate`; no ordinary v1 write compatibility is implied. Migration preserves identities, active ownership, control claims, DAG and current effective business constraints, and blocks on unresolved synchronization or a business source that needs an agent to assemble current text. Migration publication validates the exact deterministic candidate under raw-byte guards. Backend synchronization uses a receipt-bound migration identity while preserving the item owner; its follow-up publications change only synchronization receipts. Knowledge metadata is converted from JSON to YAML without dropping fields, and its Markdown body remains opaque. It does not retain obsolete document copies as a parallel project history. Project Git history provides prior versions.

Unsupported operational state is diagnostic-only until explicit recovery. The program rejects unknown nonempty autonomous or retained-generation fields instead of silently treating stored source as eligible for implementation, acceptance or collection. Existing source and stored evidence are preserved.

## Managed lifecycle state

`workflow.design_authors` cumulatively preserves authors of the original design and every substantive revision across versions; another author’s later revision never removes prior contributors or makes them independent reviewers. Uniquely determined mechanical corrections under the [shared authorship boundary](../../review-design/references/implementable-gate.md#mechanical-corrections-and-authorship) retain the reviewer’s independence and are recorded with their old binding, exact diff, evidence and final candidate SHA; the original substantive authors remain intact. Only an independently reviewed, genuinely approved candidate can use this exception; an original author cannot self-approve by claiming a mechanical correction. `design.approval.recorded_by` identifies the registrar while `source` identifies actual user approval; registrar identity alone is not authorship. Legacy `session` remains readable provenance.

`workflow.lifecycle` owns adopted policy, mode/coordinator handoff, replacement intent, immutable preservation checkpoints, retired source generations with dispositions, resource states and exact collection intents. Resources transition live → released → deleting → deleted; released resources can return live before deletion marking. Generation workflow phases remain separate. The program validates identities and uses the existing `.project/state/<id>.yaml` guarded publication authority. See [resource lifecycle](resource-lifecycle.md).
