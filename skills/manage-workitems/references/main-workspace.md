# Association with a business main workspace

A separate main workspace owns reusable business context, repository conventions, environments and local skills. The managed project owns requirements, designs, coordination and evidence in its dedicated Git repository. Association is optional; physical nesting does not merge their authority or automatically load the main workspace's instructions.

At creation, preserve the selected main-workspace identity, repository/ref when present, original instruction routes and scoped business constraints. Code may live under the project's ignored `worktrees/` or a dedicated main-workspace subdirectory such as `worktrees/<project-id>/`. The program owns portable configuration, machine-local binding and worktree resolution. Changing configuration is not authorization to move existing dirty worktrees or claims.

The program returns required original main-workspace `AGENTS.md` paths in the operation's read inputs. Actually read each original instruction before dependent business/code work; a copied summary, path string or inherited project prompt is insufficient. Preserve its permission, delivery, environment and repository boundaries. Load further business context/skills only as returned or needed for the authorized substantive source task. When delegating an authorized review, pass these required original paths and the verified roots.

The main checkout keeps its own branch. Project metadata publication targets only the selected dedicated project ref and does not commit main-workspace changes. Creation may use the same storage repository with a separate empty project branch; it does not copy main-workspace files or history. Nested independent repositories require scoped, versionable container ignore rules that preserve the container's own `.gitignore` and unrelated contents. The setup program owns those checks; report a missing supported setup input instead of manually constructing Git configuration.

Recovery restores the separate main workspace and verified local binding through program-provided inputs. A clone of project records alone does not restore that environment. Missing binding, original instructions or ambiguous paths stop affected work with the program's listed facts; abstract diagnostic reads can still report available records.

Cleanup/removal enumerates exact item-owned worktrees both inside and outside the project. Preserve the main workspace, shared roots, environments, skills, source repositories, sibling projects and their worktrees. Never recursively remove a shared worktree root or infer item ownership from a directory prefix. Keep remote refs and external history outside the default local-removal scope.
