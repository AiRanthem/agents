# Project lifecycle

Ordinary operations follow the command workflow below. A script blocker or defect may use [user-authorized manual recovery](recovery.md#user-authorized-manual-recovery), including explicitly authorized state/file correction and script repair. Its contract governs the command-only, returned-path and stop/retry restrictions for that repair.

Project record changes use the [command contract](commands.md). Ordinary operations use the fixed workflow: `begin` returns inputs and editable Markdown paths; read them, write only those drafts, execute the returned finish command and follow its status. Design review and design-reuse assessment supply program-declared result/provenance finish arguments after assessment; implementation review may bind a completed report at begin or declare the actual result/provenance at finish. YAML, status, ownership, dependency/fix gates and Git/Aone publication belong to the program. A `partial` outcome permits only its returned resume command. A `blocked` outcome with `code: stale_ticket` permits only its returned `next_command` to begin again with current inputs. `blocked` with `code: stale_evidence` has no `next_command` or `finish_command`; obtain current authorization/review evidence and report the blocker. Otherwise report the listed blockers or missing facts and stop the affected operation. Explicit autonomous advancement continues unrelated ready items through its coordinator interface.

## Requirements and design

Creation ends at metadata, necessary background and requirement skeletons. It preserves the user's goal, scope, acceptance and delivery obligations, leaving unknowns explicit. It does not start source investigation, splitting, a spec or a worktree.

Within an explicitly requested design scope, use `design-update` for the complete current spec. Stable designs may precede prerequisite delivery, with explicit dependency assumptions and unresolved choices. Reconcile relevant assumptions with actual delivered prerequisites and the current code baseline before formal review. Use `decision-record` to maintain the complete current decision document: retain still-effective decisions, remove superseded text, and do not copy a decision transcript into project content. Complete user confirmation before publishing a formal spec; publication attests that approval, records its binding and moves a changed design to `review-pending`. Separate approval registration is optional provenance, not a design-review gate. Reuse existing explicit approval only for the unchanged approved scope.

Design review requires the user's explicit request, either separately or within scoped autonomous advancement, and an independent reviewer. The [shared coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage) require a complete first review, then reuse valid coverage and assess only changes and affected interactions. A later round does not require a new context; prefer the original still-independent reviewer. It begins `design-review` without a result, reads the complete original requirement/spec and raw repository evidence, and writes the returned review report. After assessment it supplies actual `--result pass|fail --provenance SOURCE` and any required contract-preservation/mechanical-correction flags declared by the returned finish options under the command contract. The program binds a pass to current document bytes, design version, baseline and actual author/reviewer identities and real approval provenance. A contract-internal revised candidate preserves the original user approval under `kind: derived_revision`; an independent reviewer, preferentially the original reviewer if still independent, compares it with the full approved requirement/spec/decision captured by authorization and returned as `approved_contract`, then must return `contract_unchanged: true` before a pass. A derived revision does not create a new user approval. An actual contract change blocks for the user's decision. Only current independent coverage establishes `implementable`; exploration and self-checks cannot do so. When the program retains a genuine earlier Pass, the authorized owner/controller can use `begin design-reuse ID` and its returned report/finish workflow to establish applicability against current inputs. Its actual pass records carry-forward of the original independent conclusion and approval, not a new independent Pass or a waiver. A fail sends the affected scope to independent review. When only equivalence or key-assumption impact is unconfirmed, genuine original approval/Pass may support `derived_reuse_pending` comparison evidence; the actual independent reviewer must confirm preservation of the original approved contract before pass (`--contract-unchanged` in ordinary finish, the same flag when the controller registers the actual independent result). Pending evidence never authorizes implementation or a skip waiver, and material contract changes clear the reuse basis for actual user approval. Material contract changes require actual user approval and affected independent review; no prior Pass, a newer failed review or a pending user-owned decision prevents reuse.

For oversized work items, the full spec includes usable delivery stages, acceptance coverage, shared contracts and DAG, with `design.next_action: split` selected by `design-update --next-action split` before review. Full parent design rigor remains required. Current independent Pass routes to decomposition instead of source implementation. `create --parent` requires that Pass and creates inherited child specs with requirement/context drafts. Children go directly to their own review; only actual blocking gaps require supplemental design and affected re-review. Parent or cross-item contract changes return to their design owner. Once children cover the whole outcome and retained code is verified cleaned, the parent becomes an aggregate.

## Implementation and handoff

Use `development-start` for a requested implementation; the advancing agent uses the same guarded operation with actual author attribution. The program validates the current independent review or an explicit user-scoped waiver, checks prerequisite delivery and open upstream fixes, publishes ownership and prepares/resolves the item's development. For a simple requirement, the user may explicitly authorize `development-start --skip-design-review --approval-source SOURCE` for this unchanged contract; the program records a requirement/spec/base/dependency-bound waiver, not a review pass. The agent cannot decide to skip review itself. Resume the existing identity/worktree. Read returned original main-workspace instructions and the code repository's applicable instructions before source operations. Do not create a parallel development or take over another writer because a session is old.

After the program publishes a successful start, implement the approved contract using `implement-design`. The project workflow authorizes its final fresh-subagent `review-implementation`. Record actual independent findings with `development-finish`; a stable passing review moves the item to awaiting delivery. Capture current facts, applicable verification, snapshot identity and next action through `context-update`. Code remains uncommitted for the user's final inspection unless the user requests code submission.

## Scoped autonomous advancement

An explicit advancement instruction authorizes the coordinator to schedule ready items in the selected `--all`, `--tree` or repeated `--item` scope, including independent design/code review and contract-internal fixes. It preserves initial user approval, dependency delivery and current user acceptance gates. The advancing agent manages task trees directly; ordinary checkpoints and `autonomy complete` register current content, actual reports and independent reviewer/author attribution. Substantive authors and repair workers cannot independently review their own current artifacts. Design reviewers may directly fix authorized mechanical candidate errors under the shared standard without acquiring substantive authorship, then pass the final exact candidate in the same round. A foreign control claim needs authorized takeover when starting project or shared source writes; authorized reads, investigation and read-only reviews need no transfer; unavailable old executors do not lock project state; other ready items continue.

After a stable passing implementation review, report `awaiting_acceptance` and retain uncommitted code for the user. Record actual acceptance with `autonomy accept ID --approval-source SOURCE`; it binds current artifacts and code tree. User modifications require independent review again before acceptance. Acceptance is separate from declared delivery. `accepted_awaiting_delivery` still needs real delivery evidence; only actual delivery produces `completed`. Aggregates retain their ordinary evidence assessment and completion workflow.

## Delivery, fixes and cleanup

Use `delivery-record` after the declared obligations are actually met. The program verifies supported repository delivery evidence; the report states what was merged, built, released, deployed or tested and what remains unverified. For an aggregate, the responsible agent or reviewer must assess actual evidence against every acceptance criterion and record truthful coverage in the report. The program checks required evidence kinds, project prerequisites and available structural conditions, including supported Git inclusion for development items. It does not parse Markdown semantics or decide whether evidence satisfies acceptance criteria; that substantive assessment belongs to the responsible agent or reviewer. The program derives readiness; the agent does not rewrite downstream metadata to imitate it.

A defect in delivered scope uses `begin fix ORIGINAL --title TITLE --slug SLUG`. It creates an independently delivered item linked by `fixes`, while the original delivered state and current delivery evidence remain intact. Every unfinished fix blocks downstream new implementation, delivery and aggregate completion, including the next checkpoint of an active session. Fix delivery removes that blocker only; actual code baselines and review bindings still require current validation. There is no general reopen transition for delivered items.

Cleanup has separate authorization and evidence. Requested cleanup follows `cleanup-worktree` and preserves its exact-manifest boundary, shared main-workspace roots, sibling worktrees and retained remote recovery refs. A failed cleanup does not undo successful delivery. Code commits, pushes, cleanup and project removal retain their respective user authorization boundaries.

The design owner completes user confirmation before formal design publication, reusing covering approval of an unchanged contract. A published versioned spec can enter an authorized independent review without a second approval or separate approval-registration checkpoint. Material contract changes still require user confirmation before publication; current artifact bindings and reviewer independence remain mandatory.
