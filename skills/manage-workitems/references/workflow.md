# Project lifecycle

All project record changes use the [fixed command workflow](commands.md): `begin` returns inputs and editable Markdown paths; read them, write only those drafts, execute the returned finish command and follow its status. Only design review supplies program-declared result/provenance finish arguments after assessment; implementation review evidence is supplied at `begin development-finish`. YAML, status, ownership, dependency/fix gates and Git/Aone publication belong to the program. A `partial` outcome permits only its returned resume command. A `blocked` outcome with `code: stale_ticket` permits only its returned `next_command` to begin again with current inputs. `blocked` with `code: stale_evidence` has no `next_command` or `finish_command`; obtain current authorization/review evidence and report the blocker. Otherwise report the listed blockers or missing facts without additional operations.

## Requirements and design

Creation ends at metadata, necessary background and requirement skeletons. It preserves the user's goal, scope, acceptance and delivery obligations, leaving unknowns explicit. It does not start source investigation, splitting, a spec or a worktree.

Within an explicitly requested design scope, use `design-update` for the complete current spec. Stable designs may precede prerequisite delivery, with explicit dependency assumptions and unresolved choices. Reconcile relevant assumptions with actual delivered prerequisites and the current code baseline before formal review. Use `decision-record` to maintain the complete current decision document: retain still-effective decisions, remove superseded text, and do not copy a decision transcript into project content. An actual approval source binds the current design and moves it to `review-pending`. Reuse existing explicit approval only for the unchanged approved scope.

Design review starts only on the user's explicit request in a separate independent session. It begins `design-review` without a result, reads the complete original requirement/spec and raw repository evidence, and writes the returned review report. After assessment it supplies only `--result pass|fail --provenance SOURCE` as declared by the returned finish options. The program binds a pass to current document bytes, design version, baseline and reviewer/approval sessions. Only this current independent pass establishes `implementable`; exploration and self-checks cannot do so.

## Implementation and handoff

Use `development-start` for a requested implementation. The program validates the current independent review or an explicit user-scoped waiver, checks prerequisite delivery and open upstream fixes, publishes ownership and prepares/resolves the item's development. For a simple requirement, the user may explicitly authorize `development-start --skip-design-review --approval-source SOURCE` for this unchanged contract; the program records a requirement/spec/base/dependency-bound waiver, not a review pass. The agent cannot decide to skip review itself. Resume the existing identity/worktree. Read returned original main-workspace instructions and the code repository's applicable instructions before source operations. Do not create a parallel development or take over another writer because a session is old.

After the program publishes a successful start, implement the approved contract using `implement-design`. The project workflow authorizes its final fresh-subagent `review-implementation`. Record actual independent findings with `development-finish`; a stable passing review moves the item to awaiting delivery. Capture current facts, applicable verification, snapshot identity and next action through `context-update`. Code remains uncommitted for the user's final inspection unless the user requests code submission.

## Delivery, fixes and cleanup

Use `delivery-record` after the declared obligations are actually met. The program verifies supported repository delivery evidence; the report states what was merged, built, released, deployed or tested and what remains unverified. For an aggregate, the responsible agent or reviewer must assess actual evidence against every acceptance criterion and record truthful coverage in the report. The program checks required evidence kinds, project prerequisites and available structural conditions, including supported Git inclusion for development items. It does not parse Markdown semantics or decide whether evidence satisfies acceptance criteria; that substantive assessment belongs to the responsible agent or reviewer. The program derives readiness; the agent does not rewrite downstream metadata to imitate it.

A defect in delivered scope uses `begin fix ORIGINAL --title TITLE --slug SLUG`. It creates an independently delivered item linked by `fixes`, while the original delivered state and current delivery evidence remain intact. Every unfinished fix blocks downstream new implementation, delivery and aggregate completion, including the next checkpoint of an active session. Fix delivery removes that blocker only; actual code baselines and review bindings still require current validation. There is no general reopen transition for delivered items.

Cleanup has separate authorization and evidence. Requested cleanup follows `cleanup-worktree` and preserves its exact-manifest boundary, shared main-workspace roots, sibling worktrees and retained remote recovery refs. A failed cleanup does not undo successful delivery. Code commits, pushes, cleanup and project removal retain their respective user authorization boundaries.
