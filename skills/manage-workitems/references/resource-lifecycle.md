# Source generations and internal resource lifecycle

Use the typed `project.py lifecycle` commands in [commands](commands.md). The program owns generation identity, resource relationships, exact manifests, repository inspection and publication. Lifecycle policy is explicit authorization for preservation-ref publication and collection of registered internal resources; predevelopment authorization alone does not establish that policy. Ordinary development/PR/release refs retain their separate submission and cleanup boundaries.

## Approval and execution handoffs

A design owner completes the shared [approval handoff](../../advance-project/references/discussion-and-authorization.md#design-approval-handoff), then records actual approval against unchanged inputs. `show.workflow_gates` distinguishes approval, independent review and implementation gates. A successful query or published draft does not establish stage eligibility.

Use [control-claim takeover](commands.md#control-claims-and-takeover) when a different conversation must continue the same work item; it preserves mode and advancement authorization. Use `lifecycle handoff` for an actual execution-mode/coordinator handoff: it retains contract, source, reviews and any speculative marker, archives current execution authorization, and leaves actual prerequisite/convergence gates intact. It requires its own covering user instruction and grants no archive-publication or GC policy. For a changed contract or prerequisite baseline, use `lifecycle replan`. Before replacing work, settle exact pending project publications. The advancing agent coordinates source writers and necessary isolation through available host facilities; project state requires no worker registration or inaccessible-host stop confirmation. `lifecycle replan` retains history, stores an unreviewed preservation checkpoint and records the intended manual/autonomous coordinator handoff. It clears current authorization and review/acceptance evidence without inventing new approval. A repeated unresolved transition retains its checkpoint identity. A handoff does not authenticate a dishonest coordinator; the existing trusted-capture boundary applies.

`lifecycle prepare` creates a fresh isolated baseline. Autonomous speculative preparation still requires explicit predevelopment authorization and reviewed frozen prerequisites; manual preparation requires actual accepted prerequisite delivery. Mode switching preserves the replacement gate until preparation completes. Replacement work must migrate only its own delta, excluding inherited prerequisite code. Assess design applicability against the actual replacement under the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage). A retained genuine independent Pass requires current applicability evidence; independently review invalidated design coverage, or perform the first full review when no valid basis exists. Independent implementation review of the actual replacement remains mandatory; an old Pass or a skip-design-review authorization cannot waive it. `retained_sources` and the generation records identify the old source for that assessment.

Preservation stores the working tree and staged tree in immutable reachable commits without changing source HEAD, staging or working files. It captures the nonignored source only. Ignored files, nested repositories and unfinished Git operations require their own disposition; they are never silently uploaded or deleted. A preservation checkpoint is recovery evidence and cannot supply an independently reviewed prerequisite.

## References and retention

Local resource IDs include their host; physical manifests additionally guard the bound Git common directory. An offline host’s copies stay pending rather than being reinterpreted as same-named paths on another machine. Controlled cross-host replacement starts in the receiving host’s bound repository only after verifying the preserved source ref. Resources are exact registered worktrees, internal local refs, remote snapshot/preservation refs and fetched snapshot refs. A resource has a stable ID, project/item association, repository/ref or recorded worktree descriptor, expected OID, lifecycle state and retention reasons. Physical deletion manifests additionally bind host, Git common directory and exact path. Existing snapshot and retained-development descriptors are inventoried; unknown resources are not claimed by name.

Explicit `release` removes a frozen offer. A formal-convergence recovery ref can be released only with actual evidence covering the unchanged independently reviewed formal result; speculative/reconciling source recovery stays protected. Current frozen offers, unsettled snapshot publication, active/preparing generations, formal convergence, undisposed retired sources and explicit retention keep their required recovery refs. References follow each frozen snapshot's original transitive closure, even when today's DAG changes. Current contract changes stop advertising the old offer for new work. Audit history and old approvals do not permanently require physical copies. Reconstructible local refs may be collected while their verified remote snapshot remains pinned, provided no active local executor needs them.

Use `lifecycle adopt --worktree RELATIVE_PATH` to preserve an already-registered legacy retained source and give it a generation/disposition identity. `dispose --disposition migrated` records actual migration evidence bound to the current independent implementation review and unchanged target. `discarded` additionally requires an actual user source for discarding that exact unique generation. A source disposition releases logical migration references; dirty/ignored data continues to block physical worktree removal and consume capacity. Ordinary development worktrees continue through separately authorized `cleanup-worktree`.

The default adopted policy is seven days of grace for unused remote refs, two retained source generations/worktrees, twenty resident internal snapshot/preservation refs and twenty completed result caches per item. `max_snapshots` bounds both ref and completed-cache counts independently. Limits are configurable through typed policy arguments. Reaching a limit blocks creation; it never permits deleting a live reference or unique source. Status shows retention reasons, release/eligibility timestamps, pending operations and cleanup blockers. No unattended daemon is required: within an adopted policy, the coordinator performs maintenance at quiescent stage boundaries or when capacity blocks progress.

Completed result caches are collectible only when their signed manifest matches the result and complete reports already persisted in project Git. Collection verifies the canonical host-local path again, removes only that manifest and removes the empty directory. Unknown files, including files created during collection, remain and block completion. Pending/current executions retain their caches. Formal convergence re-fetches its pinned immutable recovery snapshot before creating the new worktree, so eviction of a reconstructible local ref does not prevent rebase.

known-limit: external stage directories have no program-owned allocation record. Preserve those paths; extending collection to them requires an exact allocation and ownership protocol.

## Collection and recovery

`lifecycle plan` persists exact deletion intent through guarded project publication. Pin creation and deletion marking check the same project item states, including consumers outside today's ancestor DAG. A marked/deleted remote snapshot is ineligible for new pins and deduplication; a new capture receives a new identity. Re-fetching an evicted local cache records a new residency while retaining the live immutable snapshot identity. Releasing an offer does not revoke an existing consumer’s inherited frozen closure. `collect` accepts only the returned intent/digest under the current control claim, including after an authorized takeover. The digest binds the manifest and does not create authorization.

Remote deletion is conditional on the exact recorded OID; unsupported conditional deletion fails closed. Local ref deletion also compares its OID. Collection orders reconstructible local refs before remote refs; each extant local copy requires exact verified remote recovery. Worktree removal rechecks ownership, repository identity, clean/ignored state, unfinished Git state and exact remote recovery. It uses ordinary Git worktree removal. Partial deletion retains the same intent: an absent exact ref can finish that resource, while a divergent/recreated ref is preserved. Metadata-publication recovery settles its original journal before continuing the outer lifecycle operation. A confirmed pre-push rejected project journal is historical evidence, not an uncertain live publication.

Project removal inventories current and retained worktrees, blocks unsettled lifecycle operations and includes the resource registry and its retained project-remote recovery ref. Default remote retention remains explicit in that manifest; removing the local project does not erase the surviving registry. Ref deletion does not guarantee immediate Git object reclamation; normal Git maintenance owns object storage.

known-limit: resource discovery covers registered project resources in the bound repositories; cross-project snapshot consumption needs an explicit shared-reference protocol before it can be supported. Offline-host local copies remain pending for their recorded host. Refreshing an adopted source after new commits produces a new checkpoint and resets its old disposition, retaining superseded checkpoints until the new disposition. Dirty retained worktrees require source cleanup/disposition and remain visible capacity consumers; preservation is not permission to force-remove them. Independently changed refs and unregistered data are reported for disposition rather than inferred disposable from their names.
