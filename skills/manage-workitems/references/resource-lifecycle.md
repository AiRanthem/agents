# Source generations and internal resource lifecycle

For script blockers or defects, [user-authorized manual recovery](recovery.md#user-authorized-manual-recovery) permits concrete approved state/file correction and script repair as an exception to the ordinary command-only and stop/retry rules below. Preserve actual evidence, permissions and source recovery.

Use the typed `project.py lifecycle` commands in [commands](commands.md). The program owns generation identity, resource relationships, exact manifests, repository inspection and publication. Lifecycle policy is explicit authorization for preservation-ref publication and collection of registered internal resources. Ordinary development/PR/release refs retain their separate submission and cleanup boundaries.

## Approval and execution handoffs

A design owner completes the shared [approval handoff](../../advance-project/references/discussion-and-authorization.md#design-approval-handoff) before formal spec publication; publication records its approval binding, without a separate approval-registration gate before review. `show.workflow_gates` distinguishes independent review and implementation gates. A successful query or published draft does not establish implementation eligibility.

Use [control-claim takeover](commands.md#control-claims-and-takeover) before modifying an item under a foreign claim; authorized read-only inspection needs no transfer. Use `lifecycle handoff` for an actual execution-mode/coordinator handoff: retain contract, source, reviews and recovery evidence, archive current execution authorization, and preserve actual prerequisite gates. It requires covering user instructions and grants no archive-publication or GC policy. For a changed contract or prerequisite baseline, use `lifecycle replan`. Settle exact pending project publications first and coordinate real source writers and necessary isolation; project state requires no worker registration or inaccessible-host stop confirmation.

`lifecycle replan` stores an unreviewed preservation checkpoint and the intended manual/autonomous coordinator handoff, retires the current generation and invalidates affected review/acceptance evidence. An unresolved transition retains its original identity. `lifecycle prepare` requires actual accepted prerequisite delivery in either mode, then creates a fresh isolated baseline. Migrate only the source item's own delta. Assess design applicability against the replacement under the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage), independently reviewing invalidated scope or conducting the first full review when no valid basis exists. Independent implementation review of the replacement remains required. `retained_sources` and generation records identify source to preserve and assess.

Preservation stores working and staged trees in immutable reachable commits without changing source HEAD, staging or working files. It captures nonignored source only. Ignored files, nested repositories and unfinished Git operations require their own disposition; never silently upload or delete them. A preservation checkpoint provides recovery, not independent approval or delivery.

Unsupported nonempty operational or retained-generation state blocks mutation until explicit recovery. Preserve the recorded source, resource locators and evidence; never drop unknown fields to make an item appear ready. Read-only diagnostic data is not permission to resume source writes or collect resources.

## References and retention

Resources are exact registered worktrees, internal preservation refs and retained caches. Each has an item/repository association, stable identity, expected OID or development descriptor, state and retention reasons. Local IDs include their host; physical manifests also bind Git common directory and exact path. An offline host's copies remain pending instead of being reinterpreted as same-named receiving-host paths. A controlled cross-host replacement requires verified preserved source and the receiving host's bound repository. Unknown resources are never claimed by name or prefix.

Undisposed retired source, pending preservation publication, current development and required physical recovery keep resources live. Semantic migration/discard does not release the last recovery ref until worktree removal is recorded. Superseded preservation checkpoints remain protected while their generation lacks an actual disposition. Audit history alone does not retain physical copies forever.

Use `lifecycle adopt --worktree RELATIVE_PATH` to refresh preservation for an exact registered retained source. `dispose --disposition migrated` requires actual migration evidence bound to the independently reviewed unchanged replacement; `discarded` requires the user's explicit authorization for that exact unique generation. Dirty or ignored source still blocks physical removal and consumes capacity. Ordinary development worktrees retain separately authorized `cleanup-worktree` boundaries.

The default adopted policy is seven days of grace for unused remote refs, two retained source generations/worktrees and twenty resident preservation checkpoints per item. Typed policy arguments configure these limits. Capacity exhaustion blocks creation; it never permits deleting a live ref or unique source. Status reports retention reasons, pending operations and cleanup blockers. At quiescent stage boundaries or on capacity blockage, the controller may maintain resources within an already adopted policy; no unattended daemon is required.

Historical runtime caches may contain the only unpublished report and remain protected without an independent archival verifier. Unknown files and externally allocated stage directories are not disposable merely because a stage completed.

## Collection and recovery

`lifecycle plan` publishes exact deletion intent under guarded project state. `collect` accepts only its returned intent/digest under the current control claim, including after an authorized takeover. The digest binds the manifest, not authorization. Recheck current retention requirements, source identity and publication outcomes before deletion. A blocked collection retains its continuation for the same intent; an uncertain archive publication resumes its original transition. The current coordinator must hand off before another session replaces or collects its resources.

Remote deletion is conditional on the recorded OID; unsupported conditional deletion fails closed. Local ref deletion also compares its OID and requires verified remote recovery. Collection orders local refs before worktrees and remote refs. Worktree removal rechecks ownership, repository identity, clean/ignored state, unfinished Git state and exact recovery, using ordinary Git worktree removal. Partial deletion retains the same manifest: an absent exact target may finish, while a divergent or recreated target is preserved. Settle metadata publication recovery before continuing the outer lifecycle operation.

Project removal inventories current and retained worktrees, blocks unsettled lifecycle operations and retains the resource registry with its project-remote recovery commit. Default remote retention remains explicit in that manifest; local project removal does not erase the surviving registry. Ref deletion does not guarantee immediate Git object reclamation.

known-limit: discovery covers registered resources in bound repositories, not unknown external stage directories or cross-project consumers. Extending collection needs explicit allocation, ownership and shared-reference protocols. Refreshing retained source after new commits creates another preservation checkpoint and resets disposition. Dirty source remains visible and protected; preservation never authorizes force-removal.
