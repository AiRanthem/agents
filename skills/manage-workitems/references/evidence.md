# Evidence and independent review

The commands below govern ordinary evidence registration. For script blockers or defects, use the separate [user-authorized manual recovery](recovery.md#user-authorized-manual-recovery) contract. Every record must describe actual review, acceptance, delivery or verification evidence.

Evidence distinguishes observed facts, inferences, search coverage and verification limits. Read primary requirement/spec and raw source pointers from the operation's complete `read` payload. A cached summary or previous review cannot establish the current contract, an absence claim or delivery.

For actual repository investigation within the user's requested scope, retain source paths/symbols, revisions or relevant content identity, configuration and observed outcomes. A matching HEAD does not identify dirty tracked/untracked source or dependency inputs. Claims such as “all callers” require a bounded search universe; new files or configuration may invalidate that coverage.

Current item facts, verification and handoff go through `context-update`. Reviews and delivery use the returned report drafts for their operation; the program writes paired Markdown/YAML records with requirement/spec/base/session and code snapshot bindings. Retain only the current records referenced by review, delivery, waiver, cleanup or snapshot state, plus pending recovery artifacts. Decisions use `decision-record` to replace the complete current decision document; use the actual user input and provenance when recording an approval, but do not accumulate superseded decision text. The program treats Markdown as opaque text and does not detect semantically obsolete passages. In ordinary registration, use the returned evidence paths and let the program maintain YAML gate bindings.

The shared knowledge store is separate from item records and does not require an item pointer. Use `knowledge-show ID` through the command contract to get the body path, hashes and exact guarded update/remove commands. Replace the entire Markdown body when updating; metadata YAML is maintained by the program. Use `knowledge-remove` only when the entry is explicitly obsolete or no longer useful. No-pointer status alone is not grounds for removal, and the program does not parse body semantics or identify stale claims. In ordinary updates, let the program maintain metadata YAML and supply the complete current body.

Initial independent reviewers form their own assessment from original inputs before reading previous findings. Independence requires separation from the target’s substantive authors/revisers; authorized mechanical corrections under the shared design standard do not establish substantive authorship; a later design-review round can reuse the original reviewer while it remains independent. A different session alone does not prove a review happened. Follow the [design coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage) for later changes and applicability carry-forward. Record the real review source and result; never manufacture provenance to satisfy a command. Design review additionally requires the user's explicit invocation, separately or as part of scoped autonomous advancement. The implementation workflow may require its final fresh-subagent review within the authorized item.

Autonomous evidence records current artifact bindings, actual report bodies/provenance and substantive author/reviewer attribution. The advancing agent manages native task trees outside project state. Structural checks reject stale content but cannot authenticate a dishonest registrar or prove semantic review quality. Preserve original user approval and the complete approved requirement/spec/decision for independent comparison of a derived revision; only the actual independent reviewer can confirm unchanged contract. Human acceptance must come from the user for the bound current artifact and code tree.

Verification claims name their practical limit: unit test, build, CI, merge, release, deployment and end-to-end evidence are distinct. Evidence applies only to the code, inputs and acceptance it actually covers. A delivered prerequisite, fix or rebase may invalidate a baseline even when spec bytes match. The program rechecks structural bindings; agents and reviewers remain responsible for deciding whether evidence substantively covers acceptance criteria and for reporting only what they verified.
