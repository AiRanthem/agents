# Project command contract

Run `<PYTHON> <installed-manage-workitems>/scripts/project.py --root <project> COMMAND`. `<PYTHON>` is the current workspace's prescribed Python 3 executable/environment; use that environment for every command and its returned continuation. Resolve the installed skill's physical path once. Git and [the declared Python dependencies](../scripts/requirements.txt) are required; enabled Aone also requires authenticated `a1`.

## Progress report

A request to report project progress or current status ends at one `progress` command. The [progress section](../SKILL.md#progress-report) is the complete instruction for writing that report. `progress` returns the lifecycle summary, publication recovery, and each item's stored predevelopment marker. A `blocked` or `partial` result follows the status table below.

When dependencies are missing, install them into the workspace-selected environment with `<PYTHON> -m pip install -r <installed-manage-workitems>/scripts/requirements.txt`. If that environment is missing or cannot install packages under its instructions, report the missing prerequisite rather than switching to system Python. The ordinary agent interface uses typed command options and Markdown files.

Ordinary work-item writes use the following `begin`/`finish` workflow. Authorized autonomous advancement uses the coordinator interface below and the same guarded workflow internally. Shared knowledge commands are direct typed CLI operations described in the operations table; they use returned body paths and hash guards and do not use `begin`.

## Fixed write workflow

1. Run `begin OP [ID]` with the requested operation's typed inputs.
2. Read every entry in the returned `read` payload completely. Read any required original instruction path returned for an external main workspace. Use only `editable` absolute paths for Markdown writes; the program supplies their initial content and publication destinations.
3. Only `ready` returns a `finish_command`; run it unchanged, including when `editable` is empty. The `finish` CLI accepts result/provenance options only for `design-review`: after assessment, add its actual `--result pass|fail --provenance SOURCE` to that returned base command. `development-finish` review evidence is supplied to `begin`, never added to the finish command.
4. Follow the returned status without expanding the workflow:

| Status | Action |
| --- | --- |
| `ready` | Read its inputs, edit its returned drafts and finish; a diagnostic status without an edit payload is reported as ready. |
| `published` | Report the completed checkpoint and end. |
| `no_op` | Report no change and end; there is no new publication. |
| `partial` | Execute only its `next_command` (resume of the retained operation), then apply this same status table. |
| `blocked` | For `code: stale_ticket`, execute only the returned `next_command` to begin the same operation with current inputs. For `code: stale_evidence`, the program returns no `next_command` or `finish_command`; obtain current authorization/review evidence and report the blocker. Otherwise report the exact blockers/missing facts and stop the affected operation. |

`status` reports current facts and the same fixed recovery branch. A successful autonomous checkpoint ends that operation, while the coordinator continues other ready work within the authorized scope. Do not create a replacement operation while an outcome is uncertain. Program-owned YAML, publication receipts, IDs, owner tokens, hashes, version increments, DAG checks and Git/Aone inspection are not agent work; the autonomy interface separately accepts actual host receipts captured by the coordinator. The JSON `apply` interface and lower-level runtime helpers are legacy diagnostics, not an alternative write route.

## Operations

`ID` accepts a full ID, hierarchy code, phrase or exact title. Ambiguity is reported with candidates. Use the returned full ID in later operations. Supply actual user decisions and evidence; a command option is an assertion whose truth the agent must establish.

| Operation | Typed inputs and Markdown purpose |
| --- | --- |
| `create` | `--title TITLE --slug SLUG`; optional `--parent ID`, `--repository ID`, `--kind development\|aggregate`, repeated `--depends-on ID` and `--delivery-required KIND`. Fill the returned requirement and context drafts. |
| `fix ORIGINAL` | `--title TITLE --slug SLUG`; fill a new requirement/context describing the defect and acceptance. Links to the delivered original and leaves its delivered state intact. |
| `requirement-update ID` | Edit the returned current requirement draft. |
| `design-update ID` | Edit the returned complete current design draft, only for requested design work. |
| `decision-record ID` | Replace the complete current decision Markdown in the returned draft, retaining effective decisions and removing superseded text; `--approval-source SOURCE` records actual user approval of the current design. |
| `design-review ID` | Begin without a result. An independent session reviews an unowned item directly. For an owned developing item, its owner registers an actual external review with paired `--reviewer-session SESSION --review-file FILE`; the source report must stay unchanged through publication, and the reviewer differs from author, approval session and registrar. Preserve the current owner and record reviewer/registrar separately; external identity and reviewed-target provenance are trusted owner assertions. Finish with the real `--result pass\|fail --provenance SOURCE` as declared in `finish_options`. Requires explicit ordinary review authorization or the autonomous bound-worker workflow. |
| `development-start ID` | `--base-ref REF --branch BRANCH --worktree RELATIVE_PATH` as required for the selected code development. Only explicit user authorization permits `--skip-design-review --approval-source SOURCE` for this unchanged contract. Publication establishes ownership before code edits. |
| `development-finish ID` | At `begin`, supply `--result pass\|fail --provenance SOURCE --reviewer-session SESSION --review-file FILE` from the actual independent reviewer; persist the review through the returned report draft, then run the returned finish command unchanged. These are required begin inputs, not finish options. |
| `delivery-record ID` | Repeated `--kind KIND --reference SOURCE` and `--provenance SOURCE`; fill the returned delivery report with actual obligation coverage. |
| `context-update ID` | Edit the returned current facts, verification and handoff draft. |
| `log-record ID` | Replace the complete current log/context Markdown in the returned draft. The program does not append machine-generated events. |
| `rename ID` | `--title TITLE`. |
| `dependency-update ID` | Repeated `--depends-on ID` for the requested prerequisite set. |
| `archive ID` | `--archived` or `--no-archived`; preserves identity, current state and dependency edges. Current pointer-bound evidence follows record retention rules. |
| `kind-update ID` | `--kind development\|aggregate`, with `--repository ID` when converting to development. A development item can become aggregate only after recorded cleanup is `done` and its worktree is absent. The program validates these structural conditions. |
| `cleanup-record ID` | `--cleanup-status pending\|done\|not_applicable --reference SOURCE`; record actual cleanup evidence after separately authorized cleanup. The default `--mode verify` checks actual removal; `--mode manual|skipped --approval-source SOURCE` records only the user's explicit cleanup disposition, without claiming a skipped removal happened. Explicit `--discard-development --approval-source SOURCE` with `--cleanup-status done --mode verify` also discards an unfinished recorded implementation after removal, retains its snapshot in the cleanup record, and invalidates prior base-bound review/waiver evidence; current implementation gates must be satisfied again. Ordinary cleanup preserves development metadata. |
| `knowledge-show ID` | Direct read-only command: `project.py --root ROOT knowledge-show ID`. Returns metadata/body/hash, a unique-per-call `body_file` path, exact guarded `update_command` and `remove_command`; an absent ID also returns absent guards and `create_required_flags`. It does not create the draft file and does not use `begin`. |
| `knowledge-update ID` | Write the complete UTF-8 Markdown body to returned `body_file` (create its parent directory if needed), then use returned `update_command` with its exact guards; append only intentional typed metadata options. Its guarded form is `project.py --root ROOT knowledge-update ID --body-file PATH --expect-metadata-sha256 HASH\|absent --expect-body-sha256 HASH\|absent`. Creating an entry also requires the returned `--repository --topic --summary --scope --kind fact\|inference\|search\|verification` values. Existing metadata is reused unless options are supplied. Repeated `--input KEY=VALUE` replaces the entire inputs mapping; repeated `--source PATH` replaces the entire sources list. Use `--clear-inputs` or `--clear-sources` to clear the mapping/list; each clear option is mutually exclusive with its corresponding repeated option. Repeated `--source-revision PATH=REVISION` and `--source-sha256 PATH=SHA256` set source metadata: each path must uniquely match a path in the current sources or the complete replacement list supplied by `--source`; an unlisted or ambiguous path is rejected. SHA256 values must be 64 lowercase hexadecimal characters. |
| `knowledge-remove ID` | Use only the returned `remove_command`, guarded by `--expect-metadata-sha256 HASH --expect-body-sha256 HASH`, to remove an explicitly obsolete/unneeded YAML/Markdown pair. Lack of an item pointer does not establish staleness. This does not use `begin`. Successful, pending or stale draft files are not automatically removed and remain uncommitted work. |

A requirement/spec change invalidates affected approval and review bindings. The program derives design versions from raw bytes: first design is version 1, a changed design increments once, identical bytes do not increment. It checks prerequisite delivery, open upstream fixes and current review/base/session bindings at each gated checkpoint, including checkpoints in an already active session.

## Autonomous advancement

Use `autonomy status SCOPE` or `autonomy authorize SCOPE --approval-source SOURCE [--skip-design-review] [--predevelop]`, where `SCOPE` is exactly one of `--all`, `--tree ID` (the selected item and its decomposition descendants), or repeated `--item ID`. Authorization records the actual user instruction for this scope. For a current actual user approval, it captures the full approved requirement, spec and decision under `approved_contract`; dispatch returns this snapshot for independent comparison after a derived revision. A derived approval does not invent a new user approval. `--skip-design-review` requires explicit user authorization; it does not waive approval of the initial contract or independent review of a derived revision. Mixed-scope authorization skips attempts or ownership whose liveness is unresolved, returns them in `blocked_items`, and authorizes the remaining items; it does not take over the blocked items.

`status`, `progress` and `autonomy status` refresh the exact remote authority and may fast-forward the management checkout. They need Git metadata write access, including `.git/project-publish.lock`; they are not local read-only queries. `host_permission_required` identifies the exact path and required access: use the harness permission mechanism for the same command, retaining the current attempt. Local `list`, `show` and `knowledge-show` remain available for read-only inspection; their results do not replace authoritative scheduling status.

`autonomy status` returns `items` with reasons and the disjoint collections `ready`, `blocked`, `running`, `awaiting_acceptance`, `awaiting_predecessor_delivery`, `accepted_awaiting_delivery` and `completed`. A ready item names `next_role` or `next_action: prepare` for opt-in predevelopment; running items retain their attempt/role/worker identity. `round_finished` means no ready or running item remains, not that every item was delivered. Blocked items do not stop unrelated ready items.

The trusted coordinator captures real host tool calls and passes their receipts through these commands; receipts are not worker-authored claims:

| Command | Captured inputs and result |
| --- | --- |
| `autonomy dispatch ID --role ROLE --receipt-file FILE` | `ROLE` is `design-review`, `implementation`, `code-review`, `fix`, `design-revision`, `baseline` or `rebase`. The last two reuse the implementer template and explicitly permit only the assigned isolated Git transformation. The spawn receipt includes `host`, `tool`, `worker_id` and nonempty `raw` captured native tool data; `call_id` is optional and supplied only when actually observable. The program binds a new attempt and returns its `input_binding`, `approved_contract`, current `read` payload and code context. |
| `autonomy resume ID --attempt ATTEMPT` | Continues the same coordinator's existing dispatch or captured result for its actual worker. Dispatch preparation settles its returned lower-level `next_command` before the continuation. A captured-result continuation recovers its selected journal itself; no new attempt or worker is created. Original contract, dirty snapshot and required read guards remain in force. Only final dispatch `ready` with `worker_paused: false` and the complete identity, binding and context releases the worker. Captured-result continuation reuses its signed local capture, original receipt/artifact bodies and result ticket, and recovers its exact journal before further publication; an already finalized same attempt returns `no_op` with `outcome: execution_completed`. |
| `autonomy result ID --receipt-file FILE` | The actual result receipt repeats the matching host, attempt, role, worker and input binding, and contains `outcome`, `report_file`, `terminal_status`, `descendants_stopped: true` and captured raw tool output associating this worker with its observed terminal state. Outcomes are `pass`, `fail`, `blocked`, `revised` or `contract-change`, subject to role checks. A verdict requires `terminal_status: completed`; an observed `failed` or `stopped` worker may only report `blocked`. A revised design supplies `candidate_file`; passing review of a derived revision additionally returns `contract_unchanged: true`. At initial capture, report/candidate paths must be actual regular files without symlinks; their persisted bodies and hashes govern continuation. A spawn receipt never establishes termination. |
| `autonomy retire ID --receipt-file FILE` | Ends an unusable current attempt only for the same coordinator and original worker/role/input binding. Capture an actual worker `terminal_status` (`completed`, `failed` or `stopped`) plus `descendants_stopped: true`; raw native data must associate the terminal state with this worker. It records lifecycle closure, accepts no stale verdict or approval, and blocks until the user explicitly starts advancement again. Unknown liveness, timeout and a new coordinator never authorize retirement. |
| `autonomy accept ID --approval-source SOURCE` | Records actual user acceptance for ordinary and autonomous items alike, without authorizing advancement. Requires current independent implementation review for a development item and no unresolved active worker. The binding includes current artifact inputs and code tree; changed user code requires a new independent review. For an already delivered item with recorded verified cleanup and an absent recorded code worktree, use its retained reviewed snapshot; only missing historical reads within that removed worktree are exempt, while current contract, project and ancestor instruction guards remain. Acceptance does not submit code or record delivery. |

The coordinator retains the returned attempt and input binding exactly. `raw` must contain a native identity matching `worker_id`; the program recursively recognizes `task_name`, `agent_id`, `agent_name`, `worker_id` and `target` fields. If the tool result omits identity, capture its actual arguments and result together, for example the real `arguments.target`. Keep an observable `call_id` only; never fabricate it or search private logs to recover one. Without it, provenance is the explicit local `coordinator-capture-sha256:<receipt hash>`, not a host call ID. Receipts are structurally checked against the current item, role, attempt, worker, contract, original required read hashes and dirty code input; writers may change their own code worktree, while reviews require unchanged inputs. They are captured by a trusted coordinator and have no host signature; structural checks cannot authenticate a dishonest coordinator. Never fabricate tool output, worker identity, provenance or user approval. Autonomous design review, development start and implementation review require their bound `--execution ATTEMPT` when using the ordinary workflow; the coordinator interface supplies this binding internally. Do not invent a parallel `begin` to bypass it.

Every partial or blocked dispatch/result checkpoint retains an exact `continuation_command`; dispatch also retains `worker_paused: true`. Captured-result checkpoints expose `stage_result_pending: true`; on `partial`, `next_command` is the same-attempt continuation, with the lower-level diagnostic recovery retained as `publication_next_command`. Before the first publication, result receipt and artifact bodies are saved in a signed program-owned `.project-local/autonomy-results/<attempt>` checkpoint. They are immutable persisted inputs; continuation does not reread their temporary source files. Confirmed pre-push rejection preserves the old journal and allows only fresh guard validation of the same captured result; any uncertain remote outcome retains its original journal and blocks new publication. Settling a lower-level publication alone does not complete the outer dispatch or result. Resume the retained attempt rather than calling dispatch or spawning another worker. Its read guards include original decisions and absence of optional instruction inputs; adding a previously absent instruction or changing a current decision invalidates the affected evidence. Source writers are conservatively recorded as contributors at dispatch, including workers that later fail or block, so they cannot review code they may have changed.

The runtime publishes project metadata and retains formal source changes for user inspection. Explicit `--predevelop` authorizes only its frozen snapshot publication and isolated Git transformation commits as specified below; other code commits/pushes require covering user instructions. Aggregate evidence assessment and delivery use the ordinary workflow; aggregates have no automatic worker stage.

Autonomous review freshness also compares the captured project configuration hash with the current project file. Recorded acceptance of a development item remains valid only while its independent review, original read guards and code binding remain current; dependency readiness rechecks these guards instead of trusting the stored accepted label. Verified-cleaned delivered items retain the same narrow historical-read exception.

## Predevelopment commands

Explicit `--predevelop` applies to the selected scope and does not imply initial design approval or human acceptance. Read the [predevelopment contract](../../advance-project/references/predevelopment.md) when enabled or resuming a marked item.

- `autonomy snapshot ID`: capture/resume a stable independently reviewed full source tree into a new immutable snapshot branch and publish it using the repository's actual ref mapping. Original source HEAD, index and working contents remain unchanged. The record retains frozen requirement/spec/decisions, project/repository identity, tree/commit/ref and authorization. A published snapshot is reusable while live prerequisite inputs change; its frozen identity is authoritative.
- `autonomy prepare ID`: when status returns `next_action: prepare`, pin the required prerequisite snapshot closure and create an isolated generation. The generation pins the fetched formal base as well as its prerequisite snapshots. Same-repository pins and that formal base must all be integrated before design review; foreign-repository pins are fixed external context. A baseline integration uses runtime role `baseline` with the existing implementer template. After all prerequisites have current human acceptance and actual delivery, the same command freezes the speculative version, retains its worktree, records the formal target and schedules `rebase` in another isolated generation. A ready dispatch returns `git_operation` and frozen `prerequisites` alongside the normal binding/read/code context.

A snapshot/prepare publication preserves its pending intent. Settle its returned lower-level publication command, then repeat the same snapshot/prepare command; never create a replacement generation or overwrite a divergent remote ref. Worker-stage partials continue through the normal attempt-bound `autonomy resume`. Only the controller calls project commands; Git-stage workers may commit in the bound isolated generation, never push.

Speculative Pass reports `awaiting_predecessor_delivery`, never acceptance or delivery. It may unlock further opted-in snapshot work but cannot unlock ordinary development. Formal convergence replays only the item's own delta from its frozen baseline onto the exact fetched formal target; fresh design and code reviews cannot be waived, even for unchanged trees. Afterwards the resulting uncommitted formal worktree may enter `awaiting_acceptance` normally. Frozen snapshot record pairs remain retained while referenced by snapshot roots; they are not pruned with superseded review reports.

## Reading and setup

`list --query TEXT --limit 20` is an example bounded diagnostic read; `--limit` defaults to 50. `show ID [--documents]` is also a bounded diagnostic read. These do not establish a live remote claim. V1 projects support diagnostic reading and `migrate`; ordinary work-item writes require v2. Shared knowledge commands are available through the typed command interface. Read [project context](project-context.md) for session and instruction boundaries.

`migrate` deterministically migrates schema and refreshes generated project instructions from installed sources. Use `migrate --dry-run` only when the user requests a preview. Repeat execution against identical source hashes returns `no_op`. See [upgrade-project](../../upgrade-project/SKILL.md).

After the user has selected the destination and exact storage authority, initialize using typed arguments:

```text
project.py init DESTINATION --id ID --name NAME --storage-url URL --storage-branch BRANCH --context-file BACKGROUND.md --publish
```

Code repository setup uses `--repository-id ID --repository-url URL --repository-base-ref REF`. Association uses `--main-workspace-id ID --main-workspace-name NAME --main-workspace-root ROOT`, optional `--main-workspace-url URL --main-workspace-ref REF`, `--main-workspace-context-file FILE` and `--worktrees-base BASE --worktrees-path RELATIVE_PATH`. Aone uses `--aone-space SPACE --aone-type TYPE --aone-category CATEGORY` and repeated `--aone-status LOCAL=REMOTE`. Supply only the user's actual configuration; unsupported required fields are reported by the program. Write background Markdown, not configuration JSON. The program renders templates, establishes the independent repository, validates the exact ref and publishes metadata. Without `--publish`, initialization is local preparation only. Record supplied requirements afterward through `begin create`.

`removal-plan` returns a program-owned exact local-removal manifest. After explicit authorization of that concrete manifest, `remove --manifest ID --confirm DIGEST` performs the guarded removal; see [delete-project](../../delete-project/SKILL.md).

`resume` is executed exactly as returned, including its identity file/session binding. It resumes an existing intent; it does not authorize takeover. Do not reconstruct it from local YAML or retry an uncertain external creation yourself.
