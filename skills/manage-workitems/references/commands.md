# Project command contract

Run the caller-supplied project command entrypoint, or use `<PYTHON> <installed-manage-workitems>/scripts/project.py --root <project> COMMAND` with a stable `PROJECT_SESSION_ID`. Callers may supply an opaque execution identity and a continuation command prefix to the shared CLI; the project schema and workflow stay shared. Execute returned continuation commands unchanged to preserve the command entrypoint and original operation provenance. `<PYTHON>` is the current workspace's prescribed Python 3 executable/environment; use that environment for every command and its returned continuation. Resolve the installed skill's physical path once. Git and [the declared Python dependencies](../scripts/requirements.txt) are required; enabled Aone also requires authenticated `a1`.

`project.py` in shared instructions is shorthand for this resolved entrypoint and its command prefix. Keep the caller's binding in initial calls and returned continuations; do not replace it with the shared fallback. `PROJECT_SESSION_ID` is the neutral protocol's stable session input, not an instruction to infer a platform identity.

## Progress report

A request to report project progress or current status ends at one `progress` command. The [progress section](../SKILL.md#progress-report) is the complete instruction for writing that report. `progress` returns the lifecycle summary, publication recovery, and current review/acceptance evidence. A `blocked` or `partial` result follows the status table below.

When dependencies are missing, install them into the workspace-selected environment with `<PYTHON> -m pip install -r <installed-manage-workitems>/scripts/requirements.txt`. If that environment is missing or cannot install packages under its instructions, report the missing prerequisite rather than switching to system Python. The ordinary agent interface uses typed command options and Markdown files.

Ordinary work-item writes use the following `begin`/`finish` workflow. Authorized autonomous advancement uses the coordinator interface below and the same guarded workflow internally. Shared knowledge commands are direct typed CLI operations described in the operations table; they use returned body paths and hash guards and do not use `begin`.

## Fixed write workflow

The command workflow and its write-path, draft-path and retry restrictions govern ordinary operations. Script blockers or defects use the separate [user-authorized manual recovery](recovery.md#user-authorized-manual-recovery) path, governed by the approved concrete repair, verified facts and actual permissions.

1. Run `begin OP [ID]` with the requested operation's typed inputs.
2. Read every entry in the returned `read` payload completely. Read any required original instruction path returned for an external main workspace. Use only `editable` absolute paths for Markdown writes; the program supplies their initial content and publication destinations.
3. Only `ready` returns a `finish_command`; run it unchanged, including when `editable` is empty. The `finish` CLI accepts result/provenance options only for `design-review`, `design-reuse` and `development-finish`: after assessment, add its actual `--result pass|fail --provenance SOURCE` to that returned base command. Only `design-review` may additionally declare `--contract-unchanged` and `--mechanical-correction`: the latter requires an authorized candidate mechanical correction and both flags with actual independent pass, as described below. The responsible agent/controller’s `design-reuse` applicability pass needs no new independent confirmation; a pending candidate’s independent pass separately requires `--contract-unchanged`. `development-finish` may bind an existing actual report/result at begin, or receive the actual report and declared result/provenance at finish.
4. Follow the returned status without expanding the workflow:

| Status | Action |
| --- | --- |
| `ready` | Read its inputs, edit its returned drafts and finish; a diagnostic status without an edit payload is reported as ready. |
| `published` | Report the completed checkpoint and end this operation; continue the authorized phase handoff. |
| `no_op` | Report no change and end this operation; continue the authorized phase handoff. There is no new publication. |
| `partial` | Execute only its `next_command` (resume of the retained operation), then apply this same status table. |
| `blocked` | For `code: stale_ticket`, execute only the returned `next_command` to begin the same operation with current inputs. For `code: stale_evidence`, the program returns no `next_command` or `finish_command`; obtain current authorization/review evidence and report the blocker. For other blockers, investigate the listed facts; use authorized manual recovery for a script defect or inconsistent state. Pause dependent writes while required evidence or authorization is missing. |

`status` reports current facts and the same fixed recovery branch. A successful autonomous checkpoint ends that operation, while the coordinator continues other ready work within the authorized scope. Do not create a replacement operation while an outcome is uncertain. Scripts ordinarily maintain YAML, publication receipts, IDs, hashes, version increments, DAG checks and Git/Aone inspection. Authorized recovery may correct them against actual evidence. Artifact commands separately accept actual completed reports and provenance. The JSON `apply` interface and lower-level runtime helpers are legacy diagnostics, not an alternative write route.

## Operations

`ID` accepts a full ID, hierarchy code, phrase or exact title. Ambiguity is reported with candidates. Use the returned full ID in later operations. Supply actual user decisions and evidence; a command option is an assertion whose truth the agent must establish.

| `create` | `--title TITLE --slug SLUG`; optional `--parent ID`, `--repository ID`, `--kind development\|aggregate`, repeated `--depends-on ID` and `--delivery-required KIND`. Fill the returned requirement and context drafts. With `--parent`, the parent must have a current independently passed spec routed to `split`; the returned additional `spec.md` draft inherits its complete design. Extract the child’s relevant approved contract, preserving shared constraints; children can proceed directly to their own review without a mandatory redesign stage. |
| `fix ORIGINAL` | `--title TITLE --slug SLUG`; fill a new requirement/context describing the defect and acceptance. Links to the delivered original and leaves its delivered state intact. |
| `requirement-update ID` | Edit the returned current requirement draft. |
| `design-update ID` | Optional `--author-session SESSION`; scoped contract-internal revisions use `--contract-unchanged` and need independent confirmation.  Edit the returned complete current design draft, only for requested design work. Publish only after actual user confirmation; publication attests approval and records its version-bound provenance. Optional `--next-action implement|split` selects the reviewed destination; use `split` for an oversized parent whose complete spec includes usable delivery stages and DAG. Changing the route invalidates review and increments the design version. After a failed pending-contract comparison, a contract-internal repair retains `derived_reuse_pending` and its original approval/assessment solely for further independent comparison; it never authorizes implementation or reuse before independent pass with contract-preservation confirmation. |
| `decision-record ID` | Replace the complete current decision Markdown in the returned draft, retaining effective decisions and removing superseded text; `--approval-source SOURCE` records actual user approval of the current design. |
| `validation-waiver ID` | `--gate GATE --approval-source SOURCE`; write the returned report with the actual explicit user decision, selected checkpoint, target and unverified limits. Records `result: skipped` with current contract/base/dependencies and original input guards; code-related skips additionally retain the current source snapshot. This is a scoped user decision, never an independent review or an executed check. See [user verification decisions](#user-verification-decisions). |
| `design-review ID` | Begin without a result; returned editable drafts include candidate `spec.md` and `report.md`. When a basis exists, `design_basis` returns its complete `review`, `approval`, `read` and `read_hashes`; a pending comparison must read that original contract/evidence, including after a failed comparison and subsequent repair. An independent session can perform and register a review directly. Mechanical candidate edits are permitted only under the [shared standard](../../review-design/references/implementable-gate.md#mechanical-corrections-and-authorship) with a genuinely approved contract; finish actual pass with `--mechanical-correction --contract-unchanged --provenance SOURCE`, retaining the original substantive authors and recording old binding, final candidate SHA and exact diff. Candidate edits lacking this declaration are rejected; substantive revisions use the separate author workflow. A registrar can register an actual external review with `--reviewer-session SESSION --review-file FILE`; the source report must stay unchanged through publication, and the reviewer differs from all recorded substantive design authors/revisers and the external-review registrar. Approval registration alone is not authorship. Record reviewer/registrar separately; external identity and reviewed-target provenance are truthful registrar assertions. Finish with the real `--result pass\|fail --provenance SOURCE` as declared in `finish_options`. Requires a published versioned spec carrying prior user approval and current provenance, plus authorized independent review intent. Bound `derived_reuse_pending` evidence from a failed applicability assessment retains genuine original approval/Pass for the independent comparison. A pending candidate needs the independent reviewer’s comparison with the original approved contract and actual `--contract-unchanged` confirmation with pass; it does not itself authorize implementation or a skip waiver. Requires explicit ordinary review intent, including natural language, or scoped autonomous advancement. Load `review-design` and its project mode in either ordinary route; `skill_instruction_paths` returns the original paths even when missing design input or reviewer independence blocks begin. |
| `design-reuse ID` | Begin without additional options, only when a genuine earlier independent design Pass exists. Read the returned `design_basis` (original review, approval and complete original read contents/hashes) and `current_target` (including `binding`, `read_hashes` and `authorization`). The authorized responsible agent/controller writes only the returned `report.md` assessment draft, and finishes with actual `--result pass\|fail --provenance SOURCE` as declared in `finish_options`. Pass confirms the approved contract and relevant assumptions remain unchanged and prior independent coverage still applies; it records carry-forward with the original reviewer, approval, provenance and binding plus the current binding, assessor and report. It is neither a new independent Pass nor a waiver. No prior Pass, a newer failed review or a pending user-owned contract decision prevents reuse. When equivalence or the impact of key assumptions cannot be established but genuine original approval/Pass exists, return fail and independently review the affected scope. The program retains `derived_reuse_pending` solely as candidate comparison evidence against the original approved contract, never as implementation eligibility or a skip waiver. No initial approval/Pass means no such pending evidence may be created. An identified material contract change instead uses the existing contract-change/user-approval route and clears the reuse basis. The program checks bindings and stale writes; it does not decide semantic equivalence. |
| `development-start ID` | Optional `--author-session SESSION` identifies the actual source author; `--base-ref REF --branch BRANCH --worktree RELATIVE_PATH` as required for the selected code development. Only explicit user authorization permits `--skip-design-review --approval-source SOURCE` for this unchanged contract. Aggregate and split-routed items cannot start source implementation. Publish the current development checkpoint before code edits. |
| `development-finish ID` | At `begin`, supply the actual `--reviewer-session SESSION`; optionally bind an existing review with `--review-file FILE --result pass\|fail --provenance SOURCE`. When opening the checkpoint before assessment, receive the actual report in its returned draft and pass the declared result/provenance to its finish command. |
| `delivery-record ID` | Repeated `--kind KIND --reference SOURCE` and `--provenance SOURCE`; fill the returned delivery report with actual obligation coverage. |
| `context-update ID` | Edit the returned current facts, verification and handoff draft. |
| `log-record ID` | Replace the complete current log/context Markdown in the returned draft. The program does not append machine-generated events. |
| `rename ID` | `--title TITLE`. |
| `dependency-update ID` | Repeated `--depends-on ID` for the requested prerequisite set. |
| `archive ID` | `--archived` or `--no-archived`; preserves identity, current state and dependency edges. Current pointer-bound evidence follows record retention rules. |
| `kind-update ID` | `--kind development\|aggregate`, with `--repository ID` when converting to development. A development item can become aggregate only after recorded cleanup is `done` and its worktree is absent. The program validates these structural conditions. |
| `cleanup-record ID` | `--cleanup-status pending\|done\|not_applicable --reference SOURCE`; record actual cleanup evidence after separately authorized cleanup. The default `--mode verify` checks actual removal; `--mode manual|skipped --approval-source SOURCE` records only the user's explicit cleanup disposition, without claiming a skipped removal happened. Explicit `--discard-development --approval-source SOURCE` with `--cleanup-status done --mode verify` also discards an unfinished recorded implementation after removal, retains its snapshot in the cleanup record, and invalidates prior base-bound review/waiver evidence; current implementation gates must be satisfied again. Ordinary cleanup preserves development metadata. |
| `knowledge-show ID` | Direct read-only command: `project.py --root ROOT knowledge-show ID`. Returns metadata/body/hash, a unique-per-call `body_file` path, exact guarded `update_command` and `remove_command`; an absent ID also returns absent guards and `create_required_flags`. It does not create the draft file and does not use `begin`. |
| `knowledge-update ID` | Write the complete UTF-8 Markdown body to returned `body_file` (create its parent directory if needed), then use returned `update_command` with its exact guards; append only intentional typed metadata options. Its guarded form is `project.py --root ROOT knowledge-update ID --body-file PATH --expect-metadata-sha256 HASH\|absent --expect-body-sha256 HASH\|absent`. Creating an entry also requires the returned `--repository --topic --summary --scope --kind fact\|inference\|search\|verification` values. Existing metadata is reused unless options are supplied. Repeated `--input KEY=VALUE` replaces the entire inputs mapping; repeated `--source PATH` replaces the entire sources list. Use `--clear-inputs` or `--clear-sources` to clear the mapping/list; each clear option is mutually exclusive with its corresponding repeated option. Repeated `--source-revision PATH=REVISION` and `--source-sha256 PATH=SHA256` set source metadata: each path must uniquely match a path in the current sources or the complete replacement list supplied by `--source`; an unlisted or ambiguous path is rejected. SHA256 values must be 64 lowercase hexadecimal characters. |
| `knowledge-remove ID` | Use only the returned `remove_command`, guarded by `--expect-metadata-sha256 HASH --expect-body-sha256 HASH`, to remove an explicitly obsolete/unneeded YAML/Markdown pair. Lack of an item pointer does not establish staleness. This does not use `begin`. Successful, pending or stale draft files are not automatically removed and remain uncommitted work. |

A requirement/spec byte change makes affected exact bindings stale; it does not by itself revoke semantic user approval. A material contract change invalidates the affected approval and independent coverage. A retained genuine independent Pass may support `design-reuse` only through a current applicability assessment; historical evidence alone never satisfies a current gate. The program derives design versions from raw bytes: first design is version 1, changed design bytes or a changed `next_action` increment once, identical bytes and route do not increment. It checks prerequisite delivery, open upstream fixes and current review/base bindings at each gated checkpoint, including checkpoints in an already active session.

## Single-machine operation

Operate on one local project in sequence: complete or recover the current operation before starting the next. Any local session may continue from the existing artifacts and operation records within the action's user authorization and actual permissions. Session IDs preserve genuine author/reviewer attribution and operation provenance. Read complete current contracts and applicable original instructions, bind assessments to stable input identities and report changes that affect their applicability.

Input-byte checks identify changes since a checkpoint opened; re-read changed inputs before starting a current checkpoint. Short-lived local transaction locks protect publication and recovery writes. An uncertain publication retains its exact recovery command and original intent; reconcile the actual remote outcome before continuing. Preserve local tickets, journals, useful code and unpublished drafts/reports with genuine attribution.

The current advancing agent manages native tasks and uses the existing local source and project artifacts. Published project state retains current artifacts and evidence; local source, bindings and credentials remain at their actual locations. Contract approval, acceptance, source publication, external actions and deletion retain their respective authorization boundaries.

## User verification decisions

The user may explicitly skip any verification checkpoint. Use `begin validation-waiver ID --gate GATE --approval-source SOURCE`, read the complete inputs, write its returned report and execute the returned finish command. Reuse covering explicit approval; a general request to advance or finish supplies no skip authorization. The record applies only while its contract, base, dependencies and required original inputs remain current. A changed code target requires renewed confirmation for code-related skips. Program records do not invent a successful test, independent reviewer, human acceptance or delivery evidence.

Built-in checkpoints are `design-review` (including design applicability/contract confirmation), `dependencies` (prerequisite delivery/acceptance and open fixes), `implementation-review`, `human-acceptance`, `merge-verification` and `delivery-evidence`. Use another descriptive gate name for an agent-run check such as `unit-tests` or `e2e`; honor its scope in execution and reports. A waived checkpoint remains visibly skipped. Skipping delivery verification still requires an explicit actual delivery declaration; it does not authorize source publication or fabricate merge/release evidence. Actual permissions, path/data safety, valid state structure, stale-write guards and recovery of uncertain external outcomes remain required.

`autonomy accept ID --approval-source SOURCE` records actual user acceptance of the current implementation. If current independent implementation review is missing, failed or stale, that explicit human acceptance may replace it with a content-bound `development-finish` record carrying `result: pass`, `approval_kind: human_acceptance` and the real user source/registrar. It is not independent review. Other design or convergence checkpoints remain unless separately explicitly skipped. Changes invalidate the previous acceptance; another actual user acceptance can cover the new target without first requiring an independent implementation review. This command also supports ordinary development without autonomous authorization.

## Autonomous advancement

Use `autonomy status SCOPE` and `autonomy authorize SCOPE --approval-source SOURCE [--skip-design-review]`, with exactly one of `--all`, `--tree ID`, or repeated `--item ID`. Scope hierarchy is separate from dependencies. Authorization records the actual user instruction, approved requirement/spec/decision and real approval provenance. Derived approval is never relabeled as user approval; pending comparison does not count as current approval. Explicit skip flags retain their separate authorization requirements. Authorization publishes the selected scope in one operation. `authorized` reports the scope after confirmed publication; an unresolved publication returns `pending_authorization` and exact recovery for that same scope.

`status`, `progress` and `autonomy status` refresh remote authority and may fast-forward the management checkout; they require Git metadata write access including `.git/project-publish.lock`. `host_permission_required` names the required access. Local `list`, `show` and `knowledge-show` remain available for diagnostic reads.

`autonomy status` derives `ready`, `blocked`, `awaiting_acceptance`, `accepted_awaiting_delivery` and `completed` from current artifacts. Ready entries identify `next_role`, `split`, `design_reuse_assessment` or `lifecycle_prepare`. `split` materializes an oversized parent’s current independent Pass into inherited child contracts and DAG; it never dispatches parent source implementation. Children enter their own review without mandatory redesign, and only actual blockers require supplemental design. The current advancing agent owns the native task tree. `round_finished` means no item is ready; actual delivery and native task completion retain their own evidence. Blockers do not stop unrelated ready items.

| Operation | Required evidence and result |
| --- | --- |
| `begin design-review ID --reviewer-session SESSION [--review-file FILE]` | Published versioned spec carrying prior user approval and current provenance, authorized independent real reviewer, complete original reads and a stable candidate. Finish with the actual result/provenance; required contract confirmation and mechanical-correction flags come from the reviewer. A report file is optional when opening the checkpoint before the review; when supplied its bytes remain guarded. |
| `begin design-update ID --author-session SESSION --contract-unchanged` | An authorized contract-internal revision retains real original user approval and records the revision ticket. It needs independent `contract_unchanged` confirmation before implementation. Material contract changes need user approval. |
| `begin development-start ID --author-session SESSION` | Prepares or resumes retained source under current design/dependency gates. Finish before source work. Every actual author, including failed/replacement writers, remains excluded from independent code review. Explicit scoped waiver uses the existing skip/approval-source options. |
| `autonomy complete ID --role implementation\|fix --report-file FILE --provenance SOURCE` | Actual completed work report and current contract/code binding. Requires the current development-start basis and guarded required reads. Saves report body/hash and exact implementation binding; it does not approve code. |
| `begin development-finish ID --reviewer-session SESSION [--review-file FILE]` | Independent actual review of the complete stable dirty code snapshot. Finish with actual pass/fail and provenance. Source changes during review are rejected; authors and registrar cannot be reviewers. |
| `autonomy accept ID --approval-source SOURCE` | Actual human acceptance of current contract and independently reviewed code. Changed code or review inputs require affected fresh evidence. Verified-cleaned delivered items use their retained reviewed snapshot and exempt only missing reads inside the removed worktree. It grants no delivery. |

Project state records scoped authorization, current content-bound artifacts, genuine evidence and author/reviewer attribution. The current advancing agent manages native task lifecycle and serial project progression. Ordinary registration uses project commands; script defects use [authorized manual recovery](recovery.md#user-authorized-manual-recovery). Never fabricate an actor, completed report, review or user approval. The controller checks actual target identity and registers evidence; agents remain responsible for truthful attribution and substantive assessment of reports.

Completed implementation/fix may retain code when only guarded `AGENTS.md` contents or presence changed. Its product records before/after hashes in `instruction_changes`; current design applicability or independent review, then independent code review under current original instructions, remain required. The unchanged completed code proceeds to code review after design coverage is current. Changed contract/context, unsafe paths and stale review inputs remain rejected. Completion is not a requirement to redevelop retained code; the current agent inspects it and fills demonstrated gaps.

A `partial` publication or signed workflow ticket returns its exact recovery command. Recover that immutable project transaction before fresh work. A stale checkpoint needs a fresh begin on current inputs, retaining actual source/report artifacts and reusable verification. Acceptance rechecks actual code and review/read bindings, including actual dependency acceptance and delivery. Source submission and cleanup remain separately authorized.

## Reading and setup

`list --query TEXT --limit 20` is an example bounded diagnostic read; `--limit` defaults to 50. `show ID [--documents]` is also a bounded diagnostic read. Authorized read-only investigation may use these reads. Read-only reviews use `context ID --role review-design|review-implementation`, which returns the selected primary documents with hashes and defers earlier review reports until after independent assessment. Read applicable original project/main-workspace/source instructions without `begin`; retain a separate temporary report with exact reviewed inputs. Official registration is a write operation and rechecks current evidence. V1 projects support diagnostic reading and `migrate`; ordinary work-item writes require v2. Shared knowledge commands are available through the typed command interface. Read [project context](project-context.md) for session and instruction boundaries.

`migrate` deterministically migrates schema and refreshes generated project instructions from installed sources. Use `migrate --dry-run` only when the user requests a preview. Repeat execution against identical source hashes returns `no_op`. See [upgrade-project](../../upgrade-project/SKILL.md).

Migration saves its operation, exact writes/checks and validation result before publication, including failures before a publication journal exists. A partial migration returns `resume --migration OPERATION`; execute it unchanged. Recovery preserves that candidate, reconciles authoritative publication/sync state and verifies the original changes or submits the same guarded intent when publication never started. `status` exposes pending migration operations. `resume` returning an empty `no_op` proves no recovery action occurred, not migration completion: reconcile via `status`, follow pending recovery, and only after confirming no pending transaction rerun the still-authorized `migrate`. Report update need, local application, commit/push and remote verification separately.

After the user has selected the destination and exact storage authority, initialize using typed arguments:

```text
project.py init DESTINATION --id ID --name NAME --storage-url URL --storage-branch BRANCH --context-file BACKGROUND.md --publish
```

Code repository setup uses `--repository-id ID --repository-url URL --repository-base-ref REF`. Association uses `--main-workspace-id ID --main-workspace-name NAME --main-workspace-root ROOT`, optional `--main-workspace-url URL --main-workspace-ref REF`, `--main-workspace-context-file FILE` and `--worktrees-base BASE --worktrees-path RELATIVE_PATH`. Aone uses `--aone-space SPACE --aone-type TYPE --aone-category CATEGORY` and repeated `--aone-status LOCAL=REMOTE`. Supply only the user's actual configuration; unsupported required fields are reported by the program. Write background Markdown, not configuration JSON. The program renders templates, establishes the independent repository, validates the exact ref and publishes metadata. Without `--publish`, initialization is local preparation only. Record supplied requirements afterward through `begin create`.

`removal-plan` returns a program-owned exact local-removal manifest. After explicit authorization of that concrete manifest, `remove --manifest ID --confirm DIGEST` performs the guarded removal; see [delete-project](../../delete-project/SKILL.md).

In ordinary recovery, execute `resume` exactly as returned with its `--ticket`, `--journal`, `--item` or `--migration` selector. Any local session may resume the recorded transaction while preserving its original provenance and current input checks. Do not reconstruct it from local YAML or retry an uncertain external creation yourself.

`show.workflow_gates` reports current approval and operation-specific contract gates using the checkpoint predicates. Top-level `status: ready` means the diagnostic query succeeded; legacy `readiness` covers dependency delivery and open fixes only. Implementation requires the applicable approval/review gates, current input bindings and covering authorization. Successful design/decision/review checkpoints return the next authorized destination and contract identity; a published versioned spec carrying prior user approval and current provenance can enter its authorized independent review.

## Managed resource lifecycle

Read [resource lifecycle](resource-lifecycle.md) before these direct typed commands. They use the program's guarded publication path, not Markdown `begin`/`finish`. Actual policy/replan/discard sources remain assertions grounded in user instructions.

| Command | Purpose |
| --- | --- |
| `lifecycle status [ID]` | Local diagnostic resource inventory, retention reasons and pending intents. It performs no collection. |
| `lifecycle policy ID --approval-source SOURCE [--grace-days 7 --max-retained 2 --max-snapshots 20]` | Adopt the explicitly authorized internal preservation-publication and GC policy. |
| `lifecycle handoff ID --mode manual\|autonomous --approval-source SOURCE` | Record the authorized execution-mode change while preserving current source, reviews and recovery evidence. This grants no GC policy or initial design approval. |
| `lifecycle replan ID --approval-source SOURCE [--mode manual\|autonomous]` | Preserve old source and retire its generation/authorization; record the authorized execution-mode change. |
| `lifecycle prepare ID` | Continue the same replacement intent with current prerequisite gates; bind a fresh isolated baseline after actual prerequisite acceptance and delivery. Preparation leaves approval, independent review and implementation gates intact. |
| `lifecycle adopt ID --worktree RELATIVE_PATH` | Preserve and register the exact already-recorded legacy retained source for later migration/disposition. It does not claim an unregistered path. |
| `lifecycle dispose ID --generation GENERATION --disposition migrated\|discarded --reference SOURCE [--approval-source SOURCE]` | Register actual migration-review evidence or explicit user discard of a unique retained source; never claim cleanup occurred. |
| `lifecycle plan ID` | Persist current resource relationships/release times and an exact collection intent, returning its resources, blockers and `collect_command`. |
| `lifecycle collect ID --intent INTENT --confirm DIGEST` | Execute/resume only the returned exact intent under adopted policy; settle lower publication recovery first. |

A blocked collection retains `continuation_command` for the same intent after the stated blocker is resolved; it authorizes neither a new manifest nor broader cleanup. An uncertain archive publication retains the same `transition` checkpoint; inspect `lifecycle status` and preserve the original operation inputs. A mode switch preserves actual prerequisite, review and recovery gates.
