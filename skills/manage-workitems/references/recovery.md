# Restore and recover a project

Cloning the exact configured project branch restores published current requirements, design, current pointer-bound evidence and project state. Git history provides prior versions. It does not restore machine-local bindings, tools, credentials, unpublished code or the separate main workspace. Start the agent at the project root and read its generated `AGENTS.md`. Install missing shared skills through their installation contract.

Project recovery has two paths: ordinary command recovery and concrete manual repair explicitly authorized by the user. The ordinary path below uses command-selected writes, returned draft paths and guarded continuations. For script blockers, crashes or inconsistent recovery instructions, use [user-authorized manual recovery](#user-authorized-manual-recovery), which defines the scope, evidence and safeguards for direct file/state correction and script repair.

## Ordinary command recovery

Use `project.py status` for the reported facts. For an interrupted operation, run only its returned resume command and then follow the [status table](commands.md#fixed-write-workflow). Preserve local tickets, operation records and recovery files. Investigate unresolved publication or backend facts. An uncertain create requires reconciliation before retrying; a timeout does not establish the outcome.

Autonomous advancement resumes from `autonomy status` for the selected scope and current artifacts. Any local session may continue from those artifacts and existing operation records within the action’s authorization and actual permissions. Complete or recover the current operation before starting the next. The current agent manages native tasks, retains local source and reports, preserves genuine author attribution and rechecks current evidence applicability before opening the next checkpoint. Do not invent completion or approval. Contract changes need the current user's decision; design applicability uses the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage).

The program reports confirmed failures before any push separately from unresolved publication outcomes. These rejected attempts do not block `status`; their local intent remains available. A retained candidate with an uncertain push remains subject to publication recovery checks.

Migration retains its original writes, byte guards, paths and validation result in a local operation before publishing. Use its returned `resume --migration OPERATION`, including after a permission failure before a publication journal was created. Recovery verifies original changes against authoritative state or resumes the same intent. An empty `resume no_op` establishes only that no recovery action occurred. If changes were pending, reconcile through `status`; follow outstanding recovery, or rerun the still-authorized `migrate` after the program confirms no pending transaction. Validation success alone does not establish local application, commit/push or verified remote publication.

Schema-1 projects permit diagnostic reads and explicit `migrate`. `upgrade-project` runs that deterministic migration/instruction refresh while preserving current artifacts and genuine evidence; unresolved sync blocks it with concrete facts. Source hashes make repeat execution a no-op. The agent writes complete current business instructions from the returned required sources and other relevant original documents when the program reports that input is needed. Existing user-maintained authority remains valid; migration does not routinely request reapproval. If the source leaves a real business change or permission unknown, report that specific gap. Migration does not retain obsolete prompts as active project content; earlier versions remain in Git history.

The program returns required original main-workspace instruction paths. Read them before dependent work. If a binding, original instruction or code location is missing, establish its actual location or report the missing input; a concrete layout repair uses the established location and covering authorization under manual recovery. Changing a binding does not move dirty worktrees; recover them from their actual source location. Follow [the command contract](commands.md): `status: blocked` with `code: stale_ticket` returns the sole allowed restart command, while `code: stale_evidence` is blocked without a continuation command until current authorization/review evidence is supplied.

Project removal uses [delete-project](../../delete-project/SKILL.md) with an exact authorized local manifest. It preserves remote branches and Aone history by default, along with main-workspace roots, shared environments, sibling projects and unrelated worktrees. Unpublished content and uncertain external outcomes require preservation or resolution before removal; removal is not a recovery shortcut.

Ordinarily recover project publications and signed begin/finish tickets using their exact returned command, preserving their guarded intent. If recovery itself is defective, use the authorized manual-recovery contract to reconcile actual outcomes before correcting that intent. A stale checkpoint requires fresh input validation while retaining completed source and reusable verification. Use `autonomy complete` for actual completed implementation/fix under its current development basis. Guarded instruction changes retain completed source for current design coverage and independent code review. Keep useful code and reusable verification across retries. Native task lifecycle remains with the advancing agent, outside project state.

## User-authorized manual recovery

When a project script blocks, crashes or gives inconsistent recovery instructions, investigate against the approved contract and verified facts. With explicit user authorization covering the concrete repair, manually correct project files/state and repair the responsible scripts. This path permits the approved direct edits and diagnostic checks across project skills and generated instructions; its safeguards below govern those repairs. The approved repair may proceed directly under actual permissions while the broken automation remains unavailable.

Before requesting authorization, inspect the failing command/output, affected original state, approved contract, relevant code and actual source/review/publication evidence. Distinguish a script defect or inconsistent stored state from a real unmet requirement. Prepare the affected items/files, intended before/after state, script correction and verification so the user can approve a concrete repair. Reuse prior explicit authorization if it already covers that repair; a general instruction to advance or this policy alone does not approve future state edits. A legitimate unmet checkpoint requires its actual evidence or a separately authorized scoped waiver; preserve its real verification status.

After approval, preserve the original files and any unpublished source/reports in a recoverable copy or Git history, retain the current operation record and recheck the approved target. Make the smallest coherent state and script corrections within the authorized scope before resuming serial progression. During autonomous advancement, the controller integrates the diagnosis and repair evidence from stage executors. Use genuine actor identities and preserve input bindings and publication recovery records. Reconcile uncertain external publication against actual remote facts before replacing a transaction; do not discard pending journals or credentials merely to clear a block. Actual permissions, data protection and separately authorized source publication, external actions and deletion remain in force.

Preserve truthful authorship, approvals, review independence, acceptance and delivery. Invalidate bindings whose inputs changed; retain applicable genuine evidence. Record the actual authorization source, cause, changed paths and before/after facts, retained recovery location and verification in the existing project context/log or recovery record; if its writer is broken, the authorized manual edit may record it there. Use that existing record and the actual authorization even while its writer remains unavailable.

Check the repaired boundary with focused tests and state/source evidence, and rerun the relevant command when usable. Report what was corrected, what was verified and any remaining script failures; use direct evidence for checks that still cannot run. Resume the authorized workflow from the reconciled facts when its relevant requirements are established. If a consequential fact or required authorization remains unresolved, pause only dependent writes and continue unaffected work. Do not repeatedly run the same unchanged failing command or require the user to perform the repair manually.
