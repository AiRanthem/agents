# Restore and recover a project

Cloning the exact configured project branch restores published current requirements, design, current pointer-bound evidence and project state. Git history provides prior versions. It does not restore machine-local bindings, tools, credentials, unpublished code or the separate main workspace. Start the agent at the project root and read its generated `AGENTS.md`. Install missing shared skills through their installation contract.

For ordinary recovery, use `project.py status` for the reported facts. If a script blocks or malfunctions, use [user-authorized manual recovery](#user-authorized-manual-recovery), the exception to the command-only and stop/retry restrictions in this document. For an interrupted operation, run only its returned resume command and then follow the [status table](commands.md#fixed-write-workflow). Preserve local identity and recovery files. Investigate unresolved ownership, publication or backend facts. Use the authorized manual-recovery contract when scripts cannot reconcile them; never blindly repeat an uncertain create or assume a timeout releases ownership.

Autonomous advancement resumes from `autonomy status` for the selected scope and current artifacts. Authorized reading, investigation and read-only review need no takeover. Immediately before starting a project write operation or shared source modification, check the owner under [control-claim takeover](commands.md#control-claims-and-takeover). If another owner holds the item, pause those writes and ask the user whether to take over; continuation authorization alone is insufficient. Begin writes only after explicit approval and successful transfer. The current agent manages executors and source coordination; after approved transfer, an inaccessible old host or worker does not itself block continuation. Keep code, reports and genuine author attribution, then open current ordinary checkpoints. Do not invent completion or approval. Contract changes need the current user's decision; design applicability uses the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage).

The program reports confirmed failures before any push separately from unresolved publication outcomes. These rejected attempts do not block `status`; their local intent remains available. A retained candidate with an uncertain push remains subject to publication recovery checks.

Migration retains its original writes, byte guards, paths and validation result in a local operation before publishing. Use its returned `resume --migration OPERATION`, including after a permission failure before a publication journal was created. Recovery verifies original changes against authoritative state or resumes the same intent. An empty `resume no_op` establishes only that no recovery action occurred. If changes were pending, reconcile through `status`; follow outstanding recovery, or rerun the still-authorized `migrate` after the program confirms no pending transaction. Validation success alone does not establish local application, commit/push or verified remote publication.

Schema-1 projects permit diagnostic reads and explicit `migrate`. `upgrade-project` runs that deterministic migration/instruction refresh while preserving active owners and their claims; unresolved sync blocks it with concrete facts. Source hashes make repeat execution a no-op. The agent writes complete current business instructions from the returned required sources and other relevant original documents when the program reports that input is needed. Existing user-maintained authority remains valid; migration does not routinely request reapproval. If the source leaves a real business change or permission unknown, report that specific gap. Migration does not retain obsolete prompts as active project content; earlier versions remain in Git history.

The program returns required original main-workspace instruction paths. Read them before dependent work. If a binding, original instruction or code location is missing, establish its actual location or report the missing input; a concrete layout repair needs covering authorization under manual recovery, not a guessed path. Changing a binding does not move dirty worktrees or transfer a claim. Follow [the command contract](commands.md): `status: blocked` with `code: stale_ticket` returns the sole allowed restart command, while `code: stale_evidence` is blocked without a continuation command until current authorization/review evidence is supplied.

Project removal uses [delete-project](../../delete-project/SKILL.md) with an exact authorized local manifest. It preserves remote branches and Aone history by default, along with main-workspace roots, shared environments, sibling projects and unrelated worktrees. Unpublished content and uncertain external outcomes require preservation or resolution before removal; removal is not a recovery shortcut.

Ordinarily recover project publications and signed begin/finish tickets using their exact returned command, preserving their guarded intent. If recovery itself is defective, use the authorized manual-recovery contract to reconcile actual outcomes before correcting that intent. A stale checkpoint requires fresh input validation, not a new implementation. Use `autonomy complete` for actual completed implementation/fix under its current development basis. Guarded instruction changes retain completed source for current design coverage and independent code review. Keep useful code and reusable verification across retries. Native task lifecycle remains with the advancing agent, outside project state.

## User-authorized manual recovery

Project scripts are the ordinary automation path, not an authority above the approved contract and verified facts. When a script blocks, crashes or gives inconsistent recovery instructions, the agent may investigate and, with explicit user authorization covering the concrete repair, manually correct project files/state and repair the responsible scripts. This exception applies to the command-only write rules, returned-path restrictions and stop/retry rules in project skills and generated instructions. It does not require adding a bypass flag or making the broken command pass before recovery can begin.

Before requesting authorization, inspect the failing command/output, affected original state, approved contract, relevant code and actual source/review/publication evidence. Distinguish a script defect or inconsistent stored state from a real unmet requirement. Prepare the affected items/files, intended before/after state, script correction and verification so the user can approve a concrete repair. Reuse prior explicit authorization if it already covers that repair; a general instruction to advance or this policy alone does not approve future state edits. A legitimate unmet checkpoint needs its actual evidence or a separately authorized scoped waiver, not a fabricated success.

After approval, preserve the original files and any unpublished source/reports in a recoverable copy or Git history, check for competing writers and recheck that the approved target is unchanged. Make the smallest coherent state and script corrections within the authorized scope. The project owner/controller owns these writes during autonomous advancement; stage executors return the diagnosis and proposed repair to it. Repair a broken ownership-transfer mechanism only with explicit approval for that transfer, fencing the previous claim and coordinating actual writers. Never borrow another actor's identity or token. Reconcile uncertain external publication against actual remote facts before replacing a transaction; do not discard pending journals or credentials merely to clear a block. Actual permissions, data protection and separately authorized source publication, external actions and deletion remain in force.

Preserve truthful authorship, approvals, review independence, acceptance and delivery. Invalidate bindings whose inputs changed; retain applicable genuine evidence. Record the actual authorization source, cause, changed paths and before/after facts, retained recovery location and verification in the existing project context/log or recovery record; if its writer is broken, the authorized manual edit may record it there. No special new record format or successful invocation of the broken writer is required.

Check the repaired boundary with focused tests and state/source evidence, and rerun the relevant command when usable. Report what was corrected, what was verified and any remaining script failures; use direct evidence for checks that still cannot run. Resume the authorized workflow from the reconciled facts when its relevant requirements are established. If a consequential fact or required authorization remains unresolved, pause only dependent writes and continue unaffected work. Do not repeatedly run the same unchanged failing command or require the user to perform the repair manually.
