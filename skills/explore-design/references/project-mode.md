# Project design ownership

Read [shared project context](../../manage-workitems/references/project-context.md) and the [fixed command workflow](../../manage-workitems/references/commands.md). These project write instructions apply to the controller or an ordinary authorized project session, never a delegated stage executor.

During autonomous advancement, use the [controller’s ordinary candidate checkpoint workflow](../../advance-project/references/coordinator.md) to publish executor candidates and preserve their actual author/contract bindings; do not start a second ordinary design checkpoint.

For ordinary authorized design work, run `begin design-update ID`, read the complete returned requirement/spec and original instruction inputs, edit only the returned Markdown draft, then execute the exact returned `finish_command` and fixed status branch. The spec is the sole complete current Why/What document; keep machine-status frontmatter out of it. Use `decision-record` for the complete current decision document, retaining effective decisions and real approval provenance while removing superseded statements. The program owns versions, approval bindings and review state; exploration cannot establish a review pass. The controller does not perform an autonomous executor's missing design work or invent approval provenance. After an independent failure of a `derived_reuse_pending` comparison, a contract-internal `design-update` repair preserves that pending comparison and its genuine original approval/assessment, bound to the repaired candidate. Return it for independent review with actual contract-preservation confirmation; the failed review prevents applicability reuse, implementation and waiver-based bypass.

Keep design within the requested scope. Explicit prerequisite assumptions may be recorded while preparing designs early. When prerequisites are actually delivered, compare their relevant behavior with the design assumptions and prior independent coverage under the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage); independently review only invalidated coverage. Direct requested decomposition may produce requirement children without a spec. A simple requirement bypasses review only through an explicit scoped user waiver at `development-start`.

Changed bytes need current guarded bindings without automatically revoking semantic user approval. A material revision invalidates its affected previous review coverage. The program removes the superseded current review record, while Git history preserves prior versions. Do not carry `implementable` into a changed contract.

In native Plan, perform read-only exploration and use [host-mode handoff](host-modes.md); no project checkpoint or document write is permitted. In Agent mode, use the program-owned spec and approval workflow instead of creating a second design document. Complete the design approval handoff in the shared discussion rules: identify the current contract/version, reuse covering approval or present the complete candidate for the user’s decision, then record actual approval against the unchanged target. Report pending user approval distinctly from pending independent review. The author/controller retains this responsibility across published design and decision checkpoints.

Ordinary project design does not invoke `$review-design` without an explicit request. Within authorized `$advance-project`, the controller schedules the design-review stage without another permission or separate user session. An executor returns a candidate and report under [stage executor](../../advance-project/references/stage-executor.md); it does not run `begin`, `finish`, decision recording, project Git or Aone operations, or write official project documents.
