# Implementable criteria

Use this standard for explore-design's completeness reflection and review-design's independent assessment. Apply the attribution, severity and Pass principles of the [implementation review standard](../../review-implementation/references/review-standard.md) to the design being reviewed; its code-specific execution gates remain with implementation review. Pass means adequate review found no blocking problem introduced by the proposed change, including an unmet requirement assigned to it. It does not require zero findings or a defect-free design.

## Scope and evidence

Identify the approved requirements, current design and task's established integration baseline or existing system. An earlier revision of this same proposal is not a baseline that turns its unresolved defects into pre-existing warnings. Review the affected outcome/scope, end-to-end behavior, failure/lifecycle, safety/compatibility, feasibility/dependencies, observable acceptance and implementation cost at a depth justified by the change. These are coverage dimensions, not separate certification gates. Keep the coverage mapping private; report material findings, essential gaps and relevant evidence without requiring a per-row proof table or new spec sections.

Attribute each candidate before assigning acceptance impact:

- **Introduced or assigned to this change:** Show new faulty behavior, an incremental regression, or an unmet explicit requirement assigned to this design. For an existing problem made worse or newly reachable, report only the added impact and causal link.
- **Pre-existing:** A baseline problem with no demonstrated new impact is a separate warning. It does not affect Pass, require a waiver or become a mandatory fix for this change, regardless of severity. If fixing it is an explicit requirement of this change, assess that unmet requirement instead.
- **Attribution unresolved:** State the uncertainty and investigate when it could materially affect this change. Only a concrete gap in essential assessment can prevent Pass; an unrelated unknown cannot.

For each retained finding, establish severity, location, trigger, expected versus proposed behavior, consequence, violated requirement or repository rule, evidence of introduction, and meaningful uncertainty. Trace the relevant path and try to disprove it against surrounding safeguards; merge duplicate symptoms under the supported cause. A concern about a possible bad implementation is not a design defect when the contract already defines the correct outcome and feasible internal choices remain available.

## Mechanical corrections and authorship

A mechanical correction has one remedy determined by the approved contract or primary evidence, needs no design choice, and changes no behavior, interface, guarantee or acceptance criterion. Examples include a spelling/formatting error, a broken reference with a uniquely established destination, or synchronizing an already-settled symbol. A missing design decision, an ambiguous intended behavior or a changed promise is not mechanical.

Do not classify a mechanically correctable issue as blocking. When candidate writes are authorized, the reviewer may correct it directly, record the exact diff, determining evidence and preservation of the contract, then assess the final exact candidate in the same round. Such a correction is not substantive design authorship and does not require another author, reviewer or approval round. The reviewer must still be independent of the original substantive authors; an author cannot relabel its own design as mechanical to review it. Actual user approval covering the unchanged contract and the final exact candidate identity remain required; a byte change alone does not revoke that semantic approval. Optional polishing remains optional. When no candidate write is permitted, report the supported correction without bypassing host or path permissions; read-only planning remains read-only.

Substantive design authorship means establishing or changing design decisions or consequential content beyond these mechanical corrections. Authorship accumulates across the design’s versions: authors of the original design and every substantive revision remain in the author set even after another author changes it again. None can independently pass a later version of that design. Only an evidenced mechanical correction under this rule adds no substantive author. Substantive blocking corrections go to a separate author/revision worker, followed by affected independent review.

## Reuse independent coverage

The first independent review covers the complete design against original requirements and relevant repository evidence. Later assessment reuses still-valid coverage and examines the delta, unresolved findings and affected interactions. Prefer the original reviewer while it remains available and did not substantively author or revise any version of that design; replacing a context is not an independence requirement.

Material changes to requirements, public or stored interfaces, guarantees, acceptance criteria, or key dependency assumptions require independent review of their affected scope. Resolve user-owned contract changes through actual user approval before affected work continues. Broaden to a full review only when the impact cannot be bounded or prior coverage is broadly invalidated.

Equivalent wording or document organization, unrelated context changes and implementation corrections that preserve the approved contract do not by themselves require a full design review. A changed source/dependency baseline, including actual prerequisite delivery and formal predevelopment convergence, requires a design-applicability assessment: compare changed assumptions and interfaces with the original contract and prior coverage, then independently review only invalidated coverage. Independent code review of the formal result remains required.

Record the exact earlier review identity and inputs, current artifact identities, inspected changes, preserved coverage, affected interactions and remaining gaps. For managed projects, an authorized trusted owner/controller may assess applicability through `design-reuse` under the [command contract](../../manage-workitems/references/commands.md). This carries forward a genuine original independent conclusion and its approval/provenance to current bindings only when the approved contract and relevant assumptions remain unchanged; it does not produce a new independent Pass or waive review. Missing prior Pass, a newer failed review or a pending user-owned contract decision prevents reuse. If applicability cannot be established, record fail and independently review the affected scope. With genuine original approval and Pass, `derived_reuse_pending` may preserve the candidate and original approved contract for that comparison alone; it grants no implementation eligibility or skip waiver. An owner/controller’s applicability pass needs no new independent confirmation. Only the pending candidate’s independent passing reviewer must actually confirm that it preserves the original approved contract (`--contract-unchanged` for ordinary review, `contract_unchanged: true` in an autonomous receipt). Missing initial approval/Pass cannot create this pending evidence. A failed independent comparison and subsequent authorized contract-internal repair retain only the original comparison basis and pending status; the failure blocks reuse, and the repaired candidate still requires independent pass with actual contract-preservation confirmation. An identified material contract change clears the reuse basis and requires actual user approval and affected independent review. Byte-binding staleness does not itself revoke semantic user approval; current applicability still needs a guarded binding. The program validates identities, hashes and stale writes, not semantic equivalence. Never copy an old Pass to new hashes, fabricate reviewer confirmation or treat the controller's assessment as independent review.

## Severity and acceptance impact

Apply severity to substantive introduced or assigned findings remaining after permitted mechanical correction, using the same scale as implementation review:

| Severity | Design impact | Review consequence |
| --- | --- | --- |
| Critical | Likely security compromise, data loss or broad outage. | Blocks Pass. |
| High | Missing or incorrect required behavior, unintended scope, serious regression or an infeasible essential promise. | Blocks Pass. |
| Medium | A realistic design defect or substantial maintainability problem. | Normally fix before Pass; an exception needs explicit user acceptance and must not violate a governing requirement. |
| Low | A supported non-blocking improvement. | May remain with Pass; keep these few. No waiver, spec edit or re-review is required. |

Do not report cosmetic preferences or speculative risks. Private helpers, file layout, pseudocode, test commands, rollout procedures, missing reflection paperwork and opportunities to further optimize an adequate design do not by themselves block Pass. Required public/stored contracts, safety guarantees and consequential behavior must still be settled; do not disguise those gaps as implementation details. Existing authoritative requirements can establish an outcome without repeating it in every spec section. Do not require implementation or production validation merely to approve a design; seek focused evidence for a genuinely uncertain essential capability.

A necessary user decision or essential evidence gap is not a demonstrated defect. Explain the exact missing input and why a consequential conclusion depends on it. Ordinary implementation choices and nonessential uncertainty remain compatible with Pass. Preserve approved limitations consistent with governing requirements; neither author nor reviewer may waive a required guarantee.

Consolidate established blockers after reviewing the available scope. Re-review fixes and affected assumptions, preserving valid coverage. Do not reopen settled issues without new evidence or keep adding unrelated low-value comments after blockers are resolved.

## Verdict and official status

Return **Independent review passed** when adequate coverage and required independence found no blocking introduced or assigned problem and no essential assessment gap remains. Low findings, pre-existing warnings and implementation reminders may coexist with Pass. Return **Design changes required** for a concrete blocking finding; return **Unable to conclude** for a missing essential contract, stable target, independence, decision or evidence. If a blocker is demonstrated, report it and disclose additional gaps rather than hiding it behind uncertainty.

Bind the report to the exact requirement/design identity and source/dependency baseline. Separate blocking findings, non-blocking findings, baseline warnings and essential gaps as applicable; state the acceptance impact explicitly. A nonempty findings list is not a failed review. If only non-blocking issues remain, return `pass` on the final exact candidate, recording any permitted mechanical corrections; do not turn optional polishing into `revised`, another approval request or another design-review round.

An independent quality pass is only one part of official `implementable` status. Formal design publication attests prior user approval; do not impose separate approval registration or renewed confirmation before review or status writeback. Recording that status requires valid reviewer/authorship and current input bindings, plus successful persistence through the active mode's authorized workflow. Follow [execution modes](execution-modes.md) or [project mode](project-mode.md); a stage executor returns its result to the controller and never writes official status. Read-only planning never writes status.

An independent assessment must cover the current contract and relevant assumptions through retained coverage and any required incremental review. A substantive author of any version of this design cannot independently pass the candidate; permitted mechanical corrections retain independence. `Implementable` does not establish implementation authorization, prerequisite delivery, production correctness or human acceptance. Ordinary project implementation still requires actual predecessor delivery; authorized [predevelopment](../../advance-project/references/predevelopment.md) follows its frozen-input workflow, design-applicability assessment and independent formal code review after rebase.
