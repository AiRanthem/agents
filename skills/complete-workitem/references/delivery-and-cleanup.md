# Actual delivery and cleanup

Apply explicit [user verification decisions](../../manage-workitems/references/commands.md#user-verification-decisions) before the default gates below. Actual human acceptance may replace independent implementation review with an attributed pass. Any verification checkpoint may be explicitly skipped for the specified scope; preserve its user source and report the skipped verification rather than inventing evidence. Source publication, cleanup actions, ownership and transaction safety retain their separate authorization.

Use the project entrypoint resolved by the [fixed command contract](../../manage-workitems/references/commands.md), preserving the caller's binding. Record actual obligation coverage through `begin delivery-record ID --kind KIND --reference SOURCE --provenance SOURCE`, repeating paired kinds/references as needed. Read the complete returned payload and required original external instructions, write only the returned Markdown report and execute `finish_command` unchanged.

The program checks current contract/review bindings, prerequisite delivery, open upstream fixes and supported Git inclusion evidence. Do not inspect Git/Aone to reconstruct its gate or set `done` by hand. Supply truthful external evidence for the declared obligations: actual remote-trunk inclusion is distinct from source-branch publication, build, release, deployment and end-to-end behavior. A report must name what was observed and what remains unverified.

For every item, including ordinary development and aggregates, record actual user acceptance against current artifacts through `autonomy accept ID --approval-source SOURCE`; this records acceptance without authorizing autonomous advancement. Use `context-update` for the remaining obligation and evidence. Textual acceptance alone does not establish the binding required by autonomous dependents. Do not infer acceptance from an AI pass, tests, or the controller ending. The item remains awaiting delivery until its declared obligation is actually met. User edits after review invalidate affected evidence; re-check current bindings rather than accepting an old snapshot silently.

`published` or `no_op` ends the checkpoint; `partial` permits only its returned resume command. For `status: blocked` with `code: stale_ticket`, execute only the returned `next_command`; `status: blocked` with `code: stale_evidence` has no continuation command and requires current authorization/review evidence. Otherwise report those blockers or missing facts and stop. Readiness is program-derived; do not rewrite dependents to reproduce it. For aggregates, an agent or reviewer must assess actual evidence against every acceptance criterion and record truthful coverage in the report. The program verifies required evidence kinds, prerequisites and available structural conditions, including supported Git inclusion for development items. It does not parse Markdown semantics or assert that reported evidence satisfies acceptance. An unfinished linked fix blocks affected downstream delivery and aggregate completion. Fix delivery leaves the original delivered item and its current evidence intact and still requires current baseline/review validation.

Local cleanup remains separate from delivery. Invoke [cleanup-worktree](../../cleanup-worktree/SKILL.md) only when requested, using the exact program-resolved item worktree and preserving that skill's concrete-manifest authorization, cleanliness and remote-recovery gates. Preserve shared roots, main-workspace environments and sibling worktrees. Report the actual outcome with `begin cleanup-record ID --cleanup-status pending|done|not_applicable --reference SOURCE`; never mark removal complete before it happened. Ordinary cleanup preserves development metadata. When the user explicitly discards an unfinished implementation, add `--discard-development --approval-source SOURCE` to verified `done` cleanup; the program retains its historical snapshot, preserves the requirement and design, and invalidates prior base-bound review/waiver evidence; current implementation gates must be satisfied again. Failed cleanup leaves successful delivery intact. Code submission and project removal retain their separate user authorization.

An adopted [resource lifecycle policy](../../manage-workitems/references/resource-lifecycle.md) separately covers registered internal snapshots, caches and retired generation workspaces. Use its exact manifests within that policy; acceptance/delivery does not establish it. Ordinary source branches and worktree cleanup keep their existing authorization boundary.
