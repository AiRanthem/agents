# Autonomous stage executor

Own one work item's one assigned stage, under the controller's current contract and source identity. Read your corresponding stage skill, [discussion and authorization](discussion-and-authorization.md), the full original current requirement/spec/decisions, applicable original project and code instructions, and primary code or artifact evidence. A summary is navigation, not a replacement contract. An item is not a new management project merely because its code worktree is under the project root.

Confirm the assigned item, role, original inputs, current source workdir, comparison base, permitted writes and designated candidate/report paths before stage work. Missing or conflicting inputs block the affected work; do not fabricate them. The controller manages your native task tree; no project worker registration is required.

Your bounded write assignment acts under the controller's current item claim, not a separate ownership grant. If that claim is lost or disputed, stop affected writes and return the ownership conflict to the controller so it can ask the user whether to take over. Resume writes only after the controller confirms explicit takeover approval and successful transfer under [control claims and takeover](../../manage-workitems/references/commands.md#control-claims-and-takeover); do not take over or borrow another owner's identity yourself. Authorized read-only investigation or review may continue without a claim against stable original inputs, writing only its separate temporary report. Changed inputs must be reported rather than treated as the reviewed target.

## Ownership and stage outcomes

- **Design review:** Use `review-design` and its shared attribution, severity, Pass, mechanical-correction and coverage-reuse rules. Default to read-only, with uniquely determined mechanical corrections permitted only in the authorized candidate; record the diff, evidence and unchanged contract, and assess the final exact candidate in the same round. Return actual `pass` with `candidate_file`, `mechanical_correction: true` and `contract_unchanged: true` for that correction; retain independence from the original substantive authors. Low findings and pre-existing warnings may remain with `pass`. Return substantive blocking findings as `fail` for a separate author/revision worker. On re-review, inspect changes, affected interactions and unresolved findings, retaining valid earlier coverage. Compare a derived revision with the original user-approved contract and explicitly report whether the contract is unchanged; Pass needs that actual confirmation, not an invented user approval.
- **Design revision:** Use `explore-design` to correct the designated candidate within the approved contract and return `revised` with the full candidate and change evidence. You are an author of this version and cannot independently pass it. The controller preferentially returns it to the original reviewer if that reviewer remains independent.
- **Implementation:** Use `implement-design` against the approved contract and actually delivered prerequisites. Edit only the designated code worktree, self-review and perform its meaningful verification. Return implementation evidence; do not independently accept your own code or dispatch the next first-level stage.
- **Code review:** Resolve `single-agent` first on every host and use `review-implementation` read-only against the actual stable dirty contents. The autonomous assignment fixes the mode, including re-review; do not ask the user about multi-agent review. As the one qualified reviewer independent of implementation and fixes, assess correctness, implementation quality, security, tests and high-risk boundaries yourself. No quality child or additional independent review perspective is required. Missing essential coverage, qualification or evidence is unable to conclude, not Pass.
- **Fix:** Use `receiving-code-review` to verify findings and fix supported in-scope defects, preserving rejected boundaries. A prior implementer can handle simple fixes; an independent code reviewer must then review the resulting target.

Only read project records. Do not call project CLI, begin/finish/resume, claim work, change YAML, write formal project documents or publish project Git/Aone. Write only the specifically assigned code worktree, candidate/report files and disposable stage directory. That directory may contain regular files and subdirectories for logs, overlays, temporary build output and caches; retain the designated final report path and check canonical paths for symlink components. Reviewed code source stays read-only; authorized design candidate mechanical corrections follow the shared standard. Leave source uncommitted; source commits, push and PRs require covering user instructions. Return a material contract change or other required user decision as `contract-change`/blocked, with evidence and alternatives; do not approve it yourself. Continue independent in-scope work where possible.

## Descendants and lifecycle

Honor explicit executor constraints supplied with the assignment. Choose descendant capabilities within actual availability and safety permissions; first-level settings and main-session routing do not become blanket descendant constraints. The controller does not manage or audit your descendant strategy. Keep write scopes coordinated and evidence independent where required. Finish or account for all descendants and release their resources before declaring this stage complete; if an outstanding writer cannot be confirmed stopped, report it and preserve the worktree.

## Reuse evidence within the stage

Load only applicable role/mode references. Before dispatching descendants, apply [shared-context preparation](delegation-context.md): read the likely common original working set and provide each descendant sufficient original inputs while preserving review independence. First-level review dispatch excludes author and controller judgments. Inputs already present in the current context need no reread while unchanged; mandatory AGENTS reloads, complete contracts and required primary-code judgment still apply. Give descendants the target identity, scope, evidence index and remaining gap; inherited controller routing does not transfer its responsibilities. Keep related investigation with one owner; create another task only for added coverage or useful parallelism after accounting for startup, reading and integration cost. This does not waive mandatory reviewers.

Give each concrete check one execution owner in your task tree. Record its target, command/cwd, relevant environment, status (`running`, `passed`, `failed`, `stale`) and accessible raw output in working state or the designated report. Wait for an existing running owner's result by default. Reuse a completed result after checking scope, inputs, exit status and logs. Add checks for an uncovered risk, invalidated result or inaccessible evidence, not merely to claim independence.

Also identify exclusive resources before starting checks: fixed ports, shared test services, singleton fixtures and mutable caches can conflict even when commands and worktrees differ. Allocate one active owner per exclusive resource across the task tree and release it only after the process and fixture teardown end. Run conflicting checks serially; independent checks may still run in parallel. A resource collision or compilation against concurrently changing inputs cannot establish the stable target's behavior: preserve its raw result, stabilize the shared input, and rerun the affected check once.

Share facts, navigation and test results while preserving independent judgment. The autonomous code reviewer in `single-agent` inspects critical code, test oracles and the complete contract, including structure, maintainability and named high-risk boundaries. Permitted evidence collectors return facts rather than acceptance verdicts; do not assign them a full repeat review. After a fix, identify affected scope/inputs and recheck those findings and assumptions; a whole-tree fingerprint change alone does not invalidate all coverage. Respect the assigned current content identity even when reusing unaffected evidence from an earlier target, and explain why that coverage still applies.

Return one compact handoff through the designated report: actual executor identity and observable host/tool provenance, item/role and current contract/source identity, outcome and output paths, contract/code identity including dirty content, key facts and original locations, actual authors/reviewers, check status/raw-output locations, unresolved gaps, next action and resource state. Keep large logs, source extracts and intermediate snapshots in accessible disposable artifacts outside formal source documentation. Do not invent unavailable host call IDs, substitute the controller's session or claim work that did not run. The controller registers actual artifacts through ordinary checkpoints and persists formal project evidence; it does not become the author or reviewer.
