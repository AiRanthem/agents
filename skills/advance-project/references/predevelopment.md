# Opt-in predevelopment

Load this reference only when the user explicitly enables predevelopment or an item already carries a predevelopment generation. Ordinary advancement requires actual accepted delivery. Record the user's scoped opt-in with `autonomy authorize SCOPE --approval-source SOURCE --predevelop`. This authorizes freezing independently reviewed source into new snapshot branches and publishing those snapshots; it does not authorize formal source delivery, PRs or acceptance. Outside-scope prerequisites require an existing authorized snapshot or actual accepted delivery.

## Controller

Use runtime status for artifact readiness; manage task scheduling in the current agent. A ready item can return `next_action: prepare` instead of a worker role: run `autonomy prepare ID`, settle its publication, then recompute status. The program freezes any needed in-scope prerequisite, pins its contract and transitive snapshot identities, and creates an isolated development generation. Pin the fetched formal base alongside the snapshots so delivered prerequisite code remains present; recovery reuses that same formal-base OID. Use `autonomy snapshot ID` only to explicitly capture or resume a needed authorized snapshot. Repeat the same command after a snapshot/prepare interruption; preserve its recorded identity and settle any returned lower-level publication command first. Do not create replacement branches or overwrite divergent refs.

Snapshots include the full nonignored tree, including staged, unstaged and new files. Their private-index commit leaves the original HEAD, staging and worktree intact. Only a stable source tree with current independent code Pass and no concurrent source mutation may be newly frozen. A published snapshot remains an immutable input while the human edits the live prerequisite. The frozen requirement/spec/decisions and commit OIDs, rather than its moving branch or live prose, govern downstream work. Conflicting inherited snapshot versions block baseline preparation. Non-code aggregate prerequisites retain ordinary acceptance and delivery gates.

`baseline` and `rebase` use the existing `project-implementer` template and `implement-design`; prepare each with `autonomy begin-transform ID --role baseline|rebase --author-session SESSION`. Pass its full `read`, `approved_contract`, `code_context`, `git_operation` and `prerequisites` to the executor. Register verified completion with `autonomy complete ID --role baseline|rebase --report-file FILE --provenance SOURCE`. These records identify artifacts and authors, not running workers. They may commit only in their assigned isolated generation to perform that Git operation; normal implementation and fix stages retain uncommitted source. The controller captures and pushes frozen snapshots through runtime commands; workers never push or operate project records.

A completed speculative item reports `awaiting_predecessor_delivery`, retains its predevelopment marker and cannot be accepted or delivered. It can supply a snapshot for further opted-in work. Once every prerequisite is currently human-accepted and actually delivered, status returns `next_action: prepare` for formal convergence. Acceptance alone is insufficient. Preparation freezes the item's own speculative version and retains its original worktree, then schedules a rebase onto the fetched formal base. After successful rebase, the runtime exposes the result as uncommitted changes in the new worktree. The usual explicit initial design-review waiver applies before convergence. Before formal `awaiting_acceptance`, assess design applicability against the formal baseline under the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage). Retain valid design coverage and independently review invalidated scope; a baseline change alone does not require a complete new design review. Independent code review of the formal result remains mandatory, including when the source tree is unchanged; a skip-design-review authorization cannot waive that review or necessary design reassessment.

Release completed executors and keep other ready items moving. End a round when no item is ready and this run’s task trees are accounted for, including speculative waits alongside acceptance/delivery/blocker states. Report the speculative marker, frozen inputs, retained original worktree and formal convergence gap. Coordinate writes in the current task tree; changed configuration, divergent refs, missing source and material contract decisions block the affected item. An inaccessible old executor does not lock project state.

## Implementation executor: Git transformation stages

Read the original approved contract and frozen prerequisite reports supplied in the current assignment. Keep all writes within the assigned generation and report artifacts. Do not modify, reset or clean the retained original worktree, switch the recorded target, push source, or call project CLI.

- `baseline`: integrate every same-repository commit listed in `git_operation.commits` into the assigned baseline, resolve conflicts within the contract, verify the integrated content and finish at a clean committed baseline containing every pin and the pinned formal base as ancestors. Other-repository snapshots remain fixed external context; do not merge them. Return evidence of the resulting tree, ancestry and checks.
- `rebase`: replay the item's entire own delta onto `git_operation.target`, excluding inherited snapshots using `git rebase --onto TARGET OLD_BASE` with the exact bound `old_base`. Resolve conflicts within the contract, verify the resulting behavior and finish the rebase with a clean tree; preserve all own changes, including ones originally untracked. Do not reset the resulting branch yourself. The controller/runtime performs the final metadata switch and exposes uncommitted source for design-applicability assessment and formal code review. Return target, old base, resulting commit/tree, checks and any unresolved contract decision.

These explicit Git operations can replace source instruction files inherited from snapshots or the formal target. Their commit OIDs stay bound while read guards for files inside this assigned source worktree permit that transformation; project and ancestor instructions remain guarded. Reload the resulting applicable source instructions before checking the integrated/rebased output. Subsequent design and code reviewers read and guard the resulting instructions normally. A Git ancestry check proves the replay baseline, not semantic correctness; meaningful verification, affected independent design assessment and formal independent code review own that judgment.

For approved contract/DAG replanning or manual/autonomous handoff, use [resource lifecycle](../../manage-workitems/references/resource-lifecycle.md). Coordinate source writes within the current task tree, save unique old source, bind replacement prerequisites and account for retained resources. Existing frozen consumers keep their original closure until migration/disposition releases it. Collection marking makes a snapshot unavailable to new consumers; retry never resurrects its identity.
