# Autonomous project controller

Work from the schema-v2 management root. Read its original `AGENTS.md`, the [command contract](../../manage-workitems/references/commands.md) and [project context](../../manage-workitems/references/project-context.md). The caller supplies the project command entrypoint, stable execution identity and available stage-role bindings, including configuration-check evidence and permission limits. Missing required bindings block the affected stage; the shared controller does not discover or import platform implementations. The controller owns project commands, formal documents and Git/Aone persistence. Stage executors own their assigned investigation, source and assessment.

## Scope and control

Use exactly one scope: `--all`, `--tree ID`, or repeated `--item ID`. Hierarchy differs from the dependency DAG; inspect outside prerequisites without silently adding them. Inspect current scope and artifacts before acquiring write control. When starting advancement mutations, register the user's instruction with `autonomy authorize SCOPE --approval-source SOURCE` under the current write claim. `--skip-design-review` needs an explicit scoped waiver. Advancement grants neither acceptance nor source delivery; actual accepted prerequisite delivery remains required.

Read `autonomy status SCOPE` after material input, result or decision changes. It derives readiness from current approval, design coverage, code products, independent review, dependencies and acceptance. Project state does not register workers, attempts or their liveness. Manage native task IDs and task trees in the current agent's working state. Reuse available tasks and valid work; a failed executor does not invalidate completed source by itself.

Use the item claim as a write lock under [control claims and takeover](../../manage-workitems/references/commands.md#control-claims-and-takeover). Authorized inspection, investigation and report-only independent review may proceed without takeover using complete original inputs and a stable target. `autonomy status` reports artifact readiness separately from `takeover_required`; ready is not a write grant. Pending takeover approval blocks this run's writes even when the artifact remains ready; do not poll or redispatch an unchanged target merely because it stays in `ready`. Before a project write command, shared source edit or writer dispatch, check the current claim. A foreign claim or `control_claim_required` pauses those mutations: report the item and owner, then ask the user whether to take over. The advancement/continuation instruction alone is not takeover approval. Only after explicit approval, run `takeover ID --approval-source SOURCE` with that actual decision and wait for successful transfer before starting writes. If the claim is lost again, stop affected writers and ask again; read-only work and unrelated authorized items may continue. Retain temporary review reports for registration by the current writer only after checking that their input identities still match. Takeover rotates only that item's claim and preserves source and business evidence. Continue from current artifacts without restoring an old host's task tree or requesting proof that inaccessible executors stopped. Coordinate actual source writes using available host facilities; isolate competing writes when necessary. A missing physical worktree or binding is a source recovery gap: preserve its locator and report the missing source instead of guessing another path. Takeover cannot copy unpublished source from another machine.

## Stages and evidence

Verify the caller-supplied configuration evidence and actual dispatch capabilities. Disk readiness is not evidence of successful dispatch, runtime model identity or tool access. Bind these first-level responsibilities to the supplied executors; each executor manages its descendants and cleanup within actual limits. Do not add work-item managers or propagate controller routing into descendants.

| Ready role | Explicit skill |
| --- | --- |
| `design-review` | `review-design` |
| `design-revision` | `explore-design` |
| `implementation` | `implement-design` |
| `code-review` | `review-implementation` (`single-agent`) |
| `fix` | `receiving-code-review` |

Resolve code-review mode as `single-agent` before dispatch on every host, including re-review and cross-host continuation. Pass that explicit mode to the executor; do not pause advancement to ask about multi-agent review. One qualified reviewer independent of implementation and fixes covers correctness, implementation quality, security, tests and high-risk boundaries under the [shared review contract](../../review-implementation/references/review-standard.md). No review descendants are required.

Dispatch all ready in-scope items within real capacity. Keep one coordinated stage target per item. Give each executor the original complete read payload and approved contract, exact worktree/baseline, permitted writes, designated report/candidate paths, [stage-executor](stage-executor.md), explicit stage skill and a compact evidence index. Use disposable absolute paths without symlink components. An independent reviewer receives stable source and clean author-independent context. Prefer an available original reviewer on re-review only while independent of all substantive authors. Record actual authors before they can write, including replacement or repair authors.

Use ordinary checkpoints to register actual work:

- **Design review:** `begin design-review ID --reviewer-session SESSION`, optionally with `--review-file FILE` for a completed external report. Pass the returned current original inputs and candidate to the actual reviewer. Copy only its report and authorized mechanical candidate edits into the returned drafts; finish with its actual `--result pass|fail --provenance SOURCE`. Mechanical correction requires that reviewer's explicit `--mechanical-correction --contract-unchanged`; a derived pending approval needs independent `--contract-unchanged` confirmation. The registrar does not add corrections or substitute its judgment.
- **Design revision:** `begin design-update ID --author-session SESSION --contract-unchanged` for an authorized contract-internal correction. Register the actual candidate and finish; independent confirmation against the original user-approved contract remains mandatory. A material contract change returns to the user's approval handoff.
- **Implementation/fix:** `begin development-start ID --author-session SESSION`, settle preparation and finish before source work. Use `--skip-design-review --approval-source SOURCE` only for the recorded explicit waiver. Inspect and reuse retained code, fix demonstrated gaps, and obtain the actual completed report. Register `autonomy complete ID --role implementation|fix --report-file FILE --provenance SOURCE`. It records current content and meaningful completion evidence, without claiming independent approval. If guarded source instructions change, completed code remains available for current design coverage and independent code review.
- **Code review:** `begin development-finish ID --reviewer-session SESSION`, optionally with the actual `--review-file FILE`. Give the actual independent reviewer the explicit `single-agent` mode and stable complete target and write its report to the returned draft. Finish with its actual result/provenance. The source snapshot must remain unchanged. Implementation/fix authors and the registrar are excluded as reviewers. The actual report must establish the qualified reviewer's correctness, quality, security, test and high-risk coverage; a missing essential assessment cannot become Pass.

For `next_action: split`, use `split-workitem` to materialize the independently reviewed stages and DAG through the controller-owned project commands, rather than dispatching source implementation. Require the full parent spec; child refinement is not a reason to lower parent design rigor. Persist each child’s complete inherited contract, then recompute the original scope. For `--all` or `--tree`, register existing advancement authorization for newly included children and continue their own design reviews without mandatory redesign. Explicit selected-item scope does not silently expand. Genuine child blockers return to supplemental design and affected independent review; changes to shared or parent contracts return to the responsible design layer.

For `next_action: design_reuse_assessment`, use ordinary `begin design-reuse` and its actual applicability report under the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage). An owner can preserve a genuine independent conclusion; it cannot invent one. Failed applicability goes to affected independent review. For `next_action: lifecycle_prepare`, execute the indicated source replacement and recompute status.

For ordinary recovery, follow every returned `partial` publication or workflow-ticket recovery command exactly. If scripts block or malfunction, use [user-authorized manual recovery](../../manage-workitems/references/recovery.md#user-authorized-manual-recovery): the controller investigates, obtains covering explicit approval and may manually correct project state/files and responsible scripts. This exception also covers a broken takeover mechanism when approval includes the actual transfer and its fencing guarantees are preserved. These commands recover immutable project writes, not executors. Preserve signed tickets, journals and unpublished drafts. A stale ticket needs a fresh checkpoint using current inputs; retain actual code and reports and do not repeat implementation without a demonstrated gap. Never fabricate a review, user approval or host identity. Native tool refusal, missing required role or independent reviewer blocks the affected stage; do not bypass host permissions.

## Completion and user decisions

A substantive blocking design finding needs a separate revision author and affected independent re-review. Low findings and baseline warnings may coexist with Pass. Implementation success or tests do not establish independent review or human acceptance. Reviewers keep judgment; the controller registers their evidence. Keep unrelated ready items moving while consolidating actual user-owned decisions under [discussion and authorization](discussion-and-authorization.md).

The current agent owns task lifecycle, including descendants and resource cleanup. Follow all tasks started in this run through actual host completion while advancing other ready work. For tasks this run still controls, use the actual host lifecycle instead of declaring termination from a timeout. Across hosts, resume from artifacts and current project control; old task availability is not a project gate. Release resources you control and report concrete remaining source/capability gaps.

Stop per item at `awaiting_acceptance`, `accepted_awaiting_delivery`, completion or a concrete blocker. Record `autonomy accept ID --approval-source SOURCE` only for actual human acceptance of current code and contract. Use [complete-workitem](../../complete-workitem/SKILL.md) for actual authorized delivery. Source commits, push, PRs and cleanup need covering instructions; ordinary advancement leaves source uncommitted. Aggregate items retain evidence-based acceptance/delivery and have no code stage.

`round_finished` means no item is ready; it cannot describe native jobs managed outside project state. End the run after accounting for this run's outstanding task trees. Report full IDs/titles, current artifacts, actual checks and their limits, unresolved decisions, acceptance/delivery gaps and retained source locations. At settled boundaries use adopted [resource lifecycle](../../manage-workitems/references/resource-lifecycle.md) policy; preserve exact pending publication and collection intents.
