# Autonomous project controller

Stay rooted at the schema-v2 management project and read its original `AGENTS.md`. Read the installed [project command contract](../../manage-workitems/references/commands.md) and [project context](../../manage-workitems/references/project-context.md). Resolve its physical `scripts/project.py` and the workspace-prescribed Python environment. Below, `project.py` means that executable with `--root <project>`; do not change Python environments to bypass requirements. The runtime is the authority for current inputs, attempt bindings, readiness, publication and recovery. The controller alone performs project commands, formal document writes and project Git/Aone persistence.

## Host and scope

This entry supports Codex, Cursor and Qoder. Read the current host adapter, [Codex](../../../codex/AUTONOMY.md), [Cursor](../../../cursor/AUTONOMY.md) or [Qoder](../../../qoder/AUTONOMY.md), and run its real configuration check before dispatch. Load only the adapter for the active host. Check results establish configuration, not available tools, successful spawn or actual model identity. If native delegation, required role settings or required nested review capability are unavailable, report the affected host/stage blocked; do not silently change roles or models.

Use the adapter's four first-level role templates: `project-design-reviewer`, `project-implementer`, `project-implementation-reviewer`, `project-fixer`. `design-revision` uses the design-reviewer template; `baseline` and `rebase` use the implementer template under [predevelopment](predevelopment.md). Fixed role model/effort belongs to the host adapter; do not dynamically upgrade, change effort or choose by task difficulty. Leave descendant decomposition, model/effort and lifecycle to each first-level executor; do not copy controller routing or fixed first-level settings into descendant restrictions.

Resolve the user's scope as `--all`, `--tree ID` (the item and descendants), or repeated `--item ID`. Scope hierarchy is not the dependency DAG. Inspect dependencies outside the scope without automatically adding them. Ordinary eligible development items require an approved completed initial contract and prerequisites both accepted by a human and actually delivered under their declared obligations. Explicit predevelopment uses the pinned-snapshot gates in its reference; it never waives initial contract approval. Missing initial designs require a separately authorized design workflow. Aggregates retain their existing evidence-based aggregate acceptance and delivery flow; never dispatch their code implementation.

Read `project.py autonomy status <scope>`. Once the user has requested advancement and the actual source is known, register that scoped authorization with `project.py autonomy authorize <scope> --approval-source SOURCE`. Add `--skip-design-review` only for the exact scope the user explicitly waived; simplicity is not a waiver. Authorization starts the stage loop, not source publication, contract changes or human acceptance. On restart inspect existing authorization, owner, active attempt and actual host jobs first; do not re-authorize as a way to erase running state or stale evidence.

## Dispatch and consume real results

Recompute status after every material project change, stage result or user decision. Dispatch every currently ready in-scope development item, subject to real host capacity, retaining a queue for the rest. There is one current first-level executor per item's current stage. Do not add a work-item manager or skip a required stage/review to save tokens. The controller mechanically checks and registers evidence; executors own investigation, code and assessment.

If a ready item returns `next_action: design_reuse_assessment`, run `begin design-reuse ID`, read its complete original review basis and current inputs, write the applicability report, finish with the actual declared result/provenance arguments, and recompute status. Apply the [coverage-reuse rules](../../review-design/references/implementable-gate.md#reuse-independent-coverage): this trusted-owner assessment preserves an existing independent conclusion, never invents a new one. If applicability fails for current inputs, follow status into affected independent review rather than repeating the same assessment. No extra stage permission is needed within the existing scoped authorization.

If a ready item returns `next_action: lifecycle_prepare`, execute `lifecycle prepare ID` under the [resource lifecycle](../../manage-workitems/references/resource-lifecycle.md) and recompute status before spawning. If a ready item returns `next_action: prepare`, execute `autonomy prepare ID` under the predevelopment reference and recompute status before spawning. Otherwise use its runtime `next_role` and the corresponding role template:

| Runtime role | First-level role template | Explicit skill |
| --- | --- | --- |
| `design-review` | `project-design-reviewer` | `review-design`, assessment with authorized mechanical candidate corrections |
| `design-revision` | `project-design-reviewer` | `explore-design`, separate author of the candidate correction |
| `implementation`, `baseline`, `rebase` | `project-implementer` | `implement-design` |
| `code-review` | `project-implementation-reviewer` | `review-implementation` |
| `fix` | `project-fixer` | `receiving-code-review` |

1. Actually start the configured role, initially paused awaiting dispatch context. For subsequent design review, prefer waking the original independent reviewer when it remains available and has never substantively authored or revised that design; check the cumulative author set, not only the current version’s last writer. Capture the real follow-up/wake call and returned identity for this new stage; never reuse an earlier stage receipt as evidence of a new execution. Otherwise spawn an independent configured reviewer. When the real tool supports native role selection, use it. When it instead exposes explicit model/effort and fresh-context controls, read the corresponding host role template and pass its configured model/effort plus complete role instructions through those real controls as the adapter specifies. A task name alone does not select a role or model. If neither route can express the required settings and instructions, block that stage. Capture the real host/tool call and returned worker identity, preserving the unchanged actual raw tool data in a controller-owned file. Use the host adapter's receipt assembler to derive binding fields from the complete accepted dispatch instead of transcribing them. Its required dispatch fields are `host`, `tool`, `worker_id`, `raw`; include `call_id` only when the actual tool exposes it. Preserve actual tool arguments and output in `raw`, including its native worker identity. If a wait result omits the identity, retain its actual `arguments.target` together with the real result. Do not invent a host call ID or inspect private transcripts/logs to obtain one. The runtime can correlate the program-owned attempt and captured receipt hash without claiming a host-signed call ID. Do not invent a worker or populate a successful receipt when the tool did not start one.
2. Register `project.py autonomy dispatch ID --role ROLE --receipt-file FILE`. Save the complete CLI response in a controller-owned, worker-accessible temporary artifact with its identity; inspect scheduling fields (status, worker/attempt/input binding, continuation, decisions and blockers) without loading the entire contract payload into controller context. Failed calls or missing required fields block handoff. Implementation dispatch also performs the runtime-owned development-start preparation; do not separately reproduce its begin/finish work. A partially published dispatch may already reserve the current attempt and worker without completing that preparation. Retain its returned `continuation_command` (`autonomy resume ID --attempt ATTEMPT`) and keep the same worker paused. When a lower project checkpoint also returns `next_command`, execute that exact recovery command under the command contract until its publication is settled, then execute the retained `continuation_command`. A successful lower-level resume alone does not supply dispatch context or release the worker. Follow subsequent returned recovery/continuation commands; do not call dispatch again, start a new attempt, change the spawn receipt or re-spawn the worker. Unresolved partial/blocked results keep the worker paused. Only a final `status: ready`, `worker_paused: false` response with the same attempt and worker, and complete `input_binding`, `approved_contract`, `read` and `code_context`, authorizes stage handoff. A definite rejection before any attempt was reserved permits stopping the unassigned worker without letting it write; an uncertain or reserved attempt must be preserved for recovery. A worker's early completion of its pause acknowledgement is not a stage result. Deliver accepted context through the host's wake/follow-up operation for that same worker; a message-only operation may leave an idle worker stopped.
3. Give the worker its actual accepted item/role/attempt/input binding, the complete response artifact and original `approved_contract`/input locations with their identities, explicit source workdir and baseline, exact candidate/report file paths and a disposable stage directory for ordinary files and subdirectories (logs, overlays, build output and caches), all under resolved absolute paths with no symlink components, [stage-executor](stage-executor.md), and the explicitly named stage skill via the host's supported invocation. The worker reads the complete approved contract, required original inputs and applicable instruction paths. Include a compact index of prior reports, established facts, check owners/status/raw outputs and remaining gaps. Do not copy the full payload, session or unrelated routing/modes into messages; a summary does not replace original inputs. The controller retrieves original ranges when a decision requires them. Do not give the worker project-operation ownership. Implementation/fix keep source uncommitted; only dispatched baseline/rebase may commit in their assigned isolated generation; a reviewer gets stable read-only source and may mechanically correct only its expressly authorized design candidate under the shared standard. Do not review a moving target.
4. Wait through the real host lifecycle while advancing other ready items. Keep tracking all running executors; do not declare the run ended while a result is outstanding. Confirm the original executor is terminal and its descendants have stopped writing before registering a result. Capture the host/tool receipt, retaining the same worker identity and raw call arguments/output associating it with the observed terminal state (with optional observable `call_id`), plus `attempt`, `role`, `input_binding`, `outcome`, `report_file`, `terminal_status` and `descendants_stopped: true`; include `candidate_file` for a revision. For an independent design reviewer’s mechanical candidate correction, capture actual `outcome: pass`, `candidate_file`, `mechanical_correction: true` and `contract_unchanged: true`, with its exact diff, basis and final candidate identity; do not turn that correction into `revised` or add the reviewer as a substantive author. A spawn receipt or a worker's unsupported completion claim is insufficient. Outcomes are `pass`, `fail`, `blocked`, `revised`, `contract-change`; verdicts require a `completed` executor, while an observed `failed` or `stopped` executor may only report `blocked`. The report substantiates the outcome and current artifact identity. For an independently reviewed contract-preserving design revision, carry `contract_unchanged: true` only when that real reviewer explicitly confirms preservation of the original approved contract; otherwise return the missing decision or finding rather than setting the flag yourself.
5. Run `project.py autonomy result ID --receipt-file FILE`. The program binds and persists the real result using its existing checkpoints. A stale or mismatched receipt cannot overwrite current state; report the rejection and re-read status rather than editing YAML or inventing new approval. When stale inputs leave a completed attempt occupying the item, follow [attempt recovery](../../manage-workitems/references/recovery.md) to retire it only with the original worker's observed terminal receipt and confirmed descendant cleanup; unknown liveness remains blocked. For a pending result, execute its returned attempt continuation (`next_command` on partial). It restores the original receipt and artifact bodies captured before publication and recovers its exact journal; confirmed pre-push rejection permits fresh guard validation of that same result, while unknown remote outcomes remain blocked on the original journal. Follow returned blockers exactly, then recompute scope readiness.

Default flow is complete initial independent design review, implementation, independent code review, needed fix and affected re-review, then waiting for human acceptance. Apply [design coverage reuse](../../review-design/references/implementable-gate.md#reuse-independent-coverage) to later design or baseline changes. Consume the reviewer's actual verdict and acceptance impact; a nonempty findings list does not turn `pass` into `fail` or `revised`. Low findings and pre-existing warnings do not require a design revision. Mechanically correctable design issues are not blockers: the reviewer may correct its authorized candidate and pass the final exact candidate in the same round without becoming a substantive author. A substantive blocking design finding returns `fail`; dispatch a separate author/revision worker, register its actual revision, then preferentially return to the original still-independent reviewer for incremental assessment. A revision worker cannot review its own version. Implementation and simple fixes may share an author; code review must still be independent. An implementer finishing or tests passing does not supply code acceptance. Code-review executors must run their mandatory quality subagent and risk-appropriate independent perspective; no fixed review count or budget permits omitting these gates.

Wait using the host's event-driven lifecycle API within its progress-update limits. Report stage changes, substantive findings, decisions and blockers concisely. A timeout alone is not new progress and does not justify a new task or repeated detailed status narration. Keep intermediate scheduling updates separate from the final report.

## Decisions, acceptance and recovery

Own the complete design approval handoff when initial contracts or material revisions need a user decision; persist actual approval and resume only the authorized current scope. Consolidate user-owned decisions with [discussion and authorization](discussion-and-authorization.md). A changed contract invalidates the prior approval for affected work; do not fabricate a new approval or use retries/models to replace the decision. Contract-preserving internal revisions continue under the recorded scope. Pause only affected items and keep other ready items moving. Without new evidence, repeated uncertainty needs a concrete decision or capability report rather than unlimited new reviewers; re-review follows necessary fixes and essential gaps, not a requirement to clear every finding.

The automatic loop stops per item at `awaiting_acceptance` or predevelopment `awaiting_predecessor_delivery`; release its execution resources and preserve uncommitted source and evidence. After the user's actual acceptance of the current contract/code, the controller may record `project.py autonomy accept ID --approval-source SOURCE`. Do not infer acceptance from AI Pass or run completion. `accepted_awaiting_delivery` still does not unlock downstream items. Use [complete-workitem](../../complete-workitem/SKILL.md) only for actual authorized delivery; source commits/pushes/PRs and cleanup need their own covering instruction. Aggregates use that skill's existing criterion-by-criterion acceptance flow.

On a subsequent explicit start, compare current contract and actual dirty artifacts with prior bindings and reuse only still-valid independent evidence. Re-run affected stages; do not reset accepted work blindly. Before recovery or any new dispatch, inspect whether the original first-level task and its writers still run and who owns the attempt. A dispatch continuation resumes only the same controller, worker and current attempt through its returned command; it does not authorize a replacement dispatch. New sessions, age or transient silence do not authorize takeover or concurrent writes. Manage each task tree through its first-level executor; that executor owns descendant strategy and cleanup. If lifecycle state is uncertain, preserve it and report the affected blocker.

End the round only when there are no ready items and no first-level executor still running, and every in-scope item is waiting for acceptance, accepted but awaiting delivery, speculatively waiting for prerequisite delivery, completed or blocked. These dispositions can coexist; `round_finished` summarizes the runtime schedule, but an actually outstanding host writer still requires lifecycle resolution. Report full ID and title, stage, actual executor/results, stable contract/code evidence, what was and was not verified, pending user decisions, acceptance and delivery gaps, retained source paths and recovery context. Project completion still requires all project delivery obligations.

known-limit: receipt files are controller-captured host/tool evidence with structural, binding and hash validation, not independently signed host attestations. Preserve genuine raw receipts and refuse invented identities. A future host-signed receipt integration can strengthen provenance without changing the controller/executor boundary.

At quiescent stage boundaries, maintain resources only under an adopted lifecycle policy: use `lifecycle status`, settle pending intents, then `lifecycle plan` and its exact collection command. Capacity blockers require migration/disposition or collection before another generation/snapshot is created. A pure mode/coordinator transfer uses `lifecycle handoff`; replanning uses `lifecycle replan` after genuine attempt closure; it starts a new generation and never substitutes for same-attempt network recovery. Preserve ordinary source submission and cleanup authorization.
