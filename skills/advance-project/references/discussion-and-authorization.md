# Discussion and authorization

Apply these rules in ordinary development, read-only planning and managed-project work. Explicit user instructions take priority over skill guidance. Reuse the approved scope, requirements, paths, tradeoffs and execution authorization from the conversation; do not ask the user to repeat them. Actual harness, security and filesystem permissions still apply.

The user may explicitly skip any verification checkpoint for a specified scope, including design/implementation review, tests, dependency checks, formal-convergence checks and delivery verification. Honor that decision without asking again or reintroducing the skipped checkpoint under another name. Record the exact checkpoint, current target, actual user source and verification limits as a user-authorized skip, never as executed verification or an independent review. A user's explicit acceptance of the current implementation may instead record an implementation pass in place of independent implementation review, with `human_acceptance` provenance. These decisions do not imply an ownership takeover, an unrequested external action or permission to bypass harness permissions, data protection or transaction integrity. Managed projects use the [typed checkpoint records](../../manage-workitems/references/commands.md#user-verification-decisions); executors return the decision to their controller for registration.

When the sandbox prevents an already authorized command from starting, use the host's permitted approval or escalation mechanism for that same command. Continue only after actual approval. Distinguish this execution-permission request from a structured project-workflow blocker; a denied request remains blocked and must not be bypassed.

Before asking for a decision, investigate the relevant original instructions, contract, code, callers and available evidence. Resolve factual uncertainty yourself where possible, complete independent authorized work that makes the choice concrete, and combine the remaining consequential choices into one coherent decision batch. Explain the evidence, recommendation, meaningful alternatives and consequences. Revisit a settled choice only when new evidence invalidates it. Silence, elapsed time and a tool timeout are not approval. Pause only work that depends on an unresolved required choice and continue other authorized work.

Within an unchanged approved contract, the executor chooses internal implementation, private types and helpers, local representations, verification and equivalent internal corrections. Do not require approval for every type or field. Obtain the user's decision before changing requirements, public or stored contracts, compatibility, a user-selected tradeoff, key constraints, approved security or correctness guarantees, or acceptance criteria. Do not weaken these guarantees or criteria to finish. A new dependency or external action is governed by the existing task authorization and actual permissions; a review suggestion alone grants neither extra scope nor external-write authority.

A request to implement or fix authorizes the in-scope local corrections and meaningful checks that realize that contract. Merely supplying comments for evaluation does not authorize code changes; distinguish that request from an already authorized correction workflow. Posting messages, resolving external threads, deployment, destructive actions and source publication still require authorization covering that action. Never invent approval provenance or treat AI review as a user decision.

Starting autonomous advancement authorizes the controller to invoke the required stage skills, including otherwise explicit-only review skills, and continue design review, implementation, independent code review, corrections and re-review within that scope without asking at each stage. This organizational authorization does not approve missing initial contracts or material contract changes. A stage executor returns a user-owned decision to the controller; the controller consolidates it for the user. Internal choices need no extra round. Do not send the user to invoke an already authorized next stage manually.

When a skill actually causes a pause, permission request or incomplete result, identify and link its exact `SKILL.md`, quote the operative instruction and explain its application, distinguishing an explicit requirement from your interpretation. Complete unaffected authorized work first.

## Design approval handoff

The design owner or project controller owns the complete approval handoff. Once the candidate is ready for a decision, present the complete current contract, its authoritative artifact/version and consequential changes; establish whether existing user approval covers it. Reuse approval of the unchanged complete contract. Otherwise consolidate the outstanding decisions and explicitly request approval, preserving a pending-user-decision handoff until the user answers. A request to investigate, continue designing or review does not establish design approval. After actual approval, verify that the target remains unchanged before formal publication. Publishing the formal spec attests prior user approval and records its version-bound provenance; do not require separate approval registration or repeat user confirmation before reviewing a published design. Optional explicit sources can still be recorded with `decision-record`. Report the published design and next authorized stage. Approval of design content and authorization to run independent review are separate facts.
