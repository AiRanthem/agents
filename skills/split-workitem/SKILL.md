# Split Work Item

Split only after an oversized work item has a complete spec and current independent design-review Pass (`implementable`). Requirement registration does not start decomposition. During authorized design exploration, identify excessive scope from separable usable outcomes and ownership, verification or rollback boundaries; record `design-update --next-action split` before review. Complete the parent's design to the same rigor as any implementable contract. Its spec must define the whole behavior, cross-item interfaces and invariants, consequential failure outcomes, usable delivery stages, acceptance coverage and the dependency DAG. Future child refinement is not a reason to defer essential decisions. An incomplete or failed parent design returns to authorized design work and independent review before splitting.

Materialize the reviewed stages and DAG without redesigning them. Keep representation, execution, recovery, security, configuration and verification together when they share one correctness boundary. Use one repository per development child. Each child must describe its usable result, acceptance scenario, shared contract, prerequisites and coverage of the original. Preserve original acceptance coverage, incoming references, published IDs, established edges and delivered status. Hierarchy records provenance; dependencies record delivery prerequisites. Never remove an edge merely to pass a gate.

Persist through installed `project.py` and the [fixed command contract](../manage-workitems/references/commands.md). Use `begin create --parent ORIGINAL --title TITLE --slug SLUG` for each child. The program requires the current parent Pass and returns requirement/context drafts plus a spec draft initialized from the parent. Extract the child's complete relevant approved contract, preserving shared constraints and failure boundaries; this is design inheritance, not a mandatory new exploration phase. Set the reviewed prerequisite sets at creation with repeated `--depends-on`, or with `dependency-update` before child review. Read every payload, edit only returned Markdown paths and execute each returned `finish_command` unchanged. Follow the command contract's status handling.

Use `kind-update ORIGINAL --kind aggregate` only when the children fully cover the original outcome and any recorded parent code development has completed verified cleanup with its worktree absent. Make remaining integration an explicit child rather than implementing the split-routed parent. The parent retains its whole-system spec and aggregate acceptance responsibility. The program allocates IDs and validates the graph; the responsible agent assesses semantic coverage against the approved spec.

Children can proceed directly to their own `review-design` with the inherited contract and actual prerequisite baseline; parent Pass is not child Pass. Do not require redesign, extra sections or elaboration for its own sake. A demonstrated omission, contradiction or unresolved consequential choice that prevents correct implementation or acceptance is a blocker and requires supplemental design plus affected independent re-review. Low improvements, document length, formatting preferences and implementation-owned choices do not mandate refinement. Reuse valid independent coverage under the [shared standard](../review-design/references/implementable-gate.md). Changes to parent guarantees, cross-item contracts or the DAG return to the responsible design layer for approval before publication and affected independent review; never silently change them while splitting or refining a child.

Report full IDs with titles, usable outcomes, dependencies, inherited design paths and actual publication status. Finish after the agreed graph and inherited child contracts persist. Continue child review or implementation only under authorization covering that stage; splitting alone does not authorize source implementation.
