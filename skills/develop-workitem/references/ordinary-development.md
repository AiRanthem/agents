# Ordinary project development

For script blockers or defects, [user-authorized manual recovery](../../manage-workitems/references/recovery.md#user-authorized-manual-recovery) defines the approved state/file correction and script repair path. Preserve actual evidence, permissions and source recovery.

Stay rooted at the management project and use an explicit source workdir with its original instructions. A requirement alone does not authorize design or implementation. Read the [project context](../../manage-workitems/references/project-context.md).

Use installed `manage-workitems/scripts/project.py` through the [fixed command contract](../../manage-workitems/references/commands.md). Run the requested `begin OP ID` with its required typed inputs, read its complete payload and required original main-workspace instructions, edit only returned Markdown paths, then execute its returned `finish_command`; design review, design-reuse assessment and implementation review supply actual result/provenance arguments after assessment. `development-finish` requires the actual reviewer session at `begin` and may bind an existing report there. `published` or `no_op` ends that checkpoint; `partial` permits only its returned resume command; for `status: blocked` with `code: stale_ticket`, execute only the returned `next_command`, while `status: blocked` with `code: stale_evidence` has no continuation command and requires current authorization/review evidence. Otherwise report the listed blockers or missing facts. The program owns YAML, document selection, contribution provenance, worktree resolution, gates and Git/Aone checks.

During human acceptance, apply [the final-draft contract](../../complete-workitem/references/delivery-and-cleanup.md#human-final-drafts) to user-requested code and design edits in the retained worktree. Record the real user finalization source and preserve the final drafts without another review or automatic correction. These edits remain in human acceptance; use `development-start` for an explicitly requested return to ordinary agent development. The implementation/review gates below govern that ordinary development.

For requested design, use `design-update` with `explore-design` to maintain the complete current spec. Preserve explicit upstream assumptions; stable design can precede prerequisite delivery. Complete user confirmation before formal spec publication; publishing the approved design records its current approval binding for the authorized independent review. Use `decision-record` for current effective decisions and optional explicit provenance. For an oversized item, include the complete design, delivery stages and DAG, select `design-update --next-action split`, and route current independent Pass to `split-workitem`. Children inherit the relevant design and can enter their own review directly; supplement design only for actual blocking gaps. The program derives raw-byte versions and design state; keep machine state out of spec frontmatter.

For an explicit design-review request, including natural language, load [review-design](../../review-design/SKILL.md) and its [project mode](../../review-design/references/project-mode.md). Review the published versioned spec with its recorded prior user approval. A current independent pass establishes `implementable`. Apply [coverage reuse](../../review-design/references/implementable-gate.md#reuse-independent-coverage) after the complete initial review and prefer the original reviewer while independent. An independent review session may run the ordinary design-review checkpoint directly. A design author delegates the assessment to an independent reviewer, supplying a stable target, full original contract and any authorized candidate for mechanical corrections. The reviewer returns its actual identity, reviewed inputs, findings, result and report; the project operator verifies the target and registers the result through `begin design-review ID --reviewer-session SESSION --review-file FILE` and the returned finish command. Preserve the reviewer and registrar as distinct real contributions. Bound `derived_reuse_pending` permits comparison with the original approved contract and requires actual `--contract-unchanged` confirmation for pass; it grants neither implementation eligibility nor a skip waiver. Missing specs return to authorized design work. Autonomous `advance-project` uses its coordinator checkpoints and fixed single-agent code-review mode.

When a genuine earlier independent design Pass is retained, use the [design-reuse checkpoint](../../manage-workitems/references/commands.md) for authorized applicability assessment. It carries forward unchanged valid coverage; it does not replace a missing review or affected review after material changes. A failed applicability assessment returns the affected scope to independent review.

For requested implementation, use `development-start ID` with the required code inputs; run the returned finish before editing code. The runtime checks contract/review bindings, delivered prerequisites and open upstream fixes and prepares or reuses the worktree. Only the user's explicit scoped waiver permits `--skip-design-review --approval-source SOURCE`; do not infer one from apparent simplicity or a general implementation request.

After successful start use `implement-design`. Before the authorized fresh-subagent `review-implementation`, the controller resolves its mode: honor the user's existing choice or ask once whether to use multi-agent review. Pass that resolved mode with stable inputs, receive real identity/result/provenance/report and use `begin development-finish ID` and its returned finish. That implementation reviewer returns evidence without running project commands. Preserve actual author/reviewer provenance. Use `context-update` for current facts, verification, code snapshot, remaining findings and handoff.

A passing implementation review leaves human acceptance and actual delivery pending. Leave source uncommitted unless separately authorized. Continue in the recorded local worktree using current artifacts and operation records. Complete or recover each project operation before starting the next; retain stable review input identities and register only actual matching reports. Use [complete-workitem](../../complete-workitem/SKILL.md) for authorized real delivery or cleanup. An unfinished upstream fix blocks affected checkpoints.

For a requested replacement of the implementation or switch from autonomous advancement, use the [resource lifecycle](../../manage-workitems/references/resource-lifecycle.md). Account for the current task tree and settle retained publication first. Use `lifecycle handoff` when only execution mode changes, retaining the existing source and its recovery evidence; use `lifecycle replan` and `prepare` when the implementation baseline must be replaced. An adopted lifecycle policy covers only its registered internal resources.
