# Ordinary project development

Stay rooted at the management project and use an explicit source workdir with its original instructions. A requirement alone does not authorize design or implementation. Read the [project context](../../manage-workitems/references/project-context.md).

Use installed `manage-workitems/scripts/project.py` through the [fixed command contract](../../manage-workitems/references/commands.md). Run the requested `begin OP ID` with its required typed inputs, read its complete payload and required original main-workspace instructions, edit only returned Markdown paths, then execute its returned `finish_command`; design review and design-reuse assessment supplies result/provenance arguments to that finish command after assessment. `development-finish` requires the actual reviewer result, provenance, reviewer session and report file as `begin` inputs. `published` or `no_op` ends that checkpoint; `partial` permits only its returned resume command; for `status: blocked` with `code: stale_ticket`, execute only the returned `next_command`, while `status: blocked` with `code: stale_evidence` has no continuation command and requires current authorization/review evidence. Otherwise report the listed blockers or missing facts. The program owns YAML, document selection, owner/session identity, worktree resolution, gates and Git/Aone checks.

For requested design, use `design-update` with `explore-design` to maintain the complete current spec. Preserve explicit upstream assumptions; stable design can precede prerequisite delivery. Own the complete design approval handoff under the shared discussion rules. Use `decision-record --approval-source SOURCE` after actual covering approval, verifying the exact candidate is unchanged; report pending user approval distinctly from pending independent review. Use `decision-record` for current effective decisions and actual user approval provenance. The program derives raw-byte versions and design state; keep machine state out of spec frontmatter.

For an explicit design-review request, including natural language, load [review-design](../../review-design/SKILL.md) and its [project mode](../../review-design/references/project-mode.md) for every ordinary review route. First establish recorded current approval or valid applicability carry-forward of a genuine earlier Pass. Bound `derived_reuse_pending` from an inconclusive applicability assessment permits only independent comparison against the original approved contract, with actual `--contract-unchanged` confirmation required for pass; it does not permit implementation or a skip waiver. When neither exists, return the approval handoff to the design owner rather than inventing a source; eligible unchanged coverage uses the owner/controller’s `design-reuse` checkpoint before requesting approval again. For an independently requested ordinary design review of an unowned item, the independent review session owns `begin design-review ID` and its finish command. A design author delegates that complete workflow to an authorized independent reviewer. Apply [coverage reuse](../../review-design/references/implementable-gate.md#reuse-independent-coverage) after the complete initial review; a later review round does not require a new context. For an item still owned during development, retain that owner and worktree: assign an independent `review-design` worker, preferentially the original reviewer if still independent, a stable source target and any authorized candidate for mechanical corrections, with the complete current contract and original instructions, and request a temporary report containing its actual session, reviewed input identity, findings and result. That worker does not run project commands. The owner checks that the reported target is still current, registers `begin design-review ID --reviewer-session SESSION --review-file FILE`, then finishes with the actual result/provenance. The program preserves the development owner and records the independent reviewer separately from the registrar. These ordinary external identity fields are owner-captured assertions, not host-signed identities; never invent them or turn self-review into an external report. A current independent pass establishes `implementable`; exploration cannot manufacture it. Autonomous `advance-project` uses its coordinator checkpoints and fixed single-agent code-review mode.

When a genuine earlier independent design Pass is retained, use the [design-reuse checkpoint](../../manage-workitems/references/commands.md) for authorized applicability assessment. It carries forward unchanged valid coverage; it does not replace a missing review or affected review after material changes. A failed applicability assessment returns the affected scope to independent review.

For requested implementation, use `development-start ID` with the required code inputs; run the returned finish before editing code. The runtime checks contract/review bindings, delivered prerequisites and open upstream fixes and prepares or reuses the worktree. Only the user's explicit scoped waiver permits `--skip-design-review --approval-source SOURCE`; do not infer one from apparent simplicity or a general implementation request.

After successful start use `implement-design`. Before the authorized fresh-subagent `review-implementation`, the controller resolves its mode: honor the user's existing choice or ask once whether to use multi-agent review. Pass that resolved mode with stable inputs, receive real identity/result/provenance/report and use `begin development-finish ID` and its returned finish. That implementation reviewer returns evidence without running project commands. Preserve actual author/reviewer provenance. Use `context-update` for current facts, verification, code snapshot, remaining findings and handoff.

A passing implementation review leaves human acceptance and actual delivery pending. Leave source uncommitted unless separately authorized. Preserve existing owner/development across sessions and machines; age or a new session does not authorize takeover. Use [complete-workitem](../../complete-workitem/SKILL.md) only for authorized real delivery or cleanup. An unfinished upstream fix blocks affected checkpoints.

For a requested replacement of old implementation or switch from autonomous advancement, use the [resource lifecycle](../../manage-workitems/references/resource-lifecycle.md). Account for the current task tree and settle retained publication first. Use `lifecycle handoff` when only execution mode/coordination changes, retaining the existing source and predevelopment marker; use `lifecycle replan` and `prepare` when the implementation baseline must be replaced. Existing predevelopment work does not become formal merely by choosing manual mode. An adopted lifecycle policy covers only its registered internal resources.
