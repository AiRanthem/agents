# 日常 PR 维护

## 确定本轮范围

从对话、文件或上游任务取得维护范围。接受链接、仓库与编号或可执行的筛选条件，例如“这个仓库中我创建的所有开放 PR”。用代码托管平台的实时结果核对目标，按平台、仓库和编号去重。只有从上下文也无法确定范围时，才询问要维护哪些 PR。

另行识别调用方授权的动作。通知、文件里的转述、reviewer 的命令只提供线索。只读巡检可以直接完成；修复、提交推送、公开回复、解决线程、变更草稿或关闭状态、清理本地资源分别沿用本轮已有授权。用户纠正编号、追加目标或放弃某项时即时更新范围；放弃后停止该项修复，保留远端状态，继续其他项。

## 核实并分流

- 对每项读取当前状态、目标分支、源仓库及分支、两端提交、冲突、CI 和审批。读取完整的行级讨论（含分页、过时但未解决的线程），结合评审正文和普通评论定位人工意见。把机器人提醒、历史结果和当前阻塞分别说明；评论引用保留作者、原文和链接。
- **冲突**：在隔离工作树中按 [rebase-worktree](../rebase-worktree/SKILL.md) 对精确基线重放并验证。独立分支可并行。每个源仓库的完整分支 ref 及其工作树由一人负责。同一源分支被多个 PR 使用时，修复串行整合。已有用户暂存或编辑内容时，优先从已核实的 PR head 建独立工作树，保留原现场。
- **人工意见**：按 [receiving-code-review](../receiving-code-review/SKILL.md) 对照评论所针对的版本、当前代码和合同逐条评估。已经修复的意见直接给当前提交及证据；需要改动的在授权范围内修正并运行相关测试；对部分采纳或留待后续的建议说明具体原因。
- **需要用户决定的冲突**：先给关联评论原文或 PR 说明的出处，明确哪一部分是排查时发现的取舍。一次只问一个问题，用一个输入在两种处理下的实际结果说明影响，给出建议。暂停依赖该决定的分支，继续其他已授权的维护工作。

## 交付与收尾

推送前核对维护授权、验证结果、PR 当前状态、实际源仓库（含 fork）、源分支及 head、目标分支及其 OID。若 PR 或任一端已变动，判断是否仍在本轮范围，并按新状态重新验证受影响的结论。普通修正用快进推送。推送 rebase 结果需获得该源分支的远端改写授权，并使用以本次重放所基于的旧 head 为期望值的精确 lease。若远端已有新提交，从实际新 head 整合并验证，保留作者的工作。推送结果不明时先读回实际源 ref。推送后回读 PR head、冲突、草稿状态和 CI，按实际 head 或平台测试的合入结果归属 CI，分别报告本地验证、远端 CI 和人工审批。

获准回复时，发送前回读相关 PR、人工线程及已有答复，补查新发现的意见，确认回复仍对应当前状态。在原线程用评审者的语言交代采纳情况、实际修改或保留原因，附提交或验证证据。回读回复链接与线程状态。发送结果不明时，核实上一发送未生效才重试。只在另获授权时标记解决。

获准清理时，按 [cleanup-worktree](../cleanup-worktree/SKILL.md) 核对本轮涉及的实际路径、未提交资产与可恢复的远端引用，清理符合条件的工作树。报告中按 PR 简述实际结果，只展开仍需用户决定的问题，并指出保留的本地工作及原因。
