# Discussion and authorization

Apply these rules in ordinary development, read-only planning and managed-project work. Explicit user instructions take priority over skill guidance. Reuse the approved scope, requirements, paths, tradeoffs and execution authorization from the conversation; do not ask the user to repeat them. Actual harness, security and filesystem permissions still apply.

A user's explicit acceptance records the actual human conclusion and accepted implementation. During human acceptance, preserve user-finalized code and design and align only outdated text left for reconciliation. Reuse a covering acceptance conclusion for subsequent finalization, retaining its actual source. Record human acceptance separately from independent review and retain earlier reviews at the targets actually reviewed. Report checks that were not executed as unverified. External actions require covering authorization; actual permissions and data protection remain in force.

When the sandbox prevents an already authorized command from starting, use the host's permitted approval or escalation mechanism for that same command. Continue only after actual approval; a denied request remains blocked and must not be bypassed.

Before asking for a decision, investigate the relevant original instructions, contract, code, callers and available evidence. Resolve factual uncertainty yourself where possible. Make reasonable, reversible assumptions within the authorized scope and state those that affect the result. Complete independent authorized work that makes the choice concrete, and combine the remaining consequential choices into one coherent decision batch. Explain the evidence, recommendation, meaningful alternatives and consequences. Revisit a settled choice only when new evidence invalidates it. Silence, elapsed time and a tool timeout are not approval. Pause only work that depends on an unresolved required choice and continue other authorized work.

Within an unchanged approved contract, the executor chooses internal implementation, private types and helpers, local representations, verification and equivalent internal corrections. Obtain the user's decision before changing requirements, public or stored contracts, compatibility, a user-selected tradeoff, key constraints, approved security or correctness guarantees, or acceptance criteria. Preserve these guarantees and criteria through completion. A new dependency or external action is governed by the existing task authorization and actual permissions. A review suggestion alone grants neither extra scope nor external-write authority.

A request to implement or fix authorizes the in-scope local corrections and meaningful checks that realize that contract. Merely supplying comments for evaluation does not authorize code changes; distinguish that request from an already authorized correction workflow. Posting messages, resolving external threads, deployment, destructive actions and source publication still require authorization covering that action. Never invent approval provenance or treat AI review as a user decision.

Before returning, check the requested outcome, deliverables and verification against the authorized scope. Complete any remaining authorized in-scope steps yourself. Stop affected work when it is complete, a concrete blocker prevents progress, or a material scope change, consequential decision or irreversible action needs the user's input or authorization. Follow the approval and handoff requirements of the active mode.

When a skill actually causes a pause, permission request or incomplete result, identify and link its exact `SKILL.md`, quote the operative instruction and explain its application, distinguishing an explicit requirement from your interpretation. Complete unaffected authorized work first.

Write the handoff anew for a reader who has not followed the progress updates. Lead with the outcome. Keep the technical details and terminology from the request and sources that make the explanation precise. Introduce concepts before referring back to them. Use active voice, keep related details together, and give the reader enough context to follow the evidence and reasons. Draft external material for the intended audience and supply background they would otherwise lack. When editing existing material, preserve the author's wording and content outside the requested edits. Leave working shorthand from internal notes, tools or delegation out of user-facing material.

## Design approval handoff

The design owner presents the complete current contract and consequential changes for the user's decision. Reuse approval of an unchanged contract. Otherwise consolidate outstanding choices and request the user's decision. A request to investigate, continue designing or review does not establish design approval. In a managed project, record genuine approval in the existing design and decision records and publish the authorized project update. Approval of content and authorization to run independent review are separate facts.
